检索增强生成（retrieval-augmented generation，RAG）的效果，有一大半在写第一行检索代码之前就定了：文档被切成什么样，检索就只能返回什么样。切分不是预处理里的杂活，它同时决定嵌入（embedding）向量的语义纯度、上下文窗口（context window）的填充效率，以及答案能不能被追回到原文。这篇把我自己反复调过的那几个参数和判断写下来。

## 一个块就是检索的最小单位

块太小，指代就断了。"退款时限见 3.2 节" 单独成块之后，模型拿到的是一句没有主语的残句，检索再准也答不出来。块太大，语义就被平均掉：一个两千字的块里只有两句话相关，嵌入向量会被其余内容稀释，相似度分布被压平，前十里全是"看起来都差不多"的长块，反而挤掉了真正精确的小块。

这里有个容易被忽略的换算。中文的字符与 token 并不等价：BGE、m3e 这类中文词表接近一比一，而 Qwen、GPT 系的 BPE 词表在中文上常见一比一点五。所以标注为 512 token 的分块器，落到中文正文往往只有三百多字。我第一次按英文经验设 512，实际切出来平均 340 字，短句多的文档还会更碎。

```python
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
text = "向量检索的召回率在长文档上会明显下降。"
print(len(text), len(enc.encode(text)))   # 19 23：中文常常是 token 比字符还多
```

我的做法是先按汉字数量定目标，再用 token 数做上限兜底，两个约束同时生效，避免换模型后块长突然漂移。

## 三种切分粒度与各自的代价

| 方式 | 切分依据 | 优点 | 典型失败 |
| --- | --- | --- | --- |
| 固定长度 | 字符或 token 数 | 实现简单、块长均匀 | 句子被腰斩，标题与正文分离 |
| 结构切分 | 标题层级、列表、表格 | 语义单元完整、可回溯 | 遇到超长章节仍需二次切 |
| 语义切分 | 相邻句向量相似度 | 主题边界贴合内容 | 成本高、阈值随模型漂移 |

语义切分的账要算清楚：它需要对每一句做一次嵌入，成本与句子数成正比，一篇两万字的文档就是上千次调用。更麻烦的是阈值。我见过到处抄的 0.75，换个嵌入模型就完全失效，因为不同模型的余弦相似度分布根本不可比。

我的判断是：语义切分的收益集中在"主题跳变但没有标题"的文档上，比如会议记录、访谈整理、问答合集。对结构良好的技术文档，按标题切已经接近上限，再叠语义切分只是在给噪声分层。

## 重叠是必要的浪费，但要可控

重叠（overlap）的直觉是防止边界处的信息丢失：一句话被切成两半，前后各带一半，至少有一块能看到完整句子。常见取值是块长的百分之十到十五。

代价有两层。存储上，百分之十五的重叠意味着索引体积增加约百分之十五。检索上更隐蔽：同一段内容以不同偏移出现三四次，可能同时占满前五，把其他相关段落全部挤出去。这个问题在小语料上不明显，文档一多就变成主要噪声源。

我的处理是给同源块加一个 `parent_id`，命中后按父块去重，或者把相邻块合并成一个窗口再送给模型。当块本身小于一百字时，重叠比例失去意义，我直接改成整段不切——短块的重叠只会制造近乎重复的向量。

## 结构优先：表格、代码与标题

表格不能按行切。一行 `| 退款 | 7 天 |` 脱离表头之后，"7 天"指什么完全不可知。我的做法是把表格整体保留，超过长度上限就转成"列名: 值"的键值文本再切，宁可损失排版也不丢语义。

代码块必须整体保留，并且在块文本前补一行说明它属于哪个文件、哪个函数。检索时经常是函数名先命中，正文才有意义。

标题要拼进块文本，形成面包屑路径。否则"3.2 退款政策"离开父标题就只剩一个编号，向量里没有任何可检索的信息。

```python
def split_by_heading(text: str, path: tuple[str, ...] = ()):
    """按二级/三级标题切分，标题路径拼进块前缀。"""
    chunks, buf, cur = [], [], path
    for line in text.splitlines():
        if line.startswith(("## ", "### ")):
            if buf:
                chunks.append((" > ".join(cur), "\n".join(buf)))
                buf = []
            cur = path + (line.lstrip("# ").strip(),)
        else:
            buf.append(line)
    if buf:
        chunks.append((" > ".join(cur), "\n".join(buf)))
    return [{"section": s, "text": f"{s}\n{t}"} for s, t in chunks]
```

## 我的参数区间与自检方式

我现在的默认值是：技术文档目标块长四百到六百汉字，重叠六十到八十汉字，表格与代码不切；每次切完保留 `doc_id`、`section_path`、`char_start`、`updated_at` 这几个元数据字段，后面做引用回溯和增量更新全靠它们。

调参不靠感觉，靠一批小样本。我会从真实问题里挑二十到三十条，每条人工标出至少一个正确块，然后比较不同切分参数下的 recall@5。这个集合一小时能建完，却比任何"最佳实践"都更能说明问题，因为切分的好坏高度依赖你自己的文档形态。经验上，块长从三百提到五百带来的召回提升，往往大于把嵌入模型换大一档。

还有一个和块长纠缠不清的变量：嵌入模型自己的输入上限。多数中文嵌入模型是五百一十二 token，超过就截断，而且是静默截断——不报错，只是后半段没进向量。如果分块器按八百字切，前面五百字进了向量，后面三百字形同虚设，检索时永远命中不了。我会在写完分块器之后立刻加一条断言，把每个块的 token 数打出来，超过上限的直接报错而不是放行。截断造成的召回缺失极难从结果上反推，因为它表现得和"这段内容本来就不相关"一模一样。

最后一个容易忘的检查：把切出来的块按长度排序，看最短的那批。如果出现大量三四十字的碎片，问题通常不在分块器，而在原始文档的解析——PDF 提取把一段话拆成了十几行，标题识别失败，表格被压成一行。先修解析，再谈切分。
