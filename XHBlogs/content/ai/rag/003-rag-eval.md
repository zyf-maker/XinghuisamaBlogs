RAG 系统出问题时，最难的不是修，而是先说清楚是哪一层坏了。用户说"它答错了"，这句话至少对应三种完全不同的故障：检索没找到正确文档、找到了但模型没看进去、模型看了却自己编了一段。这三种故障的修复手段毫无交集，如果不分层评测，就只能靠猜着改提示词。

## 先分清检索层与生成层

我的划分很简单：检索层只回答"该在的资料在不在前 k 条里"，生成层只回答"回答是否只依赖给定的资料"。两层的输入输出可以完全隔开，所以指标也能隔开。

对应到具体指标，检索层用命中率（hit rate）与召回率（recall@k），生成层用忠实度（faithfulness）与答案相关性。把这两组合并成一个"总分"是常见的错误，它会掩盖掉真正的瓶颈。我见过总分零点八的系统，拆开看召回零点九、忠实度零点五，问题很清楚：不是找不到，是找到了还在编。

## 构建评测集：小规模、人工标注、含反例

评测集不用大。我通常从真实提问里抽三十到五十条，每条标注三样东西：问题、参考答案里必须出现的关键事实、以及支撑这个事实的原文块标识。

关键在选样。按查询类型分层抽：单跳事实、多跳推理、精确字符串查找、以及知识库里根本没有答案的问题。最后一类最容易被忽略。没有答案的问题用来测模型会不会硬编，它是幻觉最直接的探针。如果评测集里全是"有答案"的题，召回的短板永远暴露不出来。

标注原文块这一步不能省。没有它，你只能测端到端效果，一旦变差就不知道是检索退了还是模型变了。

```python
eval_set = [
    {
        "q": "退款审核最长需要多久？",
        "gold_facts": ["7 个工作日"],
        "gold_chunk_ids": ["policy-3.2#2"],
        "answerable": True,
    },
    {
        "q": "支持数字人民币退款吗？",
        "gold_facts": [],
        "gold_chunk_ids": [],
        "answerable": False,
    },
]
```

## 召回率怎么算才不误导

`recall@k` 的分母是"应当召回的相关块数"，但一个问题的相关块可能只有一个，也可能有三四个。如果标注时只标了一个，而系统召回了另一个同样正确的块，指标会误判为失败。我的处理是把同义或等价的块合并成一个标注组，命中任一即算命中。

还有个陷阱是 k 的选择。k 从五提到十，召回几乎必然上涨，但送给模型的上下文也翻倍，生成质量可能下降。所以我固定两个观测点：`recall@5` 用于评估直接送模型的配置，`recall@20` 用于评估重排（rerank）之前的候选池。前者看最终体验，后者看检索本身的上限。如果 `recall@20` 已经很低，再怎么调重排都没意义，该回去修切分或换嵌入模型。

实际算的时候，别只看平均值。我会把失败样本按查询类型分组打印，因为分布往往极不均匀：自然语言提问的召回可能到零点九，而错误码查询只有零点三。平均值零点六看起来"还有提升空间"，实际上是一个好好的系统被一类查询拖垮了。

## 忠实度：判断答案有没有超出资料

忠实度衡量回答中的每个论断能否在检索到的上下文里找到支撑。做这件事有三条路，成本依次上升。

第一条是让另一个模型做判定，给出"支持 / 不支持 / 矛盾"三分类。便宜，但判定器本身会有偏差，尤其是长上下文里跨段落的推理。第二条是拆成原子论断逐条核验，准确率高但调用次数按论断数增长。第三条是规则法，只对数字、日期、专有名词做字符串比对。

我的做法是混合：数字和日期一律用规则卡死，因为这些是最容易被编造也最容易验证的；其余论断用模型判定，并且要求它引用具体句子，引不出就判不支持。要求引用这一步很关键，它把"感觉像是支持的"变成了"能指出来源"。

```python
import re

def check_numbers(answer: str, contexts: list[str]) -> list[str]:
    """回答里的数字必须原样出现在上下文中。"""
    nums = re.findall(r"\d+(?:\.\d+)?%?", answer)
    joined = " ".join(contexts)
    return [n for n in nums if n not in joined]
```

这个函数很粗糙，会把"7 个工作日"里的 7 与"7 天"混淆，但它抓出的问题往往是真的。

## 幻觉定位：把错误落到具体环节

定位幻觉需要可回溯的链路。我在每次请求里记录三个东西：召回块的 id 列表、重排后的顺序、以及最终送给模型的完整上下文。有了这三样，一条错误回答可以按下面的顺序排查。

先看答案里的事实有没有出现在上下文中。没出现，是生成层越界，去查提示词里有没有"仅根据以下资料回答"这类约束，以及上下文是否被截断。出现了但答案取错了，通常是上下文里有多处相似表述，模型选了旧版本——这时候元数据里的版本号和生效日期就派上用场。出现了、取对了，但答案没引用，那是引用格式的问题，不影响正确性。

再看正确块在不在召回列表里。不在，是检索层问题，回去看切分和索引。在，但排在第十位被截断，那是排序问题，上重排或者调整融合权重。

这条链路听起来琐碎，但它把"答错了"变成了一个可以在五分钟内定位的判断，而不是一次凭直觉的改 prompt。

## 别把评测做成一次性项目

我见过太多评测集建完跑一次就再没人打开。要让它活着，得挂到流程上：每次改切分参数、换嵌入模型、调提示词，都跑一遍同一套题，把结果记进一张表。变化超过阈值才人工复核。

还有一个成本上的判断：端到端的人工评分每个样本要几分钟，模型判定只要几秒。我的配置是模型判定全量跑，人工只抽查模型判定为失败或低分的样本，以及每次发版前抽十条。这样既保住了覆盖率，也没有把时间全花在重复劳动上。

最后提醒一句，指标要连着看。忠实度提高但答案相关性下降，通常意味着模型变得过于保守，只会复述原文；召回提高但忠实度下降，可能是塞进去的噪声变多了。单看任何一个数字都会做出错误决定。
