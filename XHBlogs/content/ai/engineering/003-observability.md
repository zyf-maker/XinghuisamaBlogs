传统服务的排查路径很清晰：有报错、有堆栈、有请求参数，照着复现就行。AI 功能不是这样。它不抛异常，只是答错了——而「错」本身没有堆栈可看。用户反馈「昨天它给我算错了」，你打开日志，只看到一条 HTTP 200 和 800 个 token 的输出。

这篇文章讲我为了回答「这次回答为什么不对」而建的那套记录，以及它和评测集之间怎么接上。

## 一、只记 request 和 response 是不够的

最开始我们的日志就两栏：请求体、响应体。存了三个月，一次真正的线上问题都没查明白。因为影响输出的东西，绝大部分不在请求体里。

举一个具体的例子。用户问「这个月的报销还能报多少」，回答少算了一笔。请求体看起来完全正常，响应体语法也没问题。真正的原因是那天检索召回的文档里混进了一份去年的旧制度，而检索结果当时没有落日志。等用户反馈过来，那份召回结果早就没了，无法确认。

所以我后来定的字段清单是这样的，分四组：

**标识组**：`trace_id`（一次用户请求）、`call_id`（一次模型调用）、`session_id`、`user_id_hash`、`feature`、`app_version`。

**输入组**：完整的 messages 数组（不是拼接后的字符串）、`prompt_tokens`、`cached_tokens`、模型名与版本快照、`temperature`、`max_tokens`、`top_p`。模型名要带日期后缀，同一个别名背后的实际版本会变，这点吃过亏。

**上下文组**：检索 query、召回文档的 id 与分数（前 10 条）、重排后的顺序、命中的工具及其返回摘要、用户在本次请求前的最新操作。

**输出组**：完整输出、`finish_reason`、`completion_tokens`、首 token 延迟、总耗时、是否走了降级。

存储上，输入输出全文太大，全量存不现实。热存 7 天（可直接查），冷存 90 天（压缩后放对象存储，键是 `trace_id`）。7 天覆盖绝大多数反馈周期，90 天用来做季度复盘。

隐私方面有两件事必须做在前面：`user_id` 只存哈希；输入里的手机号、身份证号在落盘前脱敏。脱敏放在日志 SDK 里统一做，别让业务方自己处理——一定会有人忘。

## 二、trace 要串起来，而且要能回放

一次对话的调用链比想象中长：前端请求、鉴权、意图分类（可能一次小模型）、检索、重排、主模型、可能还有一次工具调用和一次总结。任何一环出问题，表现都是「答得不对」。

我用 OpenTelemetry 的 span 结构串这条链，每个 span 带自己的属性：

```python
from opentelemetry import trace

tracer = trace.get_tracer("ai.chat")

with tracer.start_as_current_span("llm.chat") as span:
    span.set_attribute("ai.feature", "reimburse_qa")
    span.set_attribute("ai.model", "gpt-4.1-mini-2025-04-14")
    span.set_attribute("ai.prompt_tokens", 3120)
    span.set_attribute("ai.cached_tokens", 2816)
    span.set_attribute("ai.completion_tokens", 412)
    span.set_attribute("ai.temperature", 0.2)
    span.set_attribute("ai.retrieval.top_ids", "doc_881,doc_902,doc_117")
    span.set_attribute("ai.retrieval.top_scores", "0.82,0.79,0.61")
    span.set_attribute("ai.finish_reason", "stop")
    span.set_attribute("ai.fallback", False)

    with tracer.start_as_current_span("retrieval.search") as s:
        s.set_attribute("retrieval.k", 20)
        s.set_attribute("retrieval.rerank_k", 5)
```

注意 `retrieval.top_scores` 这类字段。只记 id 不够，你要能看出「召回了但分数很低」和「压根没召回」，这两种情况的修法完全不同。

串起来之后还要能回放。回放不是「再问一遍」，因为再问一遍模型可能给出不同答案，你无法判断是修好了还是碰巧。回放是把当时记录的完整 messages、参数、模型快照原样重放，看输出是否一致。一致说明问题在输入侧（检索、拼装、上下文）；不一致说明问题在采样随机性或模型版本。

我做过统计，线上「答错」的案例约七成在回放时能稳定复现，属于输入侧问题；剩下三成来自采样随机性或版本变化，改 prompt 解决不了，只能靠评测集覆盖。

回放要注意锁定模型版本。厂商只给浮动别名时，回放就分不清是代码变了还是模型变了。这也是我坚持在日志里存完整版本号的原因。

## 三、坏回答的复现流程

有了上面的记录，排查流程大概是这样的。用户反馈「上周三问报销额度，它说还能报 2000，实际应该是 5000」。第一步，用 `user_id_hash` 加时间窗口找到那条 `trace`。这步的前提是日志里存了用户可检索的维度、且时间窗口能对上——所以前端在反馈入口要自动带上 `trace_id`，别指望用户描述时间。我们后来在所有回答下面加了反馈按钮，点击时把 `trace_id` 一起提交，定位时间从平均 20 分钟压到一分钟以内。

第二步，看检索。那次的前 10 条召回里，第 3 条是去年的旧制度，分数 0.78，比今年的新版（0.71）还高。原因是旧文档里「报销」出现的次数更多，向量相似度被拉高了。

第三步，看拼装。文档是按分数顺序拼进 prompt 的，旧制度在前面，模型优先采用了它。

第四步，定修法。这不是 prompt 问题，是检索问题。修法可以是加时间过滤（只召回生效中的制度），也可以是加元数据加权。如果只看输入输出，我会误以为是模型不听话，然后去改 prompt——那是最常见也最无效的一种修法。

这个案例后来进了评测集：query 固定，期望召回必须包含新版制度 id、且不能包含旧版。这类样本比「问一句看答得好不好」有用，因为它能定位到具体环节。

## 四、trace 和评测集之间那条链路

trace 是「发生过什么」，评测集是「应该发生什么」。两者的关系经常被搞混，导致团队花大力气建了一套评测，线上该出的问题一个没少。

我的做法是把它们接成一条流水线：

**线上 trace → 采样 → 人工标注 → 进入评测集 → 回归测试 → 上线**。

采样不能随机。纯随机采样里 95% 是正常样本，标了也没用。我按三个信号采样：用户点了「不满意」的、走了降级路径的、以及 `finish_reason` 异常的。这三类加起来每天几十条，人工标注的成本可控。

标注只标两件事：这条回答算不算合格（好、可用、差），以及不合格时问题出在哪一环（检索、上下文、指令、模型能力、工具）。第二列比第一列重要，因为它直接指向修法。

标注完的样本进入评测集时，要带上完整的输入快照，包括当时的检索结果。这样回归测试才能区分「检索改好了」和「模型碰巧答对了」。这一条我踩过坑：早期评测集只存了 query 和标准答案，重构检索之后分数涨了，但没人知道涨在哪，也无法判断是不是过拟合。

评测集还要分层。我分了三个集合：**冒烟集** 30 条，覆盖主流程，每次提交都跑，要求 3 分钟内出结果；**回归集** 200 条，覆盖历史 bug，每天跑一次；**探索集** 500 条，覆盖长尾，每周跑一次。三层目的不同，混在一起会导致要么太慢没人跑，要么太浅发现不了问题。

有一条我盯得比较紧：**评测集与线上的分布偏差**。如果评测集里的问题平均长度是 20 字，线上是 120 字，那评测分数再高也没有参考价值。每月对比一次两者的 token 分布和意图分布，偏差大就补样本。

## 五、几个具体的坑

**日志里存了拼接后的 prompt，没存 messages 结构。** 出了问题想改一版重放，发现无法还原哪段是 system、哪段是检索内容。后来统一存 messages 数组，拼接只发生在最后一刻。

**时间戳用服务器本地时间。** 跨时区排查时对不上，用户说「昨晚十点」，日志里是 UTC 凌晨两点。全部改 UTC 存、展示时再转。

**只记成功调用。** 超时和 429 的请求没进日志，结果成本对不上账，也没法分析失败率。所有出站请求都要落一条，包括失败的，带上错误码和耗时。

**采样率一刀切。** 早期为了省存储把采样率设成 10%，结果用户反馈的那条恰好没被采到。改成：默认 10%，但带反馈标记的、走降级的、报错的 100% 保留。规则在 SDK 里写死，不依赖业务方传参。

**评测集和线上用的不是同一个 prompt 版本。** 评测脚本里硬编码了一份 prompt，改了线上忘了改评测，两边分数对不上。现在 prompt 是一个带版本号的模块，评测和线上引用同一个，日志里也记版本号。

可观测性的收益要等到下次出问题才兑现。但 AI 功能进入第二季度后，没有这套东西的团队会陷进一种状态：知道效果不好，却不知道该改哪里，只能反复调 prompt 和换模型。那不是优化，是抽奖。
