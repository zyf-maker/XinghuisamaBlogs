上线第二周遇到一次上游限流。监控图上 429 从零跳到每分钟 400 次，用户侧是一片「生成失败」。当时的第一版处理是所有非 200 都进同一个重试函数，固定间隔 1 秒，重试 3 次。结果是把 429 放大成了接近三倍的请求量，上游的限流窗口被客户端自己撑满，恢复时间从预估的 30 秒拖到了 6 分钟。

那次事故之后，这块逻辑值得整体重写一遍。这篇文章是重写时的判断依据。

## 一、429 和 5xx 不是一类问题

429 说的是「你的配额用超了，慢点发」，请求本身没毛病。5xx 说的是「服务端这边出问题了」，可能是过载，也可能是某个 shard 挂了。把两者放进同一个重试分支，是那次事故的直接原因。

一种常见的分法：

| 状态码 | 含义 | 处理 | 退避基线 |
| --- | --- | --- | --- |
| 429 | 配额或并发超限 | 读 `Retry-After`，尊重它 | 无该头则 2s 起 |
| 500 / 502 | 上游内部错误 | 有限重试 + 抖动 | 500ms 起 |
| 503 | 过载或维护 | 优先降级，少重试 | 1s 起 |
| 504 / 超时 | 上游挂住 | 不重试同请求，走降级 | — |
| 400 / 422 | 请求本身非法 | 绝不重试 | — |
| 401 / 403 | 鉴权 | 绝不重试，告警 | — |

几个细节值得说。

`Retry-After` 要读，而且可能是秒数也可能是 HTTP 日期，两种格式都得解析。上游明确告诉你等 12 秒，你就等 12 秒；自作聪明改成 1 秒重试，只会再吃一个 429。

400 类绝对不能重试。最典型的情况是 prompt 超过上下文长度，重试一百次结果都一样，只是把配额白白烧掉。这类错误应该在组装请求的时候就拦住，用 token 计数器先算一遍。

504 和超时也不建议重试。超时意味着上游可能已经开始生成并计费了，重发会造成两份费用，而且用户等的时间翻倍。这种情况直接降级，比傻等更体面。

## 二、指数退避的参数怎么定

退避的公式本身没什么争议：

```
delay = min(base * 2^attempt, cap) * (1 + random(-jitter, +jitter))
```

真正要调的是几个数。比较稳妥的取值：

- `base`：429 用 2 秒，5xx 用 0.5 秒。理由是 429 的恢复时间通常在秒级，5xx 的瞬时抖动通常很快过去。
- `cap`：8 秒。再长用户就走了，不如直接降级。
- `jitter`：±30%。没有抖动的话，同一时刻失败的 200 个请求会在同一毫秒重试，形成波峰，这叫重试风暴。
- 最大次数：3 次。加上首次请求，总共 4 次。对一次需要 3 秒的生成来说，这已经是 20 秒以上的等待。

有个容易忽略的点：**抖动要用全抖动还是等抖动**。等抖动（±30%）够用了，全抖动（0 到 delay 之间随机）会让部分请求几乎立刻重试，对缓解拥塞帮助不大。等抖动通常是更好的选择。

另一件事是**重试预算要按请求算，不是按调用算**。一次用户请求里可能有检索、主模型、总结三次模型调用，如果每次都能重试 3 次，最坏情况是 9 次重试，延迟不可控。可行的做法是在请求上下文里放一个预算，比如总共允许 3 次重试，谁先用完谁用：

```python
class RetryBudget:
    def __init__(self, total=3):
        self.left = total

    def take(self) -> bool:
        if self.left <= 0:
            return False
        self.left -= 1
        return True

def call_with_retry(fn, budget: RetryBudget, deadline_ms: int):
    start = time.monotonic()
    attempt = 0
    while True:
        try:
            return fn()
        except RetryableError as e:
            elapsed = (time.monotonic() - start) * 1000
            if not budget.take() or elapsed > deadline_ms - 500:
                raise
            base = 2.0 if e.status == 429 else 0.5
            delay = min(base * (2 ** attempt), 8.0)
            delay *= 1 + random.uniform(-0.3, 0.3)
            if e.retry_after:
                delay = max(delay, e.retry_after)
            time.sleep(delay)
            attempt += 1
```

`deadline_ms - 500` 这个判断很重要：如果剩余时间不够一次像样的尝试，就别开始了，直接抛出去走降级。剩下 200 毫秒还要重试，结果只是把超时从一个地方挪到另一个地方。

## 三、幂等：重试之前先问自己会不会写两次

读请求天然幂等，重试无所谓。但 AI 功能经常带副作用：写数据库、发消息、扣额度、调第三方下单。这些一旦重试就可能执行两次。

一个常见的坑是「保存对话」和「生成回答」放在同一个事务里：生成成功、写库超时、重试生成、写库成功——数据库里多了一条重复记录，还多了一次模型费用。用户看到两条一模一样的回答。

现在的原则是：**副作用和模型调用分离，副作用以 `call_id` 为幂等键**。

```sql
INSERT INTO messages (call_id, session_id, role, content, created_at)
VALUES ($1, $2, 'assistant', $3, now())
ON CONFLICT (call_id) DO NOTHING;
```

`call_id` 在发起模型调用之前就生成好，重试时沿用同一个。这样即使重试了三次，落库也只有一条。

对于调用外部服务（比如退款、下单），幂等键要传给对方，用对方的幂等接口，而不是自己在本地区分。本地去重挡不住「请求发出去、对方处理了、响应丢了」这种情况。

还有一个隐性的副作用：**计费**。如果你的计费是按调用次数算的，重试必须不计费，或者按 `call_id` 去重。这一点在财务对账的时候会暴露，越早处理越好。

## 四、降级阶梯

重试解决不了的问题，就靠降级。降级通常分四级，从轻到重：

**第一级，换同档模型的另一个部署。** 多区域或多供应商的情况下，A 区 429 就切 B 区。这一级对用户几乎无感，延迟可能略高。

**第二级，降到小模型。** 主模型不可用时，用小模型生成。这里必须改 prompt——小模型照搬大模型的长指令通常效果很差。建议给每档模型维护一份精简指令，长度大约是大模型的三分之一，只保留硬约束和输出格式。

这一级要防的是「静默降质」。用户不知道这次的回答来自小模型，而小模型在复杂问题上错得更多。可行的处理是在响应里带 `model_tier`，前端在回答下方显示一个不显眼的标记。别做成警告条吓人。

**第三级，规则兜底。** 常见问题走预置答案库，用关键词加意图匹配。覆盖率不高，一般大概能接住 15% 的流量，但它的价值在于「永远可用」。这部分内容必须人工审核过，宁可答得保守，不能答错。

**第四级，明确失败。** 告诉用户「服务暂时繁忙，请稍后重试」，并给一个重试按钮。这一级听起来很失败，但比让用户对着转圈等 60 秒要好。关键是快——从判定失败到展示提示最好不要超过 1 秒。

降级的触发条件不能只看状态码。三个信号任一满足就降：连续 3 次 429、错误率在 1 分钟窗口内超过 20%、P95 延迟超过 15 秒。第二个信号是为了应对「不报错但很慢」，这种最容易被监控漏掉，因为成功率是 100%。

还有熔断。连续失败达到阈值后，直接在一段时间内跳过主模型，不再发请求。熔断的恢复要用半开模式：放 5% 的流量去试探，成功了再全量恢复。不做半开的话，恢复瞬间会有一次流量冲击，很容易二次熔断。

```bash
LLM_PRIMARY_ENABLED=false
LLM_FALLBACK_MODEL=gpt-4.1-mini
LLM_CIRCUIT_OPEN_SECONDS=30
LLM_MAX_RETRY_BUDGET=3
```

把开关做成配置而不是代码分支，是这类事故里学到的最实用的一条。当时要关掉重试，得走一遍完整的发布流程，花了四十分钟。

## 五、几个具体的坑

**重试没有区分「流式」和「非流式」。** 流式请求吐出几百个 token 后才断，重试会让用户看到内容重来一遍。一条可用的规则是：首字节前可以重试，首字节后只做续写或直接标记中断。

**`Retry-After` 是全局的，不是给你的。** 上游返回 60 秒，不代表你等 60 秒就能成功，它限制的是所有调用方。这种情况等下去没有意义，直接降级。

**并发限流没用信号量。** 早期只做重试、没做客户端限流，高峰期自己的并发把上游打满，触发全局限流后所有请求一起失败。后来加了令牌桶，按上游 RPM 的 80% 发放，留 20% 余量给突发。

**降级路径没有测过。** 真正第一次触发降级往往是在事故现场，结果兜底答案库的索引早就过期，返回的内容驴唇不对马嘴。现在降级路径每周强制触发一次，用 5% 的流量走兜底，确保它一直是活的。没被跑过的代码等于不存在。

**日志里没记重试次数。** 出问题时只知道失败了，不知道失败前重试几次、每次延迟多少。现在每次重试都落一条，带 `attempt`、`delay_ms`、`status`，事后能画出重试分布。

这块没有多少智力含量，全是细节。但它的特点是：平时完全不可见，出问题时决定你是损失 1% 的请求还是 40%。一个简单的判断标准是——如果上游明天开始限流一半，服务会变成什么样。答不上来，就说明还没做完。
