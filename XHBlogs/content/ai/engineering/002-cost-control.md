账单第一次跳起来的时候，我们的日活只涨了 30%，费用涨了 4 倍。查了两天才发现，问题不在用户量，而在某次「优化」把历史消息从 6 条放宽到了 30 条，并且把模型从便宜的换成了贵的——两个改动都没走成本评估，因为当时没人知道一次调用到底花了多少钱。

这篇讲我后来建立的那套东西。

## 一、先让成本可见，否则一切优化都是猜

在动手优化之前，我做的第一件事是给每次调用打一条成本日志。字段不多，但必须齐：

```python
import time, uuid

def log_llm_call(resp, model, tier, feature, prompt_tokens, cached_tokens,
                 completion_tokens, latency_ms, est_cost_usd, trace_id, fallback=False):
    print({
        "event": "llm_call",
        "trace_id": trace_id,          # 贯穿一次用户请求
        "call_id": str(uuid.uuid4()),  # 单次模型调用
        "model": model,
        "tier": tier,                  # small / large / reasoning
        "feature": feature,            # 哪个功能花的钱
        "prompt_tokens": prompt_tokens,
        "cached_tokens": cached_tokens,
        "completion_tokens": completion_tokens,
        "latency_ms": latency_ms,
        "est_cost_usd": est_cost_usd,
        "fallback": fallback,
        "ts": int(time.time() * 1000),
    })
```

关键是三个维度：`feature`、`tier`、`cached_tokens`。

`feature` 决定了钱花在哪个功能上。没有它，你只能看到一条总额曲线，无法回答「是搜索摘要贵还是对话贵」。我们上线后第一周就发现，占比 6% 调用的「文档润色」功能吃了 38% 的成本，因为它每次塞整篇文档进去。

`cached_tokens` 是省钱的核心指标。主流厂商的上下文缓存都按「命中部分是原价的 10% 到 25%」计费，所以命中率直接决定单位成本。我按功能统计 `cached_tokens / prompt_tokens`，低于 50% 的就去看它的 prompt 结构。

`tier` 用来做分层价格，不同模型的单价差几十倍，混在一起算平均值没有任何意义。

成本估算不要手写单价散落在代码里。我把它收到一张表里，按百万 token 记：

| 用途 | 模型档位 | 输入价（每百万 token） | 输出价（每百万 token） | 典型占比 |
| --- | --- | --- | --- | --- |
| 意图识别、改写 | small | 0.1 美元 | 0.4 美元 | 55% |
| 常规问答 | medium | 0.5 美元 | 2 美元 | 35% |
| 复杂推理、长文 | large | 3 美元 | 15 美元 | 10% |

这张表每季度核对一次。厂商降价很频繁，不更新就会高估，导致你做出错误的取舍。

## 二、缓存命中率是可以设计出来的

很多人以为缓存是自动的，只要把 prompt 写长一点就会命中。不是。缓存以「前缀」为单位匹配，前缀里任何一个字节变了，后面全部失效。我踩过的三个具体坑：

第一，把时间戳放在 system prompt 末尾。当时的写法是「当前时间：2026-11-06 14:32:07」，本意是让模型知道今天几号。结果每秒钟前缀都不同，缓存命中率 0。改法是把这类易变信息挪到用户消息里，或者放一个粗粒度日期。

第二，检索到的文档按相似度分数排序。分数每次都略有不同，导致同样的文档顺序不同，前缀不匹配。改成按文档 id 排序，稳定了。

第三，把用户偏好拼在 system prompt 里。每个用户的偏好不同，等于每个用户一条独立缓存，命中率自然低。改成把偏好放到前缀之后，前缀只保留真正全局共享的部分。

调整之后的结构是这样的，从稳定到易变排列：

```
[全局指令]        ← 所有请求共享，命中率最高
[产品知识片段]    ← 按行业分组，组内共享
[用户偏好]        ← 单用户，命中率低但体积小
[本轮对话历史]    ← 每次都变
[本次用户输入]
```

做这个改造时，我把同一份约 4000 token 的全局指令在不同位置测了一遍：放在最前面，命中率 92%；中间插一段用户偏好，掉到 61%；再在后面拼时间戳，掉到 7%。位置的影响比大多数人想的大得多。

还有个必须注意的前提：缓存有最短长度要求（有的厂商是 1024 token，有的是 2048），低于这个长度不缓存。所以不是所有 prompt 都值得优化缓存——短 prompt 老老实实省钱的方式是缩短，不是提高命中率。

## 三、上下文裁剪：砍掉的是哪一段

最早我对历史消息做的是「保留最近 N 轮」。这很简单，但效果很差：用户第三轮说的「它」，指向的可能是一开始提到的那个文件，砍掉之后就丢了。

现在的做法是分层：

**保留区**永远是最近 2 轮原文，一字不改。对话的局部连贯性全靠它。

**摘要区**是 2 到 10 轮之前的内容，用一个小模型压成 150 字以内的要点，包含实体名、结论、未完成的事项。这里有个坑：摘要要做成增量更新，而不是每次重新摘要。我试过每次都把旧摘要和新的两轮一起送进去重压，成本反而比不裁剪更高，因为摘要的输入一直在涨。

**丢弃区**是 10 轮以前的内容，直接不送。但如果用户在前面上传过文件，要保留一个短句，比如「用户上传了 a.pdf（32 页，主题为报销流程）」，否则后面问「那个文件里第三章说什么」就直接失忆。

裁剪规则也要看场景。客服场景里「用户的订单号」必须常驻，哪怕它在第 1 轮出现；写作场景里「最初的提纲」必须常驻。所以我在裁剪器里留了一个 `pin` 列表，由业务代码显式指定哪些片段不能被裁：

```python
def trim(history, keep_recent=2, pin=None):
    pin = pin or []
    recent = history[-keep_recent * 2:]
    older = [m for m in history[:-keep_recent * 2] if m["id"] in pin]
    middle = [m for m in history[:-keep_recent * 2] if m["id"] not in pin]
    return older + summarize(middle) + recent
```

实测在一个平均 11 轮的会话里，这套裁剪把输入 token 的中位数从 6800 降到 2900，回答质量的主观评分没有下降（同一批 40 条评测样本，好/中/差分布基本一致）。

## 四、分级路由：先别急着上大模型

分级路由的价值在于：大部分请求根本不需要大模型。

我的分法不是按用户等级，而是按任务的确定性。规则优先，规则处理不了再上模型：

1. 命中固定问答库的，直接返回，成本 0。
2. 意图明确且答案结构固定的（查状态、改设置），走小模型加严格 schema，失败就降级到模板。
3. 需要多步推理、需要理解长文档的，才走大模型。

判断「要不要升级」有两种方式。一种是前置分类器，用几十个 token 的小请求先判断复杂度，再决定路由。另一种是后置校验，先让小模型答，用一个规则或小模型打分，不达标再升级。

我两种都用过，结论是：**前置分类器只在流量大、任务同质的时候划算**。它的固定开销（每次多一次往返，哪怕只有 80 毫秒）在小流量下不划算，而且在任务混杂时准确率很差，我测过的一个版本把 23% 的复杂请求判成了简单。

后置校验更适合我们的场景，因为它只对「可能不够好」的样本付出代价。写法上要注意两件事：升级请求必须带上原来的问题和小模型的结果，让它「检查并改写」而不是「重新回答」，这样输出 token 少一半；以及必须设升级比例上限，超过 30% 就说明小模型根本不适合这个任务，该换的不是阈值而是路由策略。

分级路由最容易被忽略的成本是**维护成本**。每加一档就要维护一套 prompt、一套评测、一套降级逻辑。我们最后一共只保留了三档，再多就没人搞得清哪条路走哪个模型了。

## 五、把成本写进告警

日志有了，还得有人被叫醒。我设了四类告警，按灵敏度从高到低：

**单位成本**：每完成一次业务动作的平均成本。这个比总额敏感得多，总额会跟着流量涨，单位成本涨才是真问题。阈值设在基线 1.5 倍，连续两个 5 分钟窗口触发。

**单次异常调用**：单次请求 token 超过 5 万，或成本超过 0.2 美元，直接打日志并采样上报。这个抓到过一次死循环——工具调用失败后模型反复重试，一次会话烧了 40 万 token。

**缓存命中率**：按功能看，低于 50% 告警。它通常意味着有人改了 prompt 结构，而这个人往往不知道缓存的存在。

**升级率**：分级路由里升级到大模型的比例，超过 30% 告警。这个指标掉下来的时候没人注意，涨上去的时候账单已经翻倍了。

告警要带上下文，不能只说「成本超阈值」。我要求每条告警消息里必须有：触发的 feature、当前值、基线值、以及两条 trace_id。有 trace_id 才能点进去看具体是哪次调用，否则收到告警的人只能干瞪眼。

最后一件事，把成本放进发布流程。任何改动 prompt 的 PR，CI 里跑一遍那 40 条固定样本，输出「输入 token 变化 +18%、预估单次成本 +0.004 美元」。数字贴在 PR 里，评审的人就会问为什么。这比任何制度都管用——成本失控从来不是因为大家不在乎，而是因为改动的那一刻没人看得见价格。
