把 AI 审查接进 CI 之后，累计统计大约 180 条它给出的评论：有效的大约三成，噪音三成，剩下四成是「说得对但没用」——比如它提示某个函数「可以更简洁」。这篇想说的是这三成的规律，以及怎么让另外七成不占用人的时间。

## 它稳定能发现的

按常见分类，命中率最高的是这四类，顺序也大致是可靠程度从高到低。

**一、控制流里的遗漏分支。** 空值、空集合、异常路径没处理，这类它几乎不miss。给一个 Python 函数，它能指出 `data.get("items")` 在没有 key 时返回 `None`，而下一行直接 `for item in ...` 会抛 `TypeError`。这种是纯静态推理，模型很擅长。

**二、资源与生命周期。** 打开的文件、数据库会话、锁，没在异常路径上释放。这个也稳。

**三、跨文件的不一致。** 改了函数签名没改调用方，加了必填参数没更新构造处。前提是你把相关文件一起给它。只给一个文件时它看不出来。

**四、命名与文案里的语义矛盾。** 函数叫 `is_valid` 却返回 `None` 而不是布尔；错误信息写「用户不存在」但实际分支是权限不足。这类问题人眼容易滑过去，模型对文字和语义的对应比较敏感。

这四类的共同点是：判断只需要局部上下文，且答案有客观标准。这是它能做到的边界。

## 它稳定漏掉的

**一、与运行时状态有关的问题。** 竞态、连接池耗尽、缓存和数据库不一致。它读不到「这个缓存有 5 分钟 TTL，而上游写入是异步的」这种事实，除非把上下文写进去。把部署拓扑、QPS、超时配置一起贴进去，命中率会上升，但成本已经接近人工写一份设计文档了。

**二、性能问题的量级判断。** 它知道 `O(n²)` 不好，但不知道这段循环的 n 在生产上只有 20，改不改都无所谓；反过来它也不会告诉你，某个看起来无害的 `in` 判断在一次请求里被调了 8000 次。

**三、业务语义的正确性。** 它不质疑需求本身。「满 300 减 50」和「每满 300 减 50」的区别，它按你代码里的写法解释，不会回头问你是不是搞错了规则。

**四、团队的历史包袱。** 为什么这个模块故意不用 ORM、为什么这个接口不能加缓存。这些只在人的脑子里。

所以不值得指望 AI 覆盖「这次改动对不对」这个总问题。它能覆盖的是「这段代码自身有没有明显的洞」。这两件事的验收标准完全不同。

## 一个真实的误报

印象最深的例子：它给一段缓存代码标了严重问题——「TOCTOU 竞态，检查后写入，中间可能被其他进程修改」。听起来很专业。

但那段代码跑在单进程的定时任务里，全局只有一把锁，整个任务串行执行。它没有读 `crontab` 配置，也没读启动入口，从代码片段推断出了一个不存在的并发场景。

问题不在于它错了，而在于这条评论的呈现方式：它标注「严重」，附了三行解释，看起来比正确的意见更可信。由此可以加一条规则——所有关于并发的意见，必须由人确认是否存在并发，否则默认降级为「待确认」，不进阻塞列表。这类「技术上成立但前提不成立」的意见，是噪音的主要来源。

## 把结论落成 checklist

AI 审查的价值不在于评论本身，而在于把反复出现的意见固化成规则。常见的做法是定期把有效意见归类，合并进仓库里的 `docs/review-checklist.md`，然后在 prompt 里直接引用。

```markdown
## 必须阻塞（人审也要过一遍）
- [ ] 新增的外部调用是否有超时与重试上限
- [ ] 数据库写操作是否在事务内，异常时是否回滚
- [ ] 是否修改了已有函数的签名？调用方是否全部更新（grep 函数名确认）
- [ ] 新增的配置项是否有默认值，且默认值在缺省配置下可用
- [ ] 分页/批量接口是否有上限，能否被单次请求拉全表

## 需要说明（评论里回复即可，不阻塞）
- [ ] 为什么这里绕过 ORM / 直接拼 SQL
- [ ] 这个缓存的失效策略与 TTL 依据
```

配合 CI 里的调用，实际命令长这样：

```bash
git diff --unified=0 origin/main...HEAD \
  | head -c 60000 > /tmp/pr.diff

claude -p "$(cat docs/review-checklist.md)

按上面的 checklist 审查下面的 diff。
只输出命中项：文件:行号 | 类别 | 一句话结论 | 依据。
没有命中就不要输出任何内容。不要评价风格，不要提改进建议。" \
  --append-system-prompt "你是审查工具，不是助手。" \
  < /tmp/pr.diff
```

三个细节值得说。`--unified=0` 让 diff 只带改动行，同样 token 预算能多覆盖两倍代码。`head -c 60000` 是硬截断，避免大 PR 把上下文塞满导致它开始编造行号。最后那句「没有命中就不要输出任何内容」很关键——不写这句，它一定会凑几条出来，而这里需要的正是「这次干净」这个信号本身可信。

## 人的部分不能省

一种合理的分工是：AI 跑第一遍，机器能查的（lint、类型、单测覆盖）交给工具，人只看三件事——这次改动是否符合需求、有没有业务语义错误、有没有标了「待确认」的项需要裁决。

一个反直觉的观察：AI 审查能把 review 时间从平均 25 分钟降到 12 分钟，但很难再降到 5 分钟。省下的是找低级问题的时间，那些时间原本就被打断得很碎。真正需要连续思考的部分没变。

还有一点，别让它同时做审查和修复。「审查并直接改好」的结果通常是：它把一条误报按自己的理解改掉了，改动本身引入了新问题。审查输出必须是文本，修复是另一次独立的、有测试的改动。

## 让它输出可被拒绝的东西

有一个很隐蔽的坑：早期 prompt 里写「请指出潜在问题」，它几乎每次都会给出五条。这五条不是因为它真发现了五个问题，而是因为「潜在」这个词几乎不可能被证伪——任何事情都有潜在问题，加个超时、加个日志、多一层校验，永远说得通。

后来把输出结构改成了强制的三段，逼它表态：

```text
对每个问题只输出一行，格式固定：
[阻塞|建议|待确认] 文件:行号 | 问题 | 依据（引用具体代码片段，不超过 10 字）

规则：
- 依据无法引用到具体代码的，标「待确认」。
- 「可以更简洁」「建议加注释」「考虑提取函数」一律不输出。
- 如果没有任何阻塞项，只输出一个词：CLEAN
```

`依据` 这一列是关键。它必须引用实际存在的代码片段，而引用一个不存在的东西比编一句评价难得多。加上这条之后，平均输出从 5 条掉到 1.8 条，有效比例反而升了。`CLEAN` 那个兜底也很重要——有了它，模型才被允许什么都不说，否则它永远倾向于凑数。

一种可行的处理是：阻塞项必须当天有人回复，建议项进 backlog 但可以烂着，待确认项每周批量过一遍。三类分开之后，噪音不再消耗注意力，因为不必逐条读，而是按类扫。
