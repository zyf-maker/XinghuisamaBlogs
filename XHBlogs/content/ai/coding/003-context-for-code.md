同一个 bug 有两种给法，效果差别很大。一种是把报错栈涉及的文件全贴进去，假设有 9 个文件、约 4200 行；另一种是只给 3 个文件的接口签名加一处实现，约 180 行。后者定位准确，前者往往给出一段看似合理的猜测——它把注意力放在了错误的地方，因为那 4200 行里有 4000 行与问题无关。

## 先定位，再裁剪

合理的流程是先让它自己找，而不是手工挑。这一步用检索，不用阅读：

```bash
# 按符号找定义与引用，比全文搜索精准
rg -n "def refund|class RefundService|refund\(" --type py -g '!tests/' | head -40

# 找这条报错文案的出处
rg -n "exceeds refundable" --type py

# 看最近改过这些文件的提交
git log --oneline -10 -- billing/refund.py
```

拿到候选之后，通常只保留三种文件：报错栈直接涉及的、被调用方按接口依赖的、承载配置或常量的。其余一律不给。理由很简单，模型没有「忽略无关内容」的能力，只有「从给定内容里找最相关的」的能力，无关内容多了它会选错。

一个典型的失败案例：前端白屏时把整个 `src/pages` 目录贴进去，它的结论是「可能是渲染错误，建议加 ErrorBoundary」。真正原因是一个后端字段从 `null` 改成了 `[]`，而列表组件对 `[]` 走了空态分支。那个字段的契约写在另一个模块的 `types.ts` 里，却没有给。**缺的那一个类型定义，比多给的三十个组件重要。**

## 接口签名优先于实现

这一条最值得坚持。给模型看函数签名、类型定义、docstring、错误码，通常比看函数体有用得多。

原因在于实现会误导。一段 200 行的函数里有大量防御性代码、日志、历史兼容分支，模型很容易把某个历史补丁当成设计意图，然后照着它的形状写新代码。签名不含这些噪音，只表达契约。

所以更省事的做法是用工具先生成签名视图，再贴进去：

```bash
# Python：只抽顶层定义与签名，丢掉函数体
python - <<'PY' > /tmp/api.txt
import ast, pathlib
for p in pathlib.Path("billing").rglob("*.py"):
    tree = ast.parse(p.read_text(encoding="utf-8"))
    for node in tree.body:
        if isinstance(node, (ast.FunctionDef, ast.ClassDef)):
            print(f"# {p}")
            print(ast.unparse(node).split("\n")[0] + " ...")
PY
wc -l /tmp/api.txt
```

同样的思路在 TypeScript 上更省事，`tsc --declaration --emitDeclarationOnly` 出来的 `.d.ts` 就是天然的签名视图，比源码短一个数量级，还不会丢类型。

经验比例是：签名占上下文的三分之二，实现占三分之一，而且实现只放「这次要改的那一个函数」和「一个同类的参考实现」。参考实现很重要，它决定了输出风格——不给参考，模型会用它自己的习惯写，跟周围代码格不入。

## AGENTS.md 该写什么

`AGENTS.md` 最好控制在 60 行以内。超过这个长度，后面的内容基本不会被遵守——这一点和人类读文档的衰减曲线差不多。

这类文件通常只需要四类内容：

```markdown
# 项目约定

## 命令
- 测试：`pnpm test -- --run`（不要用 watch 模式，会挂住）
- 单文件：`pnpm vitest run src/billing/refund.test.ts`
- 类型检查：`pnpm tsc --noEmit`（CI 用的就是这条，本地必须一致）

## 硬约束
- 不要新增 runtime 依赖，需要工具函数先看 `src/lib/` 是否已有
- 所有金额用整数分表示，禁止浮点。类型 `Cents = number & { __brand: 'cents' }`
- 日期一律传 ISO 8601 UTC 字符串，不要传 Date 对象过 API 边界

## 目录职责
- `src/domain/` 纯逻辑，不 import React，不碰网络
- `src/api/` 只做协议转换，不含业务判断
- `src/pages/` 只编排，不写计算

## 已知的坑
- `pnpm build` 在 Node 20.11 以下会报 `ERR_UNSUPPORTED_DIR_IMPORT`，用 20.11+
- 测试里的时间统一注入 `clock`，不要用 `Date.now()`
```

通常可以删掉的内容是：技术栈介绍（它读 package.json 就知道）、代码风格（交给 lint，写进文档只会让它反复确认）、架构长文（没人读完，模型也不读完）。

一个常见的坑：在 AGENTS.md 里写「优先使用函数式写法」。结果模型在纯计算的领域层里也去掉了所有 for 循环，写成了一串 reduce，可读性反而下降。规则太抽象就没法执行。改成具体的就好得多：「领域层的集合变换用 `map`/`filter`，累计用 for 循环，不要为了链式而链式」。规则要能对应到一段具体代码的形状。

## 一张表：给什么，不给什么

| 内容 | 给不给 | 理由 |
| --- | --- | --- |
| 函数签名 / `.d.ts` | 给 | 契约清晰，token 便宜 |
| 类型定义、枚举、错误码 | 给 | 决定了合法取值的边界 |
| 报错栈原文 | 给，别压缩 | 行号和调用链是唯一的定位线索 |
| 要改的那个函数体 | 给 | 风格参考与现有分支逻辑 |
| 同类的一个参考实现 | 给 | 控制输出风格 |
| 整个目录 | 不给 | 无关内容会挤掉关键内容 |
| lock 文件、生成代码 | 不给 | 无信息量，极耗 token |
| 完整 git 历史 | 不给 | 用 `git log --oneline -10 -- <file>` 代替 |
| 团队口头约定 | 写进 AGENTS.md 再给 | 不写就等于不存在 |

## 关于「一次性塞满」的错觉

现代模型动辄几十万上下文，很容易产生「都放得下」的错觉。放得下和读得到是两件事。有对照实验能说明：同一个任务，上下文 8K 和 90K，前者正确率更高，而且高得不是一点。90K 那次的输出里出现了一个不存在的配置项名——它把两个文件里的相似字段混在了一起。

判断标准可以概括为一句话：**只给它完成任务必需的最小集合，加上一份稳定的项目约定。** 必需集合的判断方式是问自己「如果只能给三个文件，是哪三个」。答不出来说明问题还没搞清，这时候该先读代码，而不是先问模型。

## 大文件怎么切

一个 2000 行的模块，全给会稀释，切错地方又会让它看不见关系。合理的切法是按「一个可命名的职责」切，不按行数切。

比如一个 `order_service.py`，通常切成三块给它：入口函数（`create_order`）连同它的分支、它调用的领域函数签名、以及状态机定义。中间那些序列化、日志、鉴权装饰器，只留一行占位注释 `# ... 略 ...`。

这个占位注释不是偷懒，是必需的信息。完全删掉会让模型以为那里什么都没有，然后建议「在这里加校验」；留着占位它才知道有东西被省略了。不写占位的典型结果，是它建议在已经有一层校验的位置再加一层，因为那一层被省略掉了。

切完之后应当做一次自检：把切好的片段单独发给它，问「这段代码要正确运行还依赖什么，你无法从这段判断的部分是什么」。它的回答通常能暴露漏掉的东西。这个自检三十秒，比事后追一个错答案便宜。

还有一个细节：贴代码时保留文件路径和行号，用 `# lib/billing/refund.py:88-140` 这种注释开头。它引用位置时会准确一些，核对时也能直接跳过去。不带路径的话，它给的「第 120 行」经常对应到另一个文件。
