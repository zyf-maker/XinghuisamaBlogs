比较稳妥的顺序是：需求 → 验收标准（能跑的测试）→ 让 AI 写实现 → 跑测试 → 人读 diff。这个顺序是踩坑换来的。最早的做法是「描述需求 → 让它一次写完 → 跑起来看看」，结果确实能跑，但改第二版的时候整个文件被重写了一遍，原来处理边界的分支悄悄没了，而那部分没有测试覆盖。

## 验收标准先于实现

先写测试、不写实现，是这套流程里最关键的一步。测试就是验收标准，而且必须是可执行的那种，不是「应该正确处理退款」这种句子。

```python
# tests/test_refund.py
import pytest
from billing.refund import refund

def test_partial_refund_keeps_order_open():
    order = {"id": "o_1", "amount": 10000, "status": "paid", "refunded": 0}
    result = refund(order, amount=9900, reason="damaged")
    assert result["refunded"] == 9900
    assert result["status"] == "paid"        # 部分退款不改订单状态

def test_refund_exceeding_amount_raises():
    order = {"id": "o_2", "amount": 10000, "status": "paid", "refunded": 9900}
    with pytest.raises(ValueError, match="exceeds refundable"):
        refund(order, amount=200, reason="damaged")
```

写这两个用例大约十分钟，但它把三件事固定下来了：数值边界（9900 加 200 超过 10000）、状态机的语义（部分退款不改 status）、异常文案（后面有调用方靠字符串匹配做告警，改文案会静默失效）。AI 拿到这组测试之后写出来的实现，第一次就过了。

反例也很典型：只给一句「实现退款功能，注意边界」。它给了一个默认全额退款的实现，status 直接置成 refunded，也没做累加校验。跑起来不报错，测试更没有，只能靠肉眼发现——这就是问题所在。

## 一次只改一个可验证的单元

控制 diff 规模是最有效的约束之一。经验值是单次改动不超过 150 行 diff、不超过 3 个文件。超过这个量，出错率明显上升，而且错的地方往往集中在它「顺手」改的部分。

具体做法是在指令里把范围写死：

```text
只修改 billing/refund.py 里的 refund() 函数。
不要动 billing/models.py，不要新增第三方依赖。
需要辅助函数就写在 refund.py 内部，以 _ 开头。
改完先跑 pytest -q tests/test_refund.py，再输出 git diff --stat。
```

最后一句很重要。让模型自己报 diff 规模，很容易看出它有没有越界。有一种典型情况：它回复「只调整了一个函数」，`git diff --stat` 显示 `6 files changed, 412 insertions(+), 89 deletions(-)`——它顺手把整个 billing 模块的命名风格统一了。功能没错，但这次改动没法合，因为它混进了一个无关的重构，出问题时无法二分定位。

## 每一步都跑测试

一个常见的循环固定为四条命令：

```bash
pytest -x -q tests/test_refund.py      # 先只跑相关用例，第一个失败就停
ruff check billing/ && mypy billing/   # 静态检查，类型错误在运行前就暴露
pytest -q                              # 全量回归
git diff --stat                        # 看改动范围
```

`-x` 不能省。不加它的话，模型一次改坏三个地方，你会在四十行失败输出里找不到根因，把整段贴回给模型它也读不完。`-q` 是为了让输出短一点，方便原样贴回去。

全量回归也不能省。有一种情况很容易漏：局部测试全绿，全量跑出 `TypeError: refund() got an unexpected keyword argument 'reason'`。原因是另一个调用点在 `api/orders.py` 里，模型改了函数签名没改调用方。这类问题局部测试永远发现不了，而它在生产上就是一次 500。

## 何时该由人动手

有几类活不适合交给 AI：

1. 涉及钱的数值逻辑。不是不信任，是验证成本高于自己写。退款分摊、税费计算这种，人工写完让它审查更划算。
2. 数据库迁移。它会给你一条看起来对的 `ALTER TABLE`，但不会提醒你这条语句在千万行表上要锁多久。
3. 并发与锁。它写的加锁代码经常在语法上成立、在时序上不成立，比如先查后改不加事务。
4. 你本来就知道怎么写、三分钟能写完的。来回描述需求花的时间比写代码长。

适合交出去的则是：模板化的 CRUD、测试用例补全、类型标注、日志埋点、把一段脚本翻译成另一种语言、读陌生模块并整理调用关系。

判断标准其实很简单：这件事的验证成本低不低。验证便宜就交给它，验证昂贵就自己来。

还有一个经常被忽略的维度：这件事出错的代价是不是可逆的。写错一个内部工具的导出格式，改回来五分钟；写错一条删除用户的语句，代价是数据没了。所以同样是「验证成本低」的活，还要先看它碰不碰不可逆的操作。删文件、改 schema、发消息、扣款，这四类宁可人工写三十行，也不让它自由发挥。

## 把需求写成它能执行的形式

效果差异最大的往往不是模型选择，而是需求描述的粒度。同一件事，两种写法：

> 不好：给用户列表加一个筛选，支持按状态和时间范围过滤。

> 好：`GET /api/users` 增加两个可选 query 参数：`status`（枚举 active/suspended/deleted，多值用逗号分隔）、`created_after`（ISO 8601 日期，含当天）。不传则不过滤。非法枚举值返回 400，body 为 `{"error":"invalid status"}`。已有测试 `tests/test_users_list.py` 不许改。

第二种写法的关键不在于长，而在于每一条都能被验证：参数名、类型、边界、错误响应、以及「哪些不许动」。一个可用的检查清单是五项——输入是什么、输出是什么、边界在哪里、错误怎么表现、哪些不许改。五项里缺一项，它就有一次自由发挥的机会，而自由发挥的地方通常正是最不需要创意的地方。

这套流程跑顺之后，每天的有效改动大概是八到十个小步。听起来碎，但回滚成本接近于零，而且每一步都能说清它为什么是对的。

## 常见问题

最疼的一类问题是让它「优化查询性能」。它把一次 N+1 查询改成了 join，又加了 `.distinct()`。测试全过，因为测试数据里没有重复行。上线后订单列表少了一半——join 到明细表之后一对多把行数放大了，`distinct` 又把本该保留的不同明细行合并了。全程没有报错，数据静默变少，是对账脚本第二天早上才发现的。

从那之后，这类改动需要一条硬规则：涉及聚合的 SQL 改动，必须先用生产数据采样在影子库里跑一次 `count(*)` 对比，再谈性能。听起来很重，但比事后修数据轻得多。

另一类坑是「测试通过但没测到」。AI 补出来的测试里出现过这种：

```python
def test_refund():
    assert refund(order, amount=100) is not None
```

它测的是函数不返回 None，这行断言永远为真，等于没测。所以验收标准里应当明确写两条禁令：禁止只断言 `is not None`；禁止 mock 掉被测函数自身。

还有一个小习惯，成本很低但很有用：让它在每次改动后回答一句「这次改动可能破坏什么」。它给的答案经常不准，但偶尔会点出没预料到的调用方，比让它自我表扬有用。
