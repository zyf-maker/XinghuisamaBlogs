让 AI 写测试，最容易出的结果是：测试全绿，覆盖率 87%，然后线上出了一个它完全没覆盖的 bug。原因不复杂——它写测试的时候读的是实现，写出来的断言自然就是「实现做了什么」，而不是「需求要求什么」。这两者在有 bug 的时候恰好一致，所以永远测不出来。

应对办法只有一条：**断言由人先写，实现由它补。**

## 先固定断言

具体做法是，人只写测试函数名、输入和 `assert`，中间的调用留空或者写个 `NotImplementedError`，然后让它补。

```python
import pytest
from pricing.coupon import apply_coupon

def test_threshold_discount_applies_once_per_order():
    # 满 300 减 50，不叠加
    assert apply_coupon(30000, ["C50"]) == 25000

def test_below_threshold_no_discount():
    assert apply_coupon(29999, ["C50"]) == 29999

def test_unknown_coupon_raises_not_silently_ignored():
    with pytest.raises(KeyError, match="C99"):
        apply_coupon(30000, ["C99"])

def test_two_coupons_of_same_type_not_stacked():
    assert apply_coupon(60000, ["C50", "C50"]) == 55000
```

四个断言里，第二个和第四个来自两个真实事故。第二个事故是浮点数比较：`299.99` 元存成了浮点，减完变成 `249.99000000000001`；第四个是叠加 bug，用户领两张券可以叠加使用。这两条如果让它自己写，几乎不会被想到，因为它们「不符合实现的形状」。

写断言这个动作，本质是人替它定义什么叫正确。这件事不能外包。

## 补实现，也补边界

断言确定之后，让它做两件事：把被测代码补出来，然后指出这些断言还缺哪些边界。

第二个指令要用得克制。通常这样写：

```text
上面四个测试是验收标准，不要修改断言。
1) 补齐 pricing/coupon.py 的实现，使这些测试通过。
2) 列出这组测试没有覆盖的等价类，按「输入类别 → 未覆盖取值」两列输出，
   不要写测试代码，由人决定补哪些。
```

第 2 步只让它列，不让它写，是因为它会倾向于给每个分支都补一个用例，包括那些实现上根本走不到的防御分支，最后产出一堆低价值测试。让它列清单、由人来挑，命中率高得多。

它给出的清单里通常有一两列是真正有用的。比如上面那组，它指出了「币种非人民币」「券过期」「订单已取消」三个等价类——这三个确实容易被漏掉，尤其过期那条，实现里压根没有时间参数。

## 表格驱动，一次覆盖分支矩阵

分支一多，一个个写测试函数就变成体力活，而且容易漏。表格驱动是常见的默认选择，也让 AI 的输出更好审。

```python
import pytest

@pytest.mark.parametrize(
    "amount, coupons, expected, case",
    [
        (30000, ["C50"],        25000, "恰好达阈值"),
        (29999, ["C50"],        29999, "差 1 分不触发"),
        (30000, [],             30000, "无券"),
        (60000, ["C50", "C50"], 55000, "同类券不叠加"),
        (60000, ["C50", "C30"], 52000, "异类券可叠加"),
        (0,     ["C50"],            0, "零金额"),
        (-100,  ["C50"],       -100, "负数不报错但也不打折"),
    ],
)
def test_apply_coupon_matrix(amount, coupons, expected, case):
    assert apply_coupon(amount, coupons) == expected, case
```

`case` 参数不是装饰。断言失败时 pytest 只打印参数元组，七行数字里哪个失败要靠数位置；带上中文标签，输出直接是 `AssertionError: 负数不报错但也不打折`。这个习惯来自一次两小时的排查——那次失败的是第五条，数错了行。

用表格的另一个好处是，可以直接把这张表给它，说「补到 12 行，覆盖漏掉的组合，用同样的格式」。它补的行很容易审，因为格式统一；如果是散落的测试函数，审起来要读代码逻辑。

## 「测了个寂寞」的识别

这类测试并不少见。它们不报错、不超时、覆盖率贡献很高，但删掉也不影响任何结论。常见的五种：

```python
# 1. 断言永远为真
assert result is not None

# 2. 断言的是自己构造的 mock
mock_db.get.return_value = order
assert mock_db.get.return_value == order

# 3. 只测了 mock 被调用，没测结果
mock_send.assert_called_once()   # 但没断言发的内容对不对

# 4. 捕获异常但不加断言
try:
    refund(order, 999999)
except Exception:
    pass                          # 这条测试在什么情况下都能过

# 5. 用实现里的常量做期望值
assert tax(order) == order["amount"] * TAX_RATE   # TAX_RATE 就是实现用的那个
```

第五条最隐蔽。它看起来是精确断言，实际上是把实现抄了一遍，实现改错它也一起改错。正确写法是硬编码一个人工算过的数：`assert tax(10000) == 600`，然后在注释里写清 6% 的来历。

清理办法是定期跑一次变异测试，成本不高，收益很直接：

```bash
pip install mutmut
mutmut run --paths-to-mutate billing/pricing.py --tests-dir tests/
mutmut results
```

它把实现里的 `>=` 改成 `>`、把常量改小，然后跑测试。测试还绿，说明那个变异点没被覆盖。一轮下来常见的结果是 64 个变异体、存活 21 个，存活的全集中在金额边界和两张券叠加的分支上——而这两处恰好是上面手写断言保住的。这说明一件事：手写断言的地方，测试是有效的；让 AI 自己生成实现加测试的地方，覆盖是虚的。

## 一点操作习惯

测试文件最好不要和实现放在同一次提交里。分两次提交，第一次是测试（此时应该是红的），第二次是实现（转绿）。这样 review 的人能先看「要验什么」，再看「怎么做的」，顺序反了就会被实现带着走。这条在 AI 参与的改动里尤其重要，因为实现是它写的，很容易连验收标准一起被它重新定义。

还有，`pytest --lf`（只跑上次失败的）在这种流程里用处比想象中大。改一版实现，先跑失败的那几个，几十秒内知道方向对不对，再跑全量。

## 让测试先红一次

有一个不算严格但很值得坚持的习惯：拿到 AI 写的实现和测试之后，先故意把实现改坏一行，看测试会不会红。

改法是随机的，比如把 `if amount >= threshold` 改成 `> `，或者把 `assert refunded <= amount` 里的 `<=` 改成 `<`。跑一遍，如果还是全绿，说明这个分支没有测试在守。这一步三十秒，比做覆盖率报告直接得多——覆盖率说明的是「这行执行过」，变异测试说明的是「这行的错误会被发现」。

在四个模块上做这个动作，19 个变异点里存活 5 个是常见的结果。存活点集中在两个地方：一个是「两个券金额相等时的排序」，另一个是「金额为 0 的短路返回」。这两处都不是复杂逻辑，纯粹是没人想到要为它们写用例。补上之后，这批代码才敢合。

## 别让它改测试

这是最硬的一条规则：**AI 可以改实现，不可以改测试**，除非指令里明确允许。

原因很简单，模型在「让测试通过」这个目标下，最优解经常是改断言而不是改代码。它不会恶意这么做，只是那确实更快。典型的情况有两种：悄悄放宽了一个 `assert`，或者把 `approx` 的相对误差从 `1e-6` 改成 `1e-2`——后者在金额场景下等于不校验。

所以指令里应当固定带一句：`tests/ 目录只读，如果某个断言无法满足，停下来报告，不要改测试。` 这句话之后，它的行为变成了「报告冲突」，正是想要的效果。

顺带说一个挂在 CI 上的廉价防线：

```bash
# 如果 diff 动了测试文件，要求 PR 描述里说明原因
git diff --name-only origin/main...HEAD | grep -q '^tests/' \
  && echo "::warning::本次改动包含测试文件，请确认是新增用例而非放宽断言"
```

它不阻塞，只是提醒。但有了这条提醒，review 时应当先看测试 diff 再看实现 diff——顺序对了，很多问题一眼就能看出来。
