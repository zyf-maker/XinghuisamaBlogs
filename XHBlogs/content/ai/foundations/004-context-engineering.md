模型能力上来之后，很多失败案例的根因不是模型不行，是给它的材料有问题：关键信息埋在三万字中间、检索回来的片段互相矛盾、上一轮的中间结果没人清理。上下文工程（context engineering）处理的就是这一类问题。

## 窗口不是仓库，是寄存器

把上下文窗口当成寄存器而不是仓库，是我这几年最有用的一个类比。寄存器有几个特点：容量固定、读写代价随位置变化、内容一旦被覆盖就没了。

窗口里放的东西都在竞争同一份注意力预算。多加一段背景，就少一段示例；多塞一轮历史，就少一份检索文档。这不是「反正放得下」的问题——放得下不等于读得到。

有一个反复被验证的现象叫「中间遗忘」（lost in the middle）：放在上下文首尾的信息，被正确使用的概率明显高于放在中间的信息。我做文档问答时对比过，把关键段落从第 3 位挪到第 30 位，答案准确率掉了十几个点，其他条件完全不变。

所以排序不是审美问题，是性能问题。

## 该放什么，放在哪

我的默认排列是这样的：

```text
[1] 角色与硬约束（不常变）
[2] 输出格式定义 / schema
[3] 任务指令（本轮要做什么）
[4] 关键输入（要处理的正文、代码、数据）
[5] 参考材料（检索片段、示例、历史决策）
[6] 收尾复述：再强调一次格式与验收标准
```

两个要点。

一是「关键输入」要靠近指令，不要让它在中间被稀释。如果输入很长，就先把它切开，一次处理一段。

二是首尾各放一次约束。开头那次定基调，结尾那次防止长上下文把开头的指令冲淡。这条在长文档任务里效果尤其明显——结尾重复一遍「只输出 JSON，不要解释」，格式错误率能降下来。

## 压缩是必需品，不是优化

上下文里最没价值的部分通常有三类：工具返回的原始 JSON、上一轮的完整推理过程、重复的背景说明。

我的裁剪规则很粗暴但有效：

- 工具返回只保留提取后的字段，不留原始结构。一个查询接口返回 8KB JSON，真正用到的可能就三个字段。
- 历史轮次超过 N 轮后，把前面几轮压成一句结论，保留决策和已确认的事实，丢掉过程。
- 检索片段按分数截断，低于阈值的直接不进上下文，宁可少给也不给噪音。

压缩必然会丢信息，所以要能回答一个问题：丢了这段，模型还做得出这个判断吗？如果答不上来，说明这段该留着。

有一种情况我吃过亏：把报错日志「压缩」成一句「构建失败」，结果模型给出的修复建议全是猜的。错误信息的价值恰恰在于那些看起来啰嗦的堆栈行。压缩要保住异常类型、出错位置、关键参数，其余可以砍。

## 结构化比自然语言更省带宽

同样一份信息，用表格或 JSON 表达通常比散文省一半以上的 token，而且歧义更小。

比如约束条件，写成散文是「注意输出必须是合法的 JSON，不要有 markdown 代码围栏，字段名必须完全匹配，不确定的字段填空字符串」。改成清单：

```text
约束：
- 输出：合法 JSON，无代码围栏，无前后说明
- 字段名：严格匹配 schema
- 缺失值：空字符串 ""
- 数值：不带单位
```

读者（模型）扫描成本低得多。我的判断是，凡是能被枚举的东西都不要写成段落。段落适合表达意图和取舍，清单适合表达规则。

## 长上下文不等于能用长上下文

标称 200K 的窗口，实际能有效利用的部分远小于这个数。随着输入变长，模型对中段细节的召回会下降，对数字和专有名词的精确复制也更容易出错。

几个具体的边界条件：

一是精确复制。让模型从长文档里逐字抄一段，超过一定长度后错误率上升明显，尤其是数字、括号、变量名。需要精确复制时，我宁愿让它定位后由代码去取。

二是跨段推理。要求模型比较文档里相隔很远的两处说法，长上下文下经常只看到一处。

三是无关内容干扰。塞进去的「可能有用」的材料会稀释注意力，效果不比少给好。这是我最常见到的过度设计：怕漏信息，把整个知识库都塞进去。

## 状态该由代码管，不该由模型记

多轮任务里最容易崩的地方是状态。模型记不住二十轮前确认过的参数，但它会自信地重新编一个。

我的做法是把关键状态外置成一份显式的结构，每轮作为上下文的一部分重新注入：

```python
state = {
    "task": "extract_kinase_ic50",
    "confirmed": {"target": "EGFR", "unit": "nM"},
    "pending": ["assay_type"],
    "rejected": ["cell_line"],
}
```

每轮把这份 state 序列化后放进 prompt 的固定位置，模型只负责在结构化输出里返回更新。这样即使对话被压缩、被裁剪，事实也不会丢。代码是唯一可信的记忆，模型只是处理器。

代价是 prompt 变长了一点，但换来的是可复现和可调试——出问题时能直接看 state 在哪一步被改错。

## 一个验收习惯

我改完 prompt 之后不会只看一次输出。固定一组二十来条测试输入，每次都跑全量，比较结果差异。上下文工程的大部分改动——调顺序、换格式、加约束——效果都是局部的，单次抽样看不出来。

这套流程听起来笨，但它把「感觉好多了」变成了「这 20 条里 18 条稳定通过，剩下 2 条的问题是检索没召回」。上下文工程的收益，基本都来自这种可测量的迭代。
