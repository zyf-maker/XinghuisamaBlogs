同一个 prompt 连发两次，一次说「可以」，一次说「不建议」。这不是模型在犹豫，是采样（sampling）在起作用。理解温度（temperature）和 top_p 到底改了什么，比记住一组「推荐参数」有用得多。

## 解码是在一个分布上做选择

模型每一步输出的是词表上的一整个概率分布，不是某个确定的词。词表可能十几万项，模型给每一项算一个分数，再转成概率。

从这个分布里取下一个 token 的过程叫解码（decoding）。取法有两种极端：永远取概率最高的，叫贪心解码（greedy decoding）；按概率随机抽，就是采样。温度、top_p、top_k 都是在改变这个分布的形状或者截断它的尾巴。

关键点在于：这些参数只影响「怎么选」，不影响「模型认为什么更可能」。模型对「答案是 42」的置信度是它自己算的，采样参数改不了。

## 温度是给 logits 除以一个数

技术上温度做的事非常朴素：在 softmax 之前把 logits 除以温度 T。

```python
import numpy as np

def softmax(logits, T=1.0):
    # 表里推荐 T=0（贪心），但除零会直接炸；这里按极小值处理，
    # 数学上等价于取 argmax，也避免 logits 里出现相同最大值时的 nan
    T = max(float(T), 1e-8)
    z = np.asarray(logits, dtype=np.float64) / T
    z -= z.max()
    e = np.exp(z)
    return e / e.sum()
```

T 越小，分布越尖，高概率项被进一步放大；T 越大，分布越平，低概率项也有机会被抽到。T 趋近 0 就退化成了贪心。

由此可以推出两个常被忽略的结论。

第一，温度不改变排序。它只是拉伸或压缩差距，原本概率最高的项在任何温度下都是最高的。

第二，温度对「模型本身就很确定」的位置影响很小。如果某个位置最高概率已经是 0.99，把温度从 1.0 降到 0.3，输出基本不变。温度真正起作用的地方，是那些概率接近的候选之间——也就是模型本来就拿不准的位置。

## top_p 是截断尾巴，不是缩放

top_p（也叫 nucleus sampling）的做法是：把候选按概率从高到低排序，累加，只保留累计和刚超过 p 的那一小撮，其余全部置零后重新归一化。

```python
def top_p_filter(probs, p=0.9):
    order = np.argsort(probs)[::-1]
    sorted_p = probs[order]
    cum = np.cumsum(sorted_p)
    keep = order[: np.searchsorted(cum, p) + 1]
    out = np.zeros_like(probs)
    out[keep] = probs[keep]
    return out / out.sum()
```

它和温度的区别在于：温度是连续地重塑整个分布，top_p 是硬性砍掉长尾。长尾里那些千分之一概率的怪词，top_p 直接不给机会。

这里有个边界条件值得注意：p 设得很小（比如 0.1）时，保留集合可能只剩一两个 token，输出会变得极其重复。p 设成 1.0 等于不过滤，此时低概率的坏 token 仍有被抽中的可能，长文本里容易出现跑偏或者格式崩坏。

## 两个一起调是常见的错误

官方文档通常建议「温度或 top_p 改一个，不要同时改」。原因很实际：两个参数的作用会互相掩盖，出问题时你分不清是谁的责任。

温度调到 0.7 已经把分布压平了一些，再叠加 top_p=0.8 砍尾，实际效果是「中段变随机、尾巴被砍掉」，跟你凭直觉预期的组合并不一致。调参时至少保证一次只动一个变量。

我的默认组合是这样的：

| 场景 | temperature | top_p | 说明 |
| --- | --- | --- | --- |
| 结构化抽取、分类 | 0 | 1.0 | 要的是可复现 |
| 代码生成 | 0.2 | 0.95 | 允许一点措辞变化 |
| 技术问答 | 0.3 | 0.9 | 事实优先，语气可变 |
| 头脑风暴 | 0.9 | 0.95 | 要的就是发散 |
| 创意写作 | 1.0 | 1.0 | 更依赖提示词控制方向 |

这张表是长期跑下来收敛的结果，不是拍脑袋。我的做法是：新任务先按「结构化抽取」那行的保守参数跑通，确认格式和逻辑都对，再逐步往上调温度，看输出多样性有没有带来实际收益。很少需要调到 1.0 以上。

温度设 0 也不是绝对确定。浮点运算、批处理顺序、推理引擎的算子实现都可能带来微小差异，同一个请求在不同机器上偶尔还是会有不同输出。凡是需要严格复现的场合——比如回归测试——别指望温度 0，要做的是语义层面的断言。

## 设了固定参数还是会变

除了采样，还有几个来源会让输出漂移。

一是上下文本身不同。多轮对话里，哪怕只多了一句「好的」，后续每一步的输入分布都变了，采样路径自然分叉。

二是服务端的批次组成。同一个 prompt 和别的请求拼在一批里做前向计算，数值结果可能有极小差异，而这一点差异在概率接近的位置足以改变采样结果。

三是模型版本。同一个名字的模型，服务端更新权重后行为会变，而且通常不会提前通知。生产环境里我会把模型名和参数一起写进日志，出问题时有据可查。

## 重复惩罚和它的副作用

还有一个常被一起调的参数：重复惩罚（repetition penalty）。它的做法是在每生成一个 token 之后，把这个 token（或最近一段窗口内的 token）的 logit 压低，降低它再次出现的概率。

在长文本生成里它很有用——没有它，模型在温度偏低时容易陷入复读，反复输出同一句话。但它的副作用也明显：当任务本身要求重复时，惩罚会主动破坏正确输出。

我踩过的坑是表格抽取。表头 `A` `A` `B` 这类重复值是正常的，开了 1.2 的重复惩罚后，模型开始把第二个 `A` 改成 `C` 或者干脆跳过，理由是「不要重复」。解决办法是把惩罚降到 1.0 附近，只靠 prompt 里明确说明「允许重复，按原样输出」来约束。

频率惩罚（frequency penalty）和存在惩罚（presence penalty）是另一种思路：按 token 在已生成文本中出现的次数或是否出现来扣分。它们对「不要反复讲同一个论点」这类需求有效，但同样会干扰需要精确重复的任务，比如回填模板、复述原文。

我的判断是：这些惩罚项属于「治症状」的工具，能用 prompt 解决就不要用它们。真正避免复读的可靠办法是让每一步的输出都有明确的结构约束——有 schema 就不容易自由发挥，也就不容易复读。

## 一个实用的判断

采样参数的调整空间比很多人想象的小。真正决定输出质量的还是 prompt 里的约束和示例。我在做数据抽取时试过：温度从 0.7 降到 0，格式错误率降了一半；但把 schema 写进 prompt 并给两个示例之后，即使温度留在 0.3，错误率也降到了同一个水平。

所以我的顺序是：先把任务定义和格式约束写清楚，再考虑调参。参数是用来治「同一个正确答案有多种合理表述」的，不是用来治「模型不知道该输出什么」的。
