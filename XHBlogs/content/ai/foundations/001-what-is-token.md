第一次看到按 token 计价的账单，很容易以为它约等于字数。但同一段意思的中文和英文，价格差能到两倍，分词器（tokenizer）才是决定成本的那一层。这篇把 token 从切分到窗口预算的整条链路拆开讲，重点放在工程上真会用到的估算方法和几个坑。

## token 不是字，也不是词

语言模型（language model）的输入输出都是整数序列，token 就是这些整数的编号。文本进入模型之前先经过分词器切成 token，再查词表换成 id。模型本身并不知道「这句话有几个字」，它只看到一串整数。

不同厂商的切分方式不一样。同一句中文，在 A 家的分词器里是 12 个 token，在 B 家可能是 18 个。跨模型比较价格时如果只按字数折算，误差能到百分之五十。做一次小对比就能看到：把同一段 300 字的技术说明分别喂给几家的分词器，最长和最短的切分差了将近一倍。

## BPE 究竟在合并什么

主流分词器基本都基于字节对编码（byte pair encoding，BPE）。训练过程很朴素：先把文本拆成字节，统计相邻两个片段共同出现的频率，把最高频的一对合并成新片段，重复几万次。

结果是高频词会被合成一个 token，低频词被拆成几段。`the`、` of`、`tion` 这类片段几乎必然被合并；罕见的人名、化学式和变量名则会被切碎。写计算化学领域的 prompt 时，`DFT`、`B3LYP`、`GROMACS` 这些词经常被切成 2 到 4 个 token，比直觉要多。

有一个容易被忽略的细节：切分依赖上下文。`token` 单独出现是一个 token，放进 `tokenization` 里可能变成 `token` 加 `ization` 两段。所以「这个词占几个 token」没有绝对答案，得看它前后的字符。这也是为什么手工数字符来估算 token 常常出错。

## 中文为什么更费 token

英文的词之间有空格，BPE 天然有边界，高频词能稳定合并。中文没有空格，切分粒度完全由训练语料里的统计规律决定。多数主流分词器的语料以英文为主，中文片段的合并表相对稀疏。

实测经验值：中文大约 1 个汉字对应 0.7 到 1.2 个 token，视分词器而定；英文大约 4 个字符对应 1 个 token，也就是 0.75 个单词左右。同样的信息量，中文的 token 数往往是英文的 1.5 到 2 倍。这一点在按 token 计费的批处理任务里会直接体现在账上。

反过来说，如果你的应用面向中文用户，别拿英文文档里的「1 token ≈ 4 字符」去套，会低估三成以上。

## 上下文窗口不是一个数字

模型标称 128K，指的是 token 数，不是你还能贴进去多少字。窗口里同时装着系统提示、历史对话、检索到的文档、工具返回结果，以及留给模型自己的输出预算。

这里有两个坑。

第一，输入和输出共享窗口。要让模型输出 2000 token，就得在输入侧预留空间，否则请求会被截断，或者直接返回长度错误。

第二，计费按 token 算，延迟却按长度涨。上下文从 4K 涨到 64K，首 token 延迟（time to first token，TTFT）的上升往往不是线性的，翻几倍很常见。

常见的做法是给每次请求画一张预算表，写死在代码里：

| 部分 | 预算占比 |
| --- | --- |
| 系统提示与工具定义 | 10% |
| 历史对话 | 30% |
| 检索文档 | 40% |
| 输出预留 | 20% |

超出就裁剪，而不是指望模型「自己抓重点」。模型不会告诉你它看漏了哪一段。

## 用代码估，不要用感觉估

估算没那么玄，装个 `tiktoken` 就能对齐 OpenAI 系模型的分词：

```python
import tiktoken

enc = tiktoken.get_encoding("cl100k_base")
text = "分子动力学模拟的步长设置为 2 fs"
ids = enc.encode(text)
print(len(ids))
print([enc.decode([i]) for i in ids])
```

把 `cl100k_base` 换成 `o200k_base` 再跑一遍，同一句话的数字会变。这件事本身就说明了问题：token 数是分词器的属性，不是文本的属性。

结论是，不必追求精确到个位的估算。工程里用一个粗略系数加 20% 余量就够用。真正需要精确的地方只有两处：一是卡着窗口上限的长文档，二是按 token 计费的批量任务。

## 切分方式会改变结果，不只是改变账单

分词边界不只是钱的问题，它会实打实地影响模型表现。

最典型的是数字。一份财务报表里的 `1234567`，在很多分词器里被切成 `123` `456` `7` 三段，模型看到的是三个碎片，做加减法时容易出错。同理，如果把日期写成 `2026-11-05`，连字符可能被合并掉；改成 `2026 年 11 月 5 日` 反而更稳妥。

另一个是标识符。变量名 `getUserProfileById` 在代码模型的词表里通常有专门的片段，切分合理；但自己造的词比如 `calc_ic50_nM` 就会被切得很碎，模型容易在中途把下划线或大小写搞错。所以写 prompt 时，把关键标识符用反引号括起来并单独说明一次，比指望它自己拼对更可靠。

分子描述符抽取里也有类似情况：SMILES 字符串被切得极碎，模型复制时偶尔会漏掉一个括号。解决办法不是加大模型，而是让模型只输出「第几行」这样的定位信息，真正的字符串由代码去取。

还有一类是空格。BPE 常把前导空格并进 token，所以 `the` 和 ` the` 是两个不同的 id。这解释了为什么在拼接多段文本时，多加或少加一个空格偶尔会让输出风格发生细微变化。听起来很玄，但在做 A/B 对比时这是一个必须控制的变量。

## 一个反直觉的结论

短 prompt 里省 token 没什么意义。省下 30 个 token，折算成钱是小数点后好几位，但为此牺牲的清晰度会实打实地降低输出质量。

真正吃掉预算的是长上下文。把整篇论文塞进去问一个问题，成本可能是一次精炼提问的五十倍，而且答案不一定更好。所以优化方向不是「把话说短」，而是「别把不相关的东西塞进窗口」。这条判断会贯穿这个分类后面的几篇。
