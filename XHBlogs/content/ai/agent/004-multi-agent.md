在简历和架构图上，「多智能体协作」看起来比「一个大循环」高级。但把它当成默认选项的项目，多数会在第二个月开始付代价：调试成本翻倍，token 账单翻三倍，最终准确率却没比单智能体高。这篇文章想给出一条更冷的判断线——先算账，再拆。

## 一、拆分的真正理由只有一个

多智能体最常见的宣传理由是「分工」。但分工本身不创造价值，模型并不会因为被告知「你是检索专家」就真的更会检索。把同一个模型复制三份，配上不同的系统提示词，得到的不是三个专家，而是三次采样。

真正值得拆的理由只有一个：**上下文需要隔离**。

单智能体的上下文是一条单调增长的日志。做代码库分析时，读了二十个文件，上下文里塞满了源码；接下来要写结论，模型却要在这些源码中间找重点，注意力被稀释，早期读到但没写进摘要的内容也基本失效。这时候拆出一个只在子上下文里读文件的 agent，让它返回一份两千字的摘要，主 agent 的上下文就能保持干净。

除此之外的「理由」大多站不住。并行加速？如果任务之间真的独立，用并行函数调用就行，不需要多个 agent。角色扮演？系统提示词一个字符串能解决的事，不必开一个新进程。互相审查？同一个模型审查自己写的东西，倾向于确认而不是质疑，收益远小于让它在生成时多写一段自检。

## 二、三笔账

拆之前，我会把下面三项算一遍。任何一项算不过来，就不拆。

| 维度 | 单智能体 | 多智能体 | 差异来源 |
| --- | --- | --- | --- |
| token 成本 | 一条上下文线性增长 | 每个 agent 各自一份系统提示与工具定义 | 固定开销乘以 agent 数量 |
| 延迟 | 串行步数 | 可并行，但多了汇总轮次 | 并行收益 vs 协调开销 |
| 可观测性 | 一条完整轨迹 | 多条轨迹加一次交接 | 交接接口是新的故障点 |
| 失败模式 | 循环、跑偏 | 循环、跑偏、交接信息丢失、互相推责 | 后者更难复现 |

第二项经常被算反。多智能体确实能并行，但汇总那一步往往需要把各 agent 的输出再喂给一个协调者，协调者又可能要求补做，来回几轮之后，总延迟不一定低于串行。我在一个文档处理流水线上量过：拆成三个并行 agent 后，墙钟时间只降了两成，token 消耗涨了将近三倍。原因很朴素——每个 agent 都要重新读一遍公共背景。

第三项是隐性成本。单智能体的日志是一条线，出问题从头看到尾就行。多智能体的日志是一棵树，你得先判断问题出在哪个 agent，再看它拿到的输入是不是上游传歪了。这个定位过程花的时间，通常比写代码的时间长。

## 三、交接接口才是设计重点

如果决定拆，代码里最该花心思的不是每个 agent 的提示词，而是它们之间的接口。交接不能传自由文本，否则信息一定会在传递中损耗。

```python
from dataclasses import dataclass, field

@dataclass
class Handoff:
    task: str                     # 要做什么，一句话，含完成判据
    inputs: dict                  # 必需的结构化输入，键名固定
    constraints: list[str]        # 硬约束，例如「不得修改已存在的测试」
    budget: dict = field(default_factory=lambda: {"max_steps": 6, "max_tokens": 12000})
    done_when: str = ""           # 明确的完成条件，避免子 agent 无限探索

@dataclass
class Result:
    status: str                   # ok / partial / failed
    summary: str                  # 面向主 agent 的摘要，限 800 字
    artifacts: dict               # 结构化产出，例如文件路径、抽取的字段
    open_questions: list[str]     # 明确交回的不确定项
    steps_used: int
```

几个约束是刻意的。summary 限长，因为主 agent 要把它读进上下文，不设限等于把子上下文原样搬回来，隔离就白做了。status 必须三态，只给 ok 和 failed 会逼子 agent 在「差一点完成」时谎报成功。open_questions 让子 agent 有地方承认「这一点我没查到」，比让它硬编一个答案好得多。artifacts 走文件路径而不是内容，大块产物不该进上下文。

还有一个反向设计：主 agent 不应该拿到子 agent 的全部工具。子 agent 的能力边界要在创建时收窄，否则它会把本该交回主 agent 决策的事自己做了。

## 四、常见的失败模式

**信息在交接处蒸发**。主 agent 觉得自己说清楚了，子 agent 拿到的任务却是「分析一下这个项目」。对策是要求 task 里出现具体对象和完成判据，写不出来就说明这个任务还不该拆出去。

**互相等待**。A 等 B 的结论，B 又要 A 先给输入。单智能体不会死锁，多智能体一定会在某个边界条件下死锁。所以每个交接都要有超时和降级路径，超时后按 partial 处理，而不是无限等。

**责任扩散**。两个 agent 都以为对方会做校验，结果没人做。对策是给每个检查项指定唯一负责人，在交接结构里写成字段，而不是写在提示词里靠自觉。

**成本失控**。子 agent 递归创建子 agent，一层套一层。必须设硬性深度上限，并且子 agent 的预算要小于父 agent 剩余预算，否则一次请求能把月度配额烧掉。

## 五、我的判断

我现在的默认选择是单智能体加几个隔离的「工具型子调用」。所谓工具型，是指子调用只做一件事、只返回结构化摘要、不参与决策。比如「读这三十个文件并返回接口清单」可以拆，「判断这个重构方案是否可行」不拆。前者是上下文隔离，后者是决策，决策留在主循环里才能保持连贯。

只有当任务在时间上真正可以分段、每段的中间产物可以明确序列化、而且各段之间不需要频繁来回时，才值得上多个平级 agent。三个条件缺一个，我倾向不拆。

还有一个更实际的判断：如果团队里没人能在一张纸上画出多智能体的数据流和失败恢复路径，那就还不该上多智能体。架构的复杂度必须有人能完整持有，否则它只是在给未来的自己埋雷。拆分的门槛不该是「能不能做」，而是「拆完之后，我是否还看得懂它在干什么」。
