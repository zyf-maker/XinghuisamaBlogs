在 MCP 之前，每个宿主应用接每个外部系统都要写一遍适配代码。你有三个客户端、五个数据源，组合起来就是十五份实现，接口形状还各不相同。MCP（Model Context Protocol）要解决的就是这个乘法问题：把「提供服务的一侧」和「消费服务的一侧」用一套协议分开，各自只需实现一次。

## 一、协议骨架

MCP 基于 JSON-RPC 2.0，消息分三类：请求（带 id，要回响应）、响应（带同一个 id）、通知（无 id，不回复）。架构上是典型的客户端—服务器模型，但要注意谁是谁：宿主应用（host）内部为每个服务器建一个客户端（client），服务器（server）暴露能力。一个宿主可以同时连多个服务器，这是它能替代 N 份适配代码的原因。

服务器对外提供三种原语，边界很清楚：

| 原语 | 谁发起 | 用途 | 典型例子 |
| --- | --- | --- | --- |
| tools | 模型决定调用 | 有副作用或需要计算的操作 | 执行查询、发消息、写文件 |
| resources | 应用决定读取 | 只读的上下文数据 | 文件内容、数据库 schema |
| prompts | 用户主动选择 | 预置的提示词模板 | 代码审查模板、周报模板 |

这条边界值得强调。tools 是模型可以主动触发的，resources 是应用按需读取的，prompts 通常由用户从菜单里选。把只读数据做成 tool 也能跑，但会让模型每一轮都要判断「要不要读一下」，徒增不确定性和 token 消耗。

## 二、一次握手和一次调用

连接建立时先走初始化握手，双方交换协议版本和各自支持的能力，最后客户端发一条 notifications/initialized 通知，握手结束。能力协商是双向的：服务器声明自己支持 tools、resources、logging，客户端声明自己支持 sampling、roots。

一次工具调用在 JSON-RPC 层是这样：

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "query_pdb",
    "arguments": { "pdb_id": "1ABC", "format": "mmcif" }
  }
}
```

返回结果里，content 是一个数组，可以混排文本、图片和嵌入资源；另一个字段 isError 用来标记业务层失败。这里有个容易踩的坑：工具自身的逻辑错误应该用 isError: true 返回，而不是抛协议错误。协议错误（JSON-RPC error）表示方法不存在、参数结构非法这类通信层问题，客户端通常会直接终止该服务器；isError 则表示「调用成功了，但业务失败了」，结果会原样交给模型，让它自己决定下一步。

分不清这两个，就会出现「查询没找到记录，整个会话崩掉」这种事故。

## 三、传输方式怎么选

标准里定义了两种传输：标准输入输出（stdio）和可流式 HTTP（Streamable HTTP）。

stdio 适合本地进程。宿主启动一个子进程，通过 stdin 写、stdout 读，一行一条 JSON。好处是不需要端口、不需要鉴权、随宿主一起退出；坏处是日志必须写 stderr，任何一个库不小心往 stdout 打了一行调试信息，整条协议就废了。第一次接本地服务器时卡住半小时是常见的事故，原因往往就是某个依赖在 import 时打印了版本号。

HTTP 传输适合远程和共享场景。早期版本用的是 HTTP+SSE 双端点，后来收敛成单端点的 Streamable HTTP，客户端 POST 请求，服务器按需升级为 SSE 流。选型上的判断很简单：工具需要访问本机文件或本地服务，用 stdio；需要被多个用户或机器共享，用 HTTP。不要为了「统一」把本地工具也包成 HTTP，多出来的端口管理和鉴权成本换不来什么。

## 四、鉴权与权限

远程服务器走 HTTP 时，标准建议基于 OAuth 2.1 做授权，服务器用 401 加 WWW-Authenticate 引导客户端去授权服务器拿 token。实践里更常见的是静态 API key，简单但不适合多用户场景，因为 token 往往绑定了过大的权限。

稳妥的做法是双层的：协议层的凭证负责「这个客户端能不能连上这个服务器」，业务层的权限在工具内部再判一次「这个用户能不能读这条记录」。只在协议层做鉴权是不够的，因为模型可以组合多个工具，单次调用都合法，组合起来可能越权。

另外，采样（sampling）是个容易被忽视的反向能力：服务器可以请求客户端代为调用模型。这让服务器不必自己持有 API key，但也意味着服务器能把任意内容送进宿主的模型上下文。接入第三方服务器时，这一点要有意识地评估。

## 五、接入时的实际问题

**工具数量膨胀**。一个服务器暴露三十个工具，光定义就占掉大量上下文，模型的选择准确率也明显下降。可行的处理是在客户端侧做过滤，按当前任务只挂载相关工具，而不是把服务器声明的工具全量透传。

**超时与取消**。JSON-RPC 有 notifications/cancelled，但很多实现没接。长任务卡住时，客户端只能整体超时。自己写服务器时至少要把取消通知接上，否则用户点了停止，后端还在跑。

**结果体积**。MCP 的 content 数组不限制长度，一个查询返回几十兆是可能的。服务器侧应当分页，或者把大块数据放进 resource，让模型按需读取，而不是塞进 tool result。

**版本漂移**。协议在演进，字段名和语义改过几轮。接入前先确认服务器声明的协议版本，别假设它和你手上的 SDK 一致。SDK 的便利封装有时会掩盖协议细节，出问题时还是得看原始 JSON。

## 六、结论

MCP 真正的价值不在「又一个插件标准」，而在于它把工具的实现从应用里挪了出来。以前加一个数据源要改客户端代码、发版；现在只需要在配置里加一行服务器地址。对内部工具多的团队，这个解耦的收益很直接。

但它不解决工具设计的问题。协议只规定了怎么传，没规定传什么。一个描述含糊、参数宽泛的工具，用 MCP 接进来照样难用。常见不少团队把 REST 接口一比一映射成 MCP 工具，结果模型面对一堆 CRUD 方法无从下手。工具该按「任务」切，不该按「资源」切，这条跟协议无关。

对个人项目，如果只接一两个工具，直接写 function calling 更省事。MCP 的复杂度在需要多方复用、需要把工具和服务解耦的时候才划得来。先想清楚是不是真的有那个「乘法」，再决定要不要引入这一层。
