ReAct 这个词被用得很泛，有人指那篇 2022 年的论文，有人指某种提示词格式，市面上大部分「ReAct 模板」其实只是把三个标签拼进 prompt。真正的区别不在提示词，在于你是否把它当成一个有状态、有终止条件、可观测的执行循环来实现。

## 一、论文里的循环其实很短

ReAct 的核心主张是把推理轨迹（reasoning trace）和动作（action）交错生成。模型先写一段 Thought，再给出一个 Action，环境执行后返回 Observation，这三段拼回上下文，模型继续下一轮。原始论文在 HotpotQA 和多跳事实核查上演示的循环，通常三到五步就结束了。

关键在于它和两种做法的差别。纯 Chain-of-Thought 只推理不接触外部，遇到需要事实的地方只能靠参数记忆，容易一本正经地编。纯「工具调用」不写推理，模型倾向于一步到位地选工具，参数却经常选错。ReAct 把推理显式写出来，等于在选工具之前强迫模型先说明为什么，这一步对准确率的提升往往大于换模型。

## 二、一个手写的最小循环

不用任何框架，两百行以内能写清楚。下面是我常用的骨架：

```python
import json

MAX_STEPS = 8

def run(question: str, tools: dict, llm) -> str:
    scratchpad = ""
    for step in range(MAX_STEPS):
        prompt = build_prompt(question, scratchpad)   # 含工具说明与格式约束
        text = llm(prompt, stop=["Observation:"])     # 关键：在 Observation 处停

        if "Final Answer:" in text:
            return text.split("Final Answer:", 1)[1].strip()

        action, action_input = parse_action(text)     # 从 "Action:" 行解析
        if action not in tools:
            obs = f"错误：不存在名为 {action} 的工具，可用工具为 {list(tools)}"
        else:
            try:
                obs = tools[action](**action_input)
            except Exception as e:
                obs = f"工具执行失败：{type(e).__name__}: {e}"
            if len(str(obs)) > 2000:
                obs = str(obs)[:2000] + "……（结果已截断）"

        scratchpad += text + f"\nObservation: {obs}\n"

    return "达到最大步数仍未得出最终答案。已收集的信息：\n" + scratchpad
```

这段代码里有三个决定成败的地方，比提示词措辞重要得多。

**stop 序列**。让模型在生成到 "Observation:" 时就停下，否则它会自己编一段观察结果继续往下推。这是最常见的实现事故，模型编的 Observation 看起来完全合理，你甚至很难从日志里发现。

**工具不存在时不要抛异常**。把可用工具列表当作 Observation 返回，模型下一轮通常能自我纠正。抛异常则整轮结束。

**截断**。工具返回的原始内容经常是几万字符的网页或日志，直接塞进上下文，两三步就把窗口填满。截断时留一句说明，比静默裁掉更好，模型知道自己看到的是残缺信息。

## 三、循环什么时候停

终止条件至少要设四层，缺一层就会出现无限循环或者过早退出。

| 条件 | 触发 | 处理 |
| --- | --- | --- |
| 显式终答 | 模型输出 Final Answer | 正常返回 |
| 步数上限 | 达到 MAX_STEPS | 返回部分结果并告警 |
| 重复动作 | 同名工具、参数指纹相同 | 注入提示，要求换策略 |
| 时间预算 | 整体耗时超阈值 | 中断并保留已得信息 |
| 无信息增益 | 连续两轮 Observation 高度相似 | 强制收敛 |

我见过最多的失败模式是「礼貌地原地打转」：模型反复调用同一个检索工具，每次把 query 换一个同义词，观察结果大同小异，然后它继续换同义词。参数指纹相似度检测能挡住大部分，实现上对参数做归一化再算编辑距离就够用，不需要上 embedding。

另一个极端是过早终止。模型在第一步就给出 Final Answer，因为问题看起来简单。我的处理是在系统提示里明确要求：只要问题涉及具体数值、具体文件内容、具体外部状态，必须先调用工具再回答。这条硬性规则比「请仔细思考」有效得多。

## 四、Observation 的格式会反过来影响推理

这里有个不太直觉的经验：Observation 的呈现方式会显著改变模型后续的行为。

JSON 原始输出、带缩进的 YAML、自然语言摘要，三者喂给同一个模型，选工具的路径会不一样。我倾向于半结构化：先用一行自然语言概括结果，再给出关键字段的键值对。原因是模型在生成下一步 Thought 时会复用 Observation 的句式，纯 JSON 会让它的推理也变成字段堆砌，丢掉「为什么这么做」的部分。

错误信息的写法同理。「Error: 404」几乎没有信息量，「接口返回 404，说明该 DOI 不存在，可以尝试用标题检索」则直接给了下一步方向。这条不算作弊，因为工具的作者本来就知道错误意味着什么，把这层知识写进 Observation 是合理的工程投入。

## 五、我的做法

先把循环写成同步、单线程、无并行的版本，跑通再优化。异步和并行会掩盖状态管理的 bug，调试成本高一个数量级。

日志要能完整重放。每一轮我都记录：完整 prompt、模型原始输出、解析出的 action、实际执行耗时、Observation 全文。出问题时把这几项按顺序打出来，八成的问题看一眼就知道。只记最终答案的日志，等于没有日志。

不要把 ReAct 用在确定性流程上。如果任务本质是「查 A、用 A 算 B、写进 C」，写成固定代码更快更稳。ReAct 适合的是分支不确定、步数不确定、需要根据中间结果改变策略的场合。判断标准很简单：如果你自己动手做这件事时，下一步做什么取决于上一步看到了什么，那它适合 ReAct；如果你能提前把步骤列成清单，那它不适合。

## 六、和工具调用的关系

现在主流 API 都有原生的工具调用能力，很多人问还需不需要手写 ReAct 文本循环。我的判断是：协议层用原生 tool_calls，控制层保留 ReAct 的结构。

具体做法是让模型通过 tool_calls 返回动作，但要求它在调用前先输出一段 reasoning 字段。这样既拿到了结构化参数，又保留了显式推理。手写文本解析的版本仍有用武之地，比如模型不支持原生工具调用，或者你需要对格式做非常规约束。

最后提醒一个成本问题。ReAct 的每一步都要把整个 scratchpad 重新发一遍，token 消耗随步数近似平方增长。八步的循环，实际计费可能是单次问答的五六倍。控制步数上限不只是防死循环，也是在控成本。
