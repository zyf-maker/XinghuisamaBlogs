我本地跑模型的起点很功利：一批含未发表结构的分子描述不能出内网。跑起来之后发现，本地部署的难点不是「装不装得上」，而是「用哪套栈、压到几位、什么时候它反而不划算」。这篇按我实际踩过的顺序写。

## 显存要动手算，不要看推荐配置

显存占用约等于权重、KV 缓存（key-value cache）与运行时开销三部分。权重好算：

```text
权重显存 ≈ 参数量 × 每参数字节数
```

FP16 是 2 字节，INT8 约 1 字节，4 位量化约 0.5 字节，再加上量化元数据，实际取 0.55 到 0.6。7B 模型 FP16 约 14 GB，4 位约 4 GB。注意这里用的是 10 亿还是 2 的 30 次方要统一，厂商标称的「7B」通常按十进制算，和 `nvidia-smi` 显示的 GiB 差 7% 左右。

KV 缓存的公式更能解释「为什么长上下文这么吃显存」：

```text
KV 显存 ≈ 2 × 层数 × 注意力头数 × 头维度 × 序列长度 × 批大小 × 字节数
```

以 32 层、32 头、头维度 128 的 7B 模型为例，每个 token 的 KV 就是 2 × 32 × 32 × 128 = 262144 个元素，FP16 下约 0.5 MB；单条 8K 上下文约 4 GB，32K 就到 17 GB，而且随并发线性增长。这就是为什么同一张 24 GB 卡，跑 4K 对话很宽松，跑 32K 加八路并发就直接 OOM。缓解手段有两个方向：一是分组查询注意力（grouped-query attention, GQA）把 KV 头数降到查询头的几分之一，主流 7B 模型实际只占上面算出来的四分之一左右；二是分页注意力（paged attention），按块分配 KV，避免预留连续显存造成的碎片浪费，后者正是 vLLM 的核心。

## Ollama 与 vLLM 不是同一类东西

一句话概括：Ollama 是给个人开发机准备的，装完就能用；vLLM 是给服务端准备的，吞吐优先。

| 维度 | Ollama | vLLM |
|---|---|---|
| 安装 | 一条命令，自带模型拉取 | Python 包，依赖 CUDA 版本 |
| 模型格式 | GGUF 为主 | 原始权重，支持 AWQ、GPTQ、FP8 |
| 调度 | 请求级，简单排队 | 连续批处理（continuous batching）与分页 KV |
| 并发吞吐 | 低，几个人够用 | 高，几十路并发明显领先 |
| 量化 | 内置，命令带标签即可 | 需先用量化工具产出权重 |
| 适合 | 本地实验、单机助手、离线场景 | 团队共享服务、批量推理 |
| 多卡 | 支持有限 | 张量并行成熟 |

我不认为这是二选一。我的笔记本上是 Ollama，因为我不想为了试一个模型去处理 CUDA 版本地狱；实验室那台 4 卡机上是 vLLM，因为要同时服务五六个人。

## Ollama：把摩擦降到最低

```bash
ollama pull qwen2.5:7b-instruct-q4_K_M
ollama run qwen2.5:7b-instruct-q4_K_M "用三句话解释什么是 GNN"
```

服务默认监听 `127.0.0.1:11434`，接口兼容 OpenAI 的 `/v1/chat/completions`，所以已有的脚本把 base URL 一改就能指过来：

```bash
export OPENAI_BASE_URL=http://127.0.0.1:11434/v1
export OPENAI_API_KEY=ollama
```

标签里的 `q4_K_M` 值得说明：K 指 k-quants 系列，M 是中等混合精度，一部分层用更高位宽。同尺寸下 `q4_K_M` 的质量与体积平衡最好，`q2`、`q3` 这类小体积档在代码和数学任务上掉得很厉害。`q5_K_M` 比 `q4_K_M` 多占约 20% 显存，质量提升通常感知不到，除非你的任务对数字特别敏感。

还有一个 `num_ctx` 参数，默认值往往小于模型标称的上下文长度。不显式设置的话，长文档会被静默截断，这是最容易忽略的坑：

```bash
ollama run qwen2.5:7b-instruct-q4_K_M --parameter num_ctx 16384
```

## vLLM：为吞吐而设计

```bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --dtype bfloat16 \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.90 \
  --tensor-parallel-size 2
```

`--gpu-memory-utilization` 决定预分配的显存比例，vLLM 会用它装权重和 KV 块池。设太高容易和自己的其他进程抢，设太低则并发能力浪费。0.85 到 0.9 是我常用的区间。

`--max-model-len` 要按实际需求调小。它直接决定 KV 池能切出多少块，设成 128K 而实际只用 8K，等于把并发能力白白砍掉一大截。

启动后会打印一行关键信息：

```text
INFO: Maximum concurrency for 16384 tokens per request: 42.7x
```

这个数字是理论上限，实际受输出长度和调度影响，但它能让你立刻判断参数是否合理。

## GGUF 与 AWQ 该怎么选

这两个名字经常被混着说，其实解决的不是同一件事。

GGUF 是文件格式，把权重、分词器、模板、量化参数打包进一个文件，为 CPU 与 GPU 混合推理设计。它的量化方案（Q4_K_M 之类）在加载时反量化，通用性好，一台没有独显的机器也能跑。代价是反量化的计算开销，高并发下吞吐上不去。

AWQ 是量化算法，核心观察是权重里有一小部分通道对输出影响特别大，对这些通道保留更高精度，其余压到 4 位。它产出的是 4 位的 GPU 权重，配合 vLLM 这类引擎跑，吞吐明显更好。GPTQ 是更早的同类方案，精度略逊但生态更老。

| 你的情况 | 选什么 |
|---|---|
| 单机、无独显或显存紧张 | GGUF，`q4_K_M` 起步 |
| 有 N 卡、要服务多人 | AWQ 或 FP8，配 vLLM |
| 要极致省显存 | 4 位 AWQ，但要跑格式化回归 |
| 要最高质量 | 不量化，或 8 位 |

一个实践提醒：AWQ 权重是绑模型和引擎版本的。换了 vLLM 版本后如果加载报错，先怀疑量化权重不兼容，而不是模型本身坏了。

## 量化到底掉了什么

我的经验分任务看：

| 任务类型 | 4 位量化的影响 | 我的判断 |
|---|---|---|
| 分类、抽取、格式转换 | 基本无损 | 放心用 |
| 摘要、改写 | 轻微，长文本偶有漏点 | 可接受 |
| 代码生成 | 中等，长函数更易出语法错 | 关键项目用 8 位 |
| 数学与多步推理 | 明显，中间步骤容易断 | 不建议低于 8 位 |
| 工具调用与结构化输出 | 中等，参数格式出错率上升 | 必须跑回归 |

一个反直觉的观察：量化损伤不是均匀的。它更像把「本来就勉强会」的能力推过阈值，而不是整体等比例下降。所以拿基准平均分判断量化是否可用，很容易得出过于乐观的结论——要看你关心的那类难例。

这也是我坚持保留二十条金标样本的原因：换量化档位前后各跑一遍，比较失败类型，比看分数有用得多。

另一个坑是量化模型和提示词的耦合。某些提示词在 FP16 下稳定输出 JSON，压到 4 位后开始偶发多余的解释性前缀。上线前必须重跑格式合规率。

## 什么情况下本地部署不划算

算总账的时候，硬件折旧、电费、以及你自己维护环境的时间都要计入。我的经验边界是这样的：

一次性、低频的任务，走 API 更便宜也更省心。只有持续跑、数据不能出内网、或者对网络延迟极敏感的场景，本地方案才成立。

独显小、内存大的机器可以试 CPU 推理，但速度是另一个量级，只适合离线批处理。用统一内存的机型跑 4 位大模型能出结果，别指望交互体验。

还有一个常被低估的成本：模型升级。API 那边供应商帮你换，本地这边每次换模型都要重新验证显存、量化质量、模板格式。所以本地部署的隐性开销主要在维护，不在第一次跑通。

## 我的做法

一个 Ollama 装在日常机器上，用于实验、写脚本、离线读文档；一个 vLLM 服务放在带卡的机器上，只对内网开放，前面加一层简单的鉴权。两边的提示词模板和评测脚本共用同一份文件，保证换栈时行为可比。

部署完之后我做的第一件事不是压测，而是把模型名、量化档、`num_ctx`、启动参数写进一个 Markdown 文件。半年后回头看，能省掉大量「当时到底怎么配的」的考古。
