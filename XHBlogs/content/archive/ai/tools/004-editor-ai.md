一个常见的阶段是三件套同时在手：Cursor 写着，终端里挂着 Claude Code，VS Code 里 Copilot 的补全还开着。后来总会关掉一部分，因为同时开三个不是效率，是噪音。这篇讲它们真正的差异在哪，以及怎么分配。

## 差异不在模型，在上下文从哪里来

三个工具都可能用同一个底层模型，但递进去的上下文完全不同，这才是行为的根源。

Copilot 的补全看的是光标前后的代码、当前文件、以及编辑器打开的相关文件。它的强项是局部连续性：写下函数签名，它把循环体补完。它不知道数据库 schema，也不知道昨天那个 bug 的讨论。

Cursor 的对话模式会主动做检索，把相关文件、符号定义、甚至整个仓库的索引拉进来。可以问「这个接口在哪些地方被调用」，它会去搜。代价是它倾向于一次性带很多文件进去，容易把不相关的部分也塞进上下文。

Claude Code 这类命令行代理（agent）的上下文是它自己用工具读出来的。它执行 `grep`、读文件、跑测试，按需获取，而不是预先塞满。好处是范围可以很大，坏处是每一轮都要花时间探索，且必须能看懂它执行的命令。

按「自主程度」排序大致是：补全 < 编辑器内对话 < 终端代理。自主程度越高，越需要给它约束和验证手段。

## 补全：快，但只在局部成立

Copilot 那一类补全的价值在于不打断思路。它的正确用法是写清楚签名、类型、docstring，然后让它填。反过来，一个语义模糊的函数名只会换来一堆需要删的代码。

补全适合处理「显而易见但打字费时」的部分：构造参数列表、写重复的校验、补测试的样板。逻辑分支应当自己写。补全生成的代码几乎从不写边界条件，`null`、空数组、超长输入，它默认都不会管。

另外补全有个隐性成本：接受建议只需要一个 Tab，审查它却要读一遍。手速快过脑速的时候，仓库里就会积累没人真正读过的代码。对超过五行的补全建议，先看再收是更稳的习惯。

## 编辑器内对话：适合改造已有代码

Cursor 这类工具最舒服的场景是「在看得见的范围内改」。选中一段代码，说「把这个改成流式解析」，它就地给出 diff，逐块接受或拒绝。这个交互形态的价值是审阅成本低，因为改动范围就在眼前。

它的弱点是跨文件重构。让它「把这个模块拆成三个文件」，它经常改得动但改不全，比如更新了引用却漏了测试里的 mock。跨文件改动越多，越需要自己跑一遍测试。

几个使用上的细节：

- 明确告诉它不要改什么。「只改这个函数，其他文件不要动」能显著降低误伤。
- 让它先给方案再动手。比较好的做法是在对话里先要一个改动清单，确认后再让它写。
- 上下文用 `@` 精确指定文件，比让它自己猜准得多。它猜的时候倾向于拉一大堆相近名字的文件。

## 终端代理：跑得远，但要给它护栏

Claude Code 这类的形态是：你在终端描述任务，它自己读代码、改文件、跑命令。写一个从零开始的小工具、批量改几十个文件的命名、补齐缺失的测试，这类任务它做得比编辑器内对话好，因为它能验证自己的改动。

前提是环境要能验证。有测试、有类型检查、有 lint 的项目，代理的产出质量高一个档次，因为它能自己发现错误并修。没有测试的项目，它会自信地把错的东西交付出来。

一个稳妥的做法是先给它一份项目约定文件（Claude Code 读 `CLAUDE.md`），写清楚：用什么包管理器、测试怎么跑、哪些目录不要碰、代码风格要求。这份文件是投入产出比最高的一步，比反复在提示里重复要求有效。

```markdown
规则：
- 包管理用 pnpm，不要用 npm install
- 改完必须跑 `pnpm test -- --run`，失败要修到通过
- 不要修改 migrations/ 下的历史文件
- 提交信息用中文，一行，不超过 50 字
```

第二个护栏是权限。让代理自动执行所有命令很危险，`rm -rf`、`git reset --hard`、往生产环境发请求都可能发生。通常应当让它对写文件和执行命令逐次确认，只有在临时分支和容器里才放开。

第三个护栏是收尾审查。代理说「已完成」不等于完成。三件事应当固定做：看 `git diff` 的每一行、跑测试、看它有没有顺手改掉不该改的东西。有一种典型情况是，它为了让测试通过，直接把断言改宽了——这类「作弊」是自主代理最常见的问题。

## 三类工具的能力对照

| 维度 | 补全 | 编辑器内对话 | 终端代理 |
|---|---|---|---|
| 交互粒度 | 行、块 | 选区、文件 | 任务、仓库 |
| 上下文来源 | 打开的文件 | 索引加检索 | 自己读 |
| 是否执行命令 | 否 | 有限 | 是 |
| 适合任务 | 样板代码、重复结构 | 单文件重构、解释代码 | 跨文件改造、从零搭 |
| 主要风险 | 未经审查的代码堆积 | 跨文件漏改 | 越权操作、改测试作弊 |
| 审阅成本 | 低 | 中 | 高 |

## 一种分配方式

日常写业务逻辑，只开补全。它不打断思路，也不需要写提示。这种「零交互」的价值被低估了，大部分时间并不需要 AI 参与决策，只想少打点字。

单文件级别的改动、读不懂的老代码，用编辑器内对话。选中的范围就是边界，改完立刻能看 diff。

需要跨文件、需要跑命令验证的任务，交给终端代理，并且一定在独立分支上做。它的产出应当当作一个初级同事的提交来审：默认有错，必须验证。

不同时开三个。同时开的时候，大部分时间其实在管理工具而不是写代码。

## 几个判断

工具之间的差距，很大一部分取决于项目本身。测试覆盖好、类型严格、目录结构清楚的项目，三类工具都更好用，因为「对错」是可判定的。烂项目里，AI 只是更快地生产烂代码。

不要指望 AI 帮人做架构决策。它可以给三个方案，但选哪个取决于对三个月后维护成本的判断，这个信息不在仓库里。

最后一条经验：把 AI 生成的部分和人工写的部分在提交历史里分开。可以单独提交 AI 生成的样板，再单独提交人改的逻辑。出问题时 `git log` 能直接定位是哪一类改动引入的，回滚也干净。
