选模型这件事，最蠢的做法之一是拿榜单第一名直接上线，两周后因为 P95 延迟翻倍又整个换回来。所以先给自己定个规矩比较好：先写约束，再谈能力；先算单任务成本，再看单价；先看分位数，再看均值。这篇记录这套流程，以及它能省下的那些返工。

## 能力、价格、延迟不是三个能同时优化的角

同一条产品线上，这三者基本同向：参数更大、训练更久的模型，能力更强，单价更高，单次生成也更慢。所谓三角，真正的含义是你必须挑一个角让步，而不是三个都要。

跨家族时这个关系会松一些。蒸馏模型、混合专家（mixture of experts, MoE）架构、专做小模型的公司，都会在某个价位给出不成比例的能力。所以选型的动作不是找最强，而是在预算和延迟包络内找能力上限。

一个比较稳的排序是固定的：延迟和成本是硬约束，能力是可优化项。反过来做的人，最后往往在流量上涨那天被迫改架构，而改架构的成本远高于选型时多花的两天。

## 先把需求写成可验证的硬约束

这一步比评测重要，因为它能一次性砍掉大半候选。通常列成下面这张表，每条都要求能实测，而不是「大概支持」。

| 约束 | 怎么验证 | 常见虚标点 |
|---|---|---|
| 上下文窗口（context window） | 用接近上限的输入跑一次 | 标称很长，有效召回远低于标称 |
| 结构化输出 | 传 JSON Schema，跑 200 次统计合规率 | JSON 模式只保证是合法 JSON，不保证符合 schema |
| 工具调用 | 多轮对话、参数含嵌套对象 | 单轮简单调用能过，多轮就丢参数 |
| 中文长文本 | 换成自己的领域文档 | 英文基准的分数不能迁移 |
| 并发与限流 | 压测到目标 QPS | 免费额度下的表现不代表付费层 |
| 数据合规 | 看合同与日志留存策略 | 缓存与日志区域经常被忽略 |

筛完这一轮，候选通常只剩三四个，讨论范围立刻收敛。

## 价格要算单任务成本，不是每百万 token 单价

单价是给采购看的，工程上真正关心的是完成一个任务花多少钱。把它写成一个小函数，比较起来会方便很多：

```python
def cost_per_task(in_tok, out_tok, cache_tok, p_in, p_out, p_cache,
                  retry=0.05, success=0.97):
    per_call = (in_tok - cache_tok) * p_in + cache_tok * p_cache + out_tok * p_out
    return per_call * (1 + retry) / success
```

这里有两个常被忽略的乘数：重试率和成功率。一个通过率九成的模型，实际成本要除以 0.9；失败还要重跑的话，再乘一次。单价便宜四成的模型最终更贵的例子并不少见，原因就是失败率高、输出啰嗦。

输出 token 通常比输入贵三到五倍，所以「让模型简短回答」不是文风问题，是成本问题。一句「只输出结果，不要解释」常常能把输出从 400 token 压到 60，任务成本直接砍掉一大半。

提示缓存（prompt caching）对固定系统提示的收益极大。同样 1500 token 的输入里 1200 是固定前缀，命中缓存后这部分按很低的费率计费。前提是前缀逐字一致——在系统提示最前面塞一个时间戳，缓存就永远不命中，这是一个很典型的坑。

## 延迟要拆成三段看

端到端延迟约等于排队时间、首 token 时间（time to first token, TTFT）与输出 token 数乘每 token 时间（time per output token, TPOT）三者之和。这三段的对策完全不同：排队靠提额度或错峰，TTFT 靠模型规模与机房位置，TPOT 取决于模型规模和并发批大小——输出越长，总生成时长按 TPOT 线性放大，但 TPOT 本身不随输出变长而变。

流式输出改善的是感知延迟，不是总时长。如果你的下游必须等完整 JSON 才能解析，流式一点用都没有，该做的是减少输出字段。

延迟评估应当一律看 P95 而不是均值。均值 1.2 秒、P95 8 秒的服务，在交互场景里等于不可用，但报表上它很好看。

## 评测流程

1. 抽 60 到 100 条真实请求做金标集，故意留两成是长尾和已知难例。
2. prompt 固定，一次只换模型，温度设 0，原始输出全部落盘。
3. 用成对比较（pairwise）盲评，不做绝对打分。不同模型对 1 到 5 分刻度的理解差异很大，跨模型比绝对分基本无效。
4. 统计失败类型：答错、格式错、拒答、超时。这四类的修法完全不同，混在一起统计只会得出「都差不多」的结论。
5. 金标集和脚本一起进仓库，模型换版本就重跑。

这套流程一次性投入大约半天，但它把「感觉这个模型更聪明」变成了可复现的数字。

## 几个具体的坑

公开榜单和你的任务分布经常差很远。一个在数学基准上领先的模型，可能在「从表格里抽字段」这种任务上不如便宜一半的对手。榜单只用来缩小候选，不用来做最终决策。

同名模型会漂移。供应商在不改名的前提下更新后端检查点（checkpoint）是常态，所以评测结论都应当带日期，不当作永久事实。

限流往往比价格更早成为瓶颈。做容量规划时把每分钟请求数和每分钟 token 数一起算，很多模型在你的目标并发下根本不是钱的问题，是配额的问题。

长上下文有位置效应。把关键信息放在超长输入的中间段，召回会明显下降，这是已有研究反复验证过的现象。所以真正可用的上下文，往往只有标称值的一半。要放长文档，不如先做检索。

## 结论与默认做法

一个基本判断是：大多数团队高估了模型能力的差异，低估了延迟与失败率的复利。同一个需求，强模型把准确率从 88% 提到 92%，听起来不错；但如果它的 P95 从 1.5 秒涨到 6 秒，用户的实际完成率可能反而下降。所以能力提升值得设一个门槛——只有当失败率下降能省下明显的下游返工时，才值得付出延迟代价。

三层结构：一个便宜快速的小模型处理绝大多数简单请求；一个强模型处理小模型判不准的；一个路由器按输入长度、任务类型和历史失败率决定走哪层。路由用规则就够，不必再训一个模型。

这个结构最大的好处不是省钱，是可替换。任何一层换模型，只影响那层的流量，评测范围也可控。选型不是一次决定，而是给自己留好每次只换一块的余地。
