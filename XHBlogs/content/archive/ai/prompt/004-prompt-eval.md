改提示词最大的问题不是改不好，是不知道有没有改好。手工试几条样例，感觉变好了，上线之后旧场景开始出错——这种情况并不少见。更稳妥的方式是把它当成软件工程问题处理：建测试集、定指标、跑回归，用数字决定改还是不改。

结论先说：一套五十条样本的固定测试集，加上一个能在本地跑的命令行脚本，比任何提示词技巧都更能提高产出质量。它不让你变强，但让你不再自己骗自己。

## 从五十条样本开始

不要等攒够五百条再动手。合理的起步方式是：从真实输入里抽五十条，覆盖能想到的全部主路径。

采样要分层，不能随机。按业务维度切，比如按文档长度分三档、按语言分两档、按输入是否含表格分两档，每一格至少两条。这样做的原因是随机采样很容易在长尾上采不到样本，而提示词翻车基本都发生在长尾。

每条样本存成一个结构化记录，用 JSONL，一行一条：

```json
{"id": "case_012", "split": "core", "input": "...", "expected": {...}, "notes": "含嵌套表格，2026-03 用户反馈过漏抽"}
```

字段里的 `notes` 值得加上，比想象中重要。它记录这条样本为什么进来、对应哪个线上问题。半年后回来看，没有这条注释你根本不敢删它。

`split` 用来分层。通常分三档：`core` 是必须一直过的核心场景，`edge` 是边界与历史 bug，`holdout` 是平时不看、只在发版前跑的对照集。没有 holdout，测试集会慢慢被过拟合——你所有的调整都在同一批样本上验证，最终只是把它们背下来了。

五十条之后怎么扩？只从线上失败案例里加。每次线上出问题，先把它做成一条样本，再改提示词。这个顺序不能反，否则你会改出一个只在你脑子里成立的版本。

## 期望值怎么标

这一步是工程量的大头，也是最容易被低估的。

分类和抽取类任务最好办，期望值是结构化的，可以直接比对。生成类任务麻烦，可以退一步，不标「标准答案」，改标「不可违反的检查点」：必须包含的字段、必须遵守的字数上限、必须回避的表述、必须引用的原文片段。检查点比参考答案稳定，因为它不要求唯一解。

标注一致性要验。挑十条样本让两个人独立标，算一致率。一致率低于八成，说明标注标准本身没写清，此时建评测没有意义——你在测一个定义不清的东西。常见的坑就在这里：分歧往往全在「部分匹配算不算命中」这一条上，最后不得不返工重标。

还有一个务实的原则：期望值宁严勿宽。宽松的期望让指标好看，但拦不住问题。建议把「必须完全正确」和「部分正确」分成两档，分别统计，而不是合并成一个加权分数——加权一旦引入，就再也说不清提升来自哪一档。

## 指标：三层分开算

指标可以分三层，不合成单一分数。

| 层级 | 指标 | 判定方式 |
| --- | --- | --- |
| 格式 | 解析成功率、字段完整率、枚举合法率 | 代码判定，无需模型 |
| 内容 | 字段级精确匹配、召回、F1 | 代码比对结构化期望值 |
| 质量 | 检查点通过率、引用准确性 | 规则加人工抽查 |

第一层必须是百分之百。解析失败率哪怕只有百分之二，也意味着线上每五十次请求就有一次要进异常流程。这一层挂了，后面两层不用看。

第二层建议用字段级指标而不是整条匹配，因为整条匹配会把一个字段的错误放大成整条失败，看不出改进幅度。字段级指标还方便定位：是日期抽错了，还是金额单位错了。

第三层如果要用模型打分，务必固定同一个评分模型和同一份评分提示词，并把评分模型的名字和版本写进报告。常见的情况是用模型打分做前后对比，结果中间悄悄换了评分模型，指标涨了五个点，其实是评分器变宽松了。

模型打分有个已知偏差：倾向于给自己同族模型的输出更高分。所以评分模型最好和被测模型不同族，或者至少用人工标注过的一百条做一次校准，把分数映射到人判上。

## 跑回归的脚本

评测可以写成一个可以本地跑的命令，输出一份 Markdown 报告和一份机器可读的 JSON：

```python
import json, asyncio

async def run(suite_path: str, prompt_version: str) -> dict:
    cases = [json.loads(l) for l in open(suite_path, encoding="utf-8")]
    results = []
    for c in cases:
        out, usage = await call_model(prompt_version, c["input"])
        ok_fmt, err = validate_format(out)
        score = None if not ok_fmt else score_fields(out, c["expected"])
        results.append({"id": c["id"], "split": c["split"],
                        "format_ok": ok_fmt, "error": err, "score": score})
    return summarize(results, prompt_version)
```

几个实现细节值得说。并发要限，不然容易撞上速率限制（rate limit），把超时错误算进指标里会污染结果。重试策略要固定，通常只对 5xx 和超时重试两次，对 4xx 直接记失败——如果对格式错误也重试，等于偷偷给被测版本加了额外机会，对比不公平。

温度固定为 0。同一版本跑两遍结果应当完全一致；如果不一致，先解决这个问题再看指标。建议跑两次做一致性检查，两次结果不同的样本单独列出来。

成本要记账。把每次调用的 token 数和费用累加进报告，改提示词往往带来长度变化，只看质量不看成本会做出糟糕的决定。

## 怎么判断改动是否真实有效

小样本上的指标波动很容易骗人。五十条样本，命中率从 78% 到 82%，这通常只是两条样本的差别，不构成结论。

更可靠的做法是看配对差异，而不是看总分。同一批样本，逐条比较改动前后：变好的几条、变差的几条、不变的几条。如果变好 6 条、变差 5 条，这不算提升，即使总分涨了一点。如果变好 9 条、变差 1 条，方向就很清楚了。

```text
v3 → v4
improved: 9  (case_002, 007, 013, 021, 028, 030, 041, 045, 049)
regressed: 1 (case_018: 日期从 2026-03-01 变成 2026-3-1)
unchanged: 40
```

这种展示方式还有个好处：回归的样本是具体可查的。`case_018` 立刻说明格式规范化那一句被新版本弄丢了，改起来很直接。

另外，改动的评估要在 `core` 和 `holdout` 上分别看。如果 `core` 涨、`holdout` 跌，基本可以确定是过拟合到测试集了。

## 维护：测试集会腐化

测试集不是一次性的。它有三个腐化源。

标注标准变了。业务规则调整后，旧样本的期望值过期，但没人重标。做法是给每条样本加 `label_version`，规则变更时按版本号筛出受影响的样本重标。

模型换了。同一份提示词在旧模型上 90 分，新模型上可能只有 82，也可能更高。每次换模型必须全量重跑，并把模型名写进报告文件名。

样本过时。线上输入分布会漂移，半年前的五十条可能已经不代表现在的流量。建议每季度从最近的真实输入里抽二十条补进去，同时淘汰掉已经不可能出现的场景。

成本上，全量跑一次五十条很快，可以直接挂进持续集成（continuous integration），改提示词的文件就触发。门槛建议设为：格式成功率必须 100%，内容 F1 不得低于当前基线，任一条 `core` 样本从通过变失败就阻止合并。这三条挡住了绝大多数想当然的改动。

## 结论

评测的价值不在于给出一个分数，而在于把「感觉变好了」变成「哪几条变好了、哪几条变差了」。它强迫你把期望值写下来，而写下来的过程本身就会暴露需求里含糊的地方——很多时候标到第二十条样本时，你会发现原以为清楚的任务其实有三种不同的正确做法。

如果要给一个起步建议：先用半天时间，把手上正在调的那个提示词做五十条样本、写一个一百行的脚本。别追求指标体系的完备，先跑起来。跑起来之后，你会开始按测试集写提示词，而不是按直觉写。

最后一个提醒：不要把评测分数当成目标。常见有团队为了让分数好看，把难样本从测试集里挪出去——那只是把仪表盘拆了，车还在往前开。
