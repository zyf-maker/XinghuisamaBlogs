经验上：凡是能用一句规则说清的，就不要用示例。但有一类任务规则写不出来——边界靠语感、判定标准要靠对比才能说清——这时候示例是唯一有效的手段。区别在于示例传递的不是内容，是判定标准的坐标。

这篇讲的是怎么判断该用示例，以及示例怎么选才不会帮倒忙。

## 规则失效的三种情形

第一种是分类边界模糊。「判断这条 bug 报告是否包含可复现步骤」——什么叫可复现，不同人标准差很远。你写「有明确的输入和预期结果」，模型还是会放过「登录后点按钮没反应」这种缺关键信息的描述。给三条正例三条负例，边界会立刻收紧。

第二种是格式约束复杂。输出要符合某种内部规范，字段排列、空值表示、缩写习惯都有讲究。文字描述要写很长，示例三行就够。

第三种是风格迁移。要让输出带上某种语气或句式，形容词基本无效，「像下面这样写」立竿见影。

反过来，凡是能枚举成集合的（只能取这三个值）、能写成数字边界的（不超过 50 字）、能写成逻辑条件的（有 A 则输出 B），都该用规则。规则短、可维护、改起来不会牵连别的样例。

## 示例传递的是判定坐标

有个说法叫「示例教会模型任务」，这句话容易误导。模型预训练时已经见过大量同类任务，它不缺任务知识，缺的是你这次的标准。

所以示例的作用是校准，不是教学。判断标准是：如果你的示例互换顺序、或者替换成同类的其他样本，输出分布没有明显变化，说明示例只在传递「这是个什么任务」，那它基本是多余的，换成一句任务描述更省 token。

真正有效的示例，换掉任何一条都会让输出明显变化——因为每条都在钉一个具体的边界点。

## 示例数量和边际收益

做过对比的话，收益曲线大概是这样的：

| 示例数 | 典型表现 |
| --- | --- |
| 0 | 只能靠规则，边界任务失败率高 |
| 1 | 大幅改善格式，边界仍不稳 |
| 3–5 | 多数任务的甜点区，覆盖主要边界 |
| 8 以上 | 收益趋平，开始挤占输入与上下文 |

超过八条以后，常见的问题通常不是不够，而是互相矛盾。示例之间判定标准不一致，模型会取平均，输出变成四不像。选示例的第一原则不是多，是一致的判定标准——宁可只留四条干净的，也不要八条里掺两条边界冲突的。

另一个成本是上下文。示例占的空间是从输入里抢的，长文档任务上这个代价很真实。一般建议先按 4 条起步，加示例的前提是先确认输入没被截断。

## 怎么挑示例：相似度优先，多样性兜底

挑选策略可以按优先级排：

先用检索。把候选示例做成向量索引，按当前输入检索最相近的几条。这一步的收益最大，因为它让示例落在同一个子分布上。文本嵌入（text embedding）用现成的就行，不必自己训。

再补一条边界样本。检索出来的往往都是「典型正例」，模型会过度倾向判正。有必要强制塞一条最难判的负例，专门针对最容易混淆的那个情形。

最后检查多样性。如果四条示例全是同一个模板改几个词，等于只有一条。要看句式、长度、领域是否分散。

排序也有影响。把最难的示例放在最后效果通常更好——结尾位置权重高，模型更容易把最后一条的标准当成整体标准。如果最难的示例放第一条，后面三条简单的会把它稀释掉。

```python
def build_few_shot(query: str, pool: list[dict], k: int = 4) -> list[dict]:
    hits = retrieve_similar(query, pool, k=k - 1)
    hard_negative = pick_hardest_negative(query, pool)
    picked = hits + [hard_negative]
    picked.sort(key=lambda x: x["difficulty"])  # 最难的放最后
    return picked
```

这段没什么技术含量，但它把「相似度 + 强制边界 + 难度排序」三件事固化成流程，比每次手挑稳。

## 格式细节比内容更容易出事

示例的呈现方式有几个坑，前两个尤其常见。

第一，示例和真实输入必须用同一套分隔符。示例里用 `Q:` / `A:`，真实输入却只给了裸文本，模型会把输入当成示例的一部分继续续写。稳妥的做法是统一用 XML 标签，每段都闭合：

```text
<example>
<input>退款申请：收到货三天，包装破损</input>
<output>{"category": "物流破损", "urgent": true}</output>
</example>
```

第二，不要给示例编号。写「示例 1、示例 2、示例 3」，模型有时会在输出里带上「示例 4」之类的字样，尤其是在格式较松的模型上。

第三，输出示例里不要有省略号。`{"items": [...]}` 这种写法会让模型学会输出字面的 `...`。要么给完整对象，要么在提示词里明确说「此处省略，仅示意结构」，前者更稳妥。

第四，示例里的输入文本不要用真实业务数据。脱敏不彻底的话，模型会在输出里复述这些内容。确实出现过模型把示例里的人名带进新生成文本的情况。

## 示例与规则的混合

实际项目里几乎不可能是纯示例或纯规则。常见的默认结构是：规则说明什么绝对不能违反，示例说明边界在哪。

```text
判定规则：
- category 只能取 [物流破损, 商品质量, 描述不符, 其他]
- 涉及金额争议时 urgent 为 true

以下是标注示例，注意第 3 条中「包装破了但商品完好」仍归为物流破损。
<example> ... </example>
```

在示例前加一句「注意第 3 条」，能显著提高模型对该示例的利用率。这句话的成本很低，收益在测试里很稳定。

反过来，规则条数要保持克制。规则超过六条，模型对示例的依赖会下降，输出变得更像在套模板，反而丢失了示例本来要传递的语感。这是个权衡，没有一个通用数值，通常的做法是先只写规则跑一遍，再逐步加示例，看哪一步开始有增益。

## 验证示例是否真的在起作用

这一步容易被跳过。可行的做法是做消融：同一批测试样本，分别跑「零示例」「保留示例但打乱顺序」「去掉最难的那条」，比较差异。

如果零示例和四示例的结果几乎一样，说明示例是在浪费上下文，删掉。如果打乱顺序和原顺序差异很大，说明排序敏感，得把顺序固定进版本管理。如果去掉最难那条掉得最多，说明边界样本是关键，要保证每次都能检索到。

这个消融花不了多少时间，但它能挡住一种很常见的自我欺骗：改了提示词之后感觉变好了，其实只是这次抽到的输入比较简单。

## 结论

示例是提示词里最贵的部分，占 token、占维护成本、还容易互相冲突。所以更稳妥的默认姿势是先用规则，规则确实写不清边界时才上示例，而且从四条起步。

挑选上，「检索加一条硬负例」的组合通常比人工精心构造的「完美示例集」更可靠——后者在开发集上很漂亮，换一批输入就崩，因为它优化的是一批具体样本，不是判定标准。

最后一句：示例要跟着数据集版本走。标注标准改了，示例必须同步改，否则提示词里留着的是旧标准的化石，比没有示例更糟。
