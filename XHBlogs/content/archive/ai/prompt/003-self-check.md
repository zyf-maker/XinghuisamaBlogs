「让模型再检查一遍」是投入产出比最不稳定的一招。有时候它能把明显的算术错误挑出来，有时候它对着一段完全编造的内容认真地点头说没问题。差异不在提示词写得好不好，在于错误的类型——有些错误模型能从上下文里发现，有些它根本没有判断依据。

这篇想把这招的适用边界划清楚。

## 自我反思在什么条件下有效

有一个前提常被忽略：模型必须能接触到独立于原始答案的信息。

举个具体例子。模型把 2024 年的一篇论文说成 2021 年，你让它「再检查一遍引用是否正确」，它检查的是自己刚才那段话的内部一致性，而那段话里没有任何东西能证伪这个年份。它会重新确认一遍「2021 年」这个说法读起来很顺，然后告诉你没问题。

反过来，如果原始材料在上下文里，让它逐条比对「文中出现的年份」和「你引用的年份」，这件事就变得可做了。此时反思不是让模型内省，是让它做一次比对。

所以判断标准很直接：让模型检查的那件事，它的判据是否在上下文里。判据在，成功率不错；判据不在，基本是随机数。

## 能自查和不能自查的错误

可以按可验证性把常见错误分成三层。

| 错误类型 | 例子 | 自查是否有效 |
| --- | --- | --- |
| 形式约束 | JSON 缺字段、枚举值越界、字数超限 | 有效，可以用代码判，不必用模型 |
| 上下文内不一致 | 与前文数字矛盾、遗漏了输入中的某条记录 | 中等，需要明确比对指令 |
| 外部事实 | 论文年份、人名、API 参数是否存在 | 基本无效，需要检索或工具 |

第一层根本不该交给模型。JSON 能不能解析、字段在不在、枚举值合不合法，用代码检查比用模型检查快几个数量级，而且结论确定。常见有人用「请检查你的输出是否符合 JSON 格式」来兜底，结果模型回复「已检查，格式正确」，而输出里少了一个右括号。

第二层是反思真正能帮上忙的地方，但要用对写法。泛泛地说「检查是否有遗漏」，模型多半回你一句「已全面检查」。必须把检查对象具体化：把输入里的编号清单和输出里的编号清单分别列出来，让它做集合差。

第三层不要碰。调用大模型做事实核查，得到的往往是对自己前一次幻觉的二次确认，而且这次还带上了「已核实」的标签，危害更大。

## 有效的自我检查长什么样

推荐的写法是把「反省」换成「执行一道检查题」。区别在于前者要求模型对自己做元认知，后者要求它做一次具体的比对操作。

```text
下面是你刚才的输出和原始输入。

原始输入中的订单编号：[A1001, A1002, A1003, A1004]
你的输出中出现的订单编号：[A1001, A1002, A1004]

请只回答两件事：
1. 输入中有但输出中没有的编号；
2. 输出中有但输入中没有的编号。
不要评价整体质量，不要给建议。
```

这个提示词有几个刻意的地方。清单应由代码抽出来再填进去，而不是让模型自己去原文里找——让模型「从下面这段话里提取所有编号」会引入新的错误。禁止它评价质量和给建议，是因为一旦放开，它就会开始说「整体表现良好，建议……」这类无信息量的填充，反而把真正要找的差异淹了。

另外，这类检查要用独立的调用。同一次生成里让它「先写再检查」，检查那部分和生成部分共享同一份内部状态，纠错率明显低于单独发一次请求。代价是多一次调用的钱，值得。

## 用外部信号替代自我评价

基本判断是：凡是能用程序判的，就不要用模型判；凡是能用工具的，就不要用模型的记忆。

具体做法是给验证环节接上可执行的判据：

```python
import json

def validate(raw: str, schema: dict) -> tuple[bool, str]:
    try:
        obj = json.loads(raw)
    except json.JSONDecodeError as e:
        return False, f"不是合法 JSON: {e}"
    missing = [k for k in schema["required"] if k not in obj]
    if missing:
        return False, f"缺字段: {missing}"
    bad = [k for k, v in obj.items()
           if k in schema["enum"] and v not in schema["enum"][k]]
    if bad:
        return False, f"枚举越界: {bad}"
    return True, ""
```

这段代码替代了提示词里至少三行「请确保……」的祈使句，而且不会因为输入变长而失效。

需要外部知识的时候，正确做法是给工具，不是给鼓励。让模型先检索再回答，比让它「仔细回忆、确保准确」有效得多。这一点在检索增强（retrieval-augmented generation）的上下文里已经是共识，但在纯提示词场景里还是经常被忘掉。

## 反思循环的收益衰减

有对照实验连续反思三轮：生成、检查、修改、再检查。结果通常是这样：

第一轮反思能改掉一部分问题，主要是格式和明显的遗漏。第二轮收益很小，改的多是措辞。第三轮开始出现反向损伤——模型把本来正确的表述改错，或者为了「显得有改进」而加一些没必要的解释。

原因是反思本身没有新的信息来源。第二轮之后的每一次修改，都是在同一份信息上反复重采样，噪声累积。合理的上限是一轮，只有在有外部反馈（代码报错、检索结果、用户指出）时才允许第二轮。

这个观察和「思维链越长越好」的直觉是冲突的，但在实践中很稳定。长链推理（long chain-of-thought）在数学和代码这类有内在验证结构的任务上确实有效，因为每一步都能被后续步骤检验；而开放式的文本改写没有这个结构。

## 什么时候该放弃自我检查

有三种情况应该直接砍掉反思环节。

输出是给人看的、且人一定会读。让人来判比让模型判便宜，也更准。加一层模型自检只是把问题往后推。

任务本身没有唯一答案。写一段产品介绍，好不好没有判据，「检查一下是否准确」会退化成风格评价。

成本敏感的高频调用。每次调用翻倍的成本，换来的可能只是百分之几的格式修复率，而格式问题用代码兜底更划算。

## 一个折中的落地结构

比较稳妥的默认流程是：

1. 生成，输出结构化结果。
2. 代码校验格式与枚举，失败则带上错误信息重试一次。
3. 只在需要语义比对时，用独立调用做一次定向检查，检查项由代码生成。
4. 记录每次检查的命中率，命中率长期低于阈值就删掉这一步。

第四步是关键。自我检查很容易变成一种心理安慰，加了就再也不敢删。应给它记两个数：它拦下了多少真实错误，以及它引入了多少假阳性。假阳性高的时候，人还得一条条看，成本反而上升。

```text
check_calls: 1200
blocked: 37        # 拦下的错误
false_positive: 21 # 被判不合格但实际没问题
```

假阳性超过拦下数量的一半时，就说明这条检查的判据写得不够具体，该重写或者删掉。

## 结论

自我反思不是让模型变聪明的手段，它只是把一次生成拆成两次，让第二次有机会看到第一次没注意到的部分。这个机制的上限由上下文里已有的信息决定，不会因为多问几遍就突破。

所以写提示词时更值得把力气花在两件事上：把判据显式化，把能外部化的检查外部化。前者让模型有东西可比，后者让比对根本不经过模型。

至于「让模型扮演严格的审稿人」这类角色扮演式反思，通常没什么必要。它改变的往往是语气，不是判断。
