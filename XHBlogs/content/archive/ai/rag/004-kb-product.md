一个能跑通的 RAG 演示和一个能交给别人用的知识库产品，中间隔着的不是模型能力，而是数据治理。演示里语料是静态的，权限是不存在的，文档只会增加不会修改；产品里这三条全都不成立。语料每天在变，有的人只能看一部分，删掉的文档不能被检索到。这篇写把这几件事做成可用状态时要绕开的坑。

## 增量索引：先定删除语义

增量更新最容易被简化成"新文档来了就嵌入"。问题在于旧块怎么办。如果文档更新后只是追加新块，旧块仍然留在索引里，检索会同时命中两个版本，模型拿到的可能是三个月前的政策。

一种常见的做法是给每个块一个稳定标识：`doc_id` 加内容哈希，或 `doc_id` 加 `section_path` 加块序号。更新时先按 `doc_id` 查出全部旧块并删除，再写入新块。这个"先删后写"听起来浪费，但它保证不会出现版本混杂，而且实现简单，出错时容易回滚。

真正麻烦的是失败处理。删除成功、写入失败，文档就凭空消失了；写入成功、删除失败，就出现双版本。索引和元数据在两个系统里，没有跨系统事务。一种稳妥的解法是引入状态字段：文档在元数据表里标记为 `indexing`，写入完成后改成 `active`，检索时只查 `active` 的块；删除则先标记为 `deleting`，检索侧立即过滤掉，后台再清理向量。这样即使中途崩溃，也只是留下垃圾数据，不会让用户看到错误内容。

```python
def upsert_document(doc_id: str, chunks: list[dict]) -> None:
    meta.set_status(doc_id, "indexing")
    try:
        index.delete(filter={"doc_id": doc_id})
        index.upsert(vectors=chunks)
        meta.set_status(doc_id, "active", version=hash_of(chunks))
    except Exception:
        meta.set_status(doc_id, "failed")   # 检索层不返回 failed
        raise
```

`hash_of` 那一步是为了幂等。同一个版本重复触发索引时，哈希不变就直接跳过，避免把一份文档反复嵌入十几次。

## 变更捕获：轮询还是事件

知道哪些文档变了，有两种方式。事件驱动（webhook、消息队列、数据库变更日志）延迟低，但需要上游配合，而且事件丢失很难发现。轮询扫描则简单粗暴，按 `updated_at` 拉取增量。

一个基本的判断是：内部系统优先事件，外部不可控的数据源一律轮询加全量对账。对账这一步不能省，应当定期跑一次全量比对，用文档的修改时间与索引里记录的版本做差集，把漏掉的全部补上。没有对账的增量索引，半年后一定会出现"搜不到某篇明明存在的文档"这类问题，而排查它非常耗时。

轮询频率按语料的实际变更速率定。文档一天改几次，就没必要每分钟扫一次；反过来，工单类每天上千条更新，五分钟一次可能都不够，这时候该考虑的是分片和并发，而不是把间隔压到更短。还有一个隐性成本是嵌入调用：全量重建一次十万块的索引，按批量接口的价格算也是真金白银，这也是增量必须做对的经济理由。

## 权限：过滤必须发生在检索之前

这是公认最容易出事的一块。把权限过滤放在结果返回之后，等于先让无权文档占用了候选名额，再把它删掉，结果是前十里可能只剩三条。更糟的是，如果过滤逻辑写错，泄漏就是静默的。

正确做法是把权限条件下推到检索层。多数向量库支持带过滤条件的近似最近邻搜索，比如按 `tenant_id`、`acl_group` 做前置过滤。但要注意过滤的选择性：如果过滤后只剩很少的候选，近似检索的召回会明显下降，因为图索引的遍历路径被切断了。加上过滤后召回从零点九掉到零点五并不罕见，最后的解法往往是按租户分集合（collection），物理隔离，问题才消失。

```python
results = index.query(
    vector=q_emb,
    top_k=20,
    filter={"$and": [
        {"tenant_id": {"$eq": tenant}},
        {"acl_groups": {"$in": user_groups}},
        {"status": {"$eq": "active"}},
    ]},
    num_candidates=400,   # 过滤越强，候选要越大
)
```

`num_candidates` 与 `top_k` 的比例要随过滤强度调。经验值是四到十倍，权限条件多的时候还要往上加。

还有一个容易被忽略的层次：块级别的权限。文档级权限不够用时（比如一份合同里只有财务章节对销售可见），得在切分阶段就把可见范围写进块的元数据，而不是在文档级做判断再推导到块。这件事必须在切分时决定，事后补不回来。

## 更新与过期：让内容自己说话

知识库里最危险的不是没有答案，而是过时的答案听起来同样自信。常见的处理是给每条内容加生效与失效时间，检索时过滤掉已过期的块，并在上下文里保留时间戳，让模型知道资料的时点。

对于没有明确失效期的文档，用 `updated_at` 降权。具体做法是在融合排序的最后一步加一个小幅衰减，超过一年的内容分数按比例下调。幅度要小，否则会把那些长期有效的基础文档压下去。一个常用的取值是每年下调百分之五，这个数没有理论依据，纯粹是调出来的，够用即可。

版本冲突也要处理。同一主题存在新旧两份文档时，宁可只返回新的。一条常用规则是同一 `doc_id` 只保留最新版，不同 `doc_id` 但标题高度相似时，在提示词里显式标注"以下两份资料可能不一致，以更新时间较晚者为准"。这比让模型自己去猜要可靠。

## 这条链路上最容易做错的三件事

第一件是把索引当成可以随时全量重建的东西。语料小的时候重建只要几分钟，于是很容易忽略增量设计；等语料涨到几十万块之后，一次全量重建要几个小时，而这段时间索引是不可用的。解法是影子索引（shadow index）切换，代价是要维护两套别名指向，但终于能不停机更新。

第二件是低估了删除。用户删掉一份敏感文档后，向量还在索引里停留数天，虽然检索侧已经过滤，但严格来说数据还在。合规场景下这是不可接受的，所以删除必须是同步的、可验证的，最好每次都记一条审计日志。

第三件是把权限当成了接入层的活。在 API 层判断用户能不能看某篇文档、再过滤结果，这个设计在只有一种角色时没问题，一旦出现跨部门共享就崩了，因为"能看文档"和"能看文档的哪一部分"是两个不同的问题。权限模型要在切分时落地，这是最该坚持的一条。

这三个错误有一个共同点：都是在数据量小的时候看不出来，规模化之后才变成事故。如果重来一次，应当在一百份文档的规模上就把增量、删除、权限三件事按最终形态写对，而不是先跑通再说。
