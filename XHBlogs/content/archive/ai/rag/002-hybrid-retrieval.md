做检索的第一反应是上向量库：把文档嵌进去，把问题嵌进去，算余弦相似度，取前 k。这套流程在语义匹配上确实好用，问"怎么退钱"能召回"退款流程"，字面上没有任何重合。但它有一个很具体的失效面——当查询里带着一个必须精确命中的字符串时，稠密检索经常给出似是而非的结果。混合检索（hybrid retrieval）不是保险起见的多一路，而是针对这一类失效的补偿。

## 稠密向量擅长什么，不擅长什么

嵌入模型（embedding model）把文本压成一个定长向量，相似度反映的是语义分布上的接近。它对同义改写、跨语言、口语化提问都很宽容，代价是这个"宽容"本身：在向量空间里，`ERR_4012` 和 `ERR_4021` 的距离可能远小于它们与任何其他文本的距离，但它们的语义差异恰恰是全部关键信息。

经验上，稠密检索的失败集中在四类查询上：错误码与日志片段、产品型号与版本号、人名与机构缩写、以及极少出现在训练语料里的内部术语。这四类的共同点是"字符串本身就是答案的一部分"，语义泛化在这里是负资产。

## BM25 的排序逻辑

BM25 属于稀疏检索（sparse retrieval），基于词频与逆文档频率，但比朴素的 TF-IDF 多了两个修正，值得记一下公式：

```text
score(q, d) = Σ_t IDF(t) · [ f(t,d)·(k1+1) ] / [ f(t,d) + k1·(1 - b + b·|d|/avgdl) ]

IDF(t) = ln( 1 + (N - n_t + 0.5) / (n_t + 0.5) )
```

`k1` 控制词频饱和：一个词出现十次不该比出现一次重要十倍，`k1` 越大饱和越慢，常用值 1.2 到 2.0。`b` 控制长度归一化，`b=1` 时完全按文档长度惩罚，`b=0` 时完全不惩罚，常用 0.75。

中文场景有一个绕不开的前置问题：分词。用 `jieba` 这类词级分词器，词典外的专有名词会被切碎；另一种更省事的做法是只用字符二元组（character bigram），它天然覆盖任意未登录词，代价是索引膨胀、候选噪声变多。在陌生产品名和缩写很多的知识库里，bigram 往往更省心，词级分词的维护成本反而更高。

```python
import jieba
from rank_bm25 import BM25Okapi

def tokenize(text: str) -> list[str]:
    # 混合粒度：词级 + 字符二元组，兼顾未登录词
    words = [w for w in jieba.lcut(text) if w.strip()]
    chars = [text[i:i+2] for i in range(len(text) - 1)]
    return words + chars

corpus = [tokenize(d) for d in docs]
bm25 = BM25Okapi(corpus, k1=1.5, b=0.75)
scores = bm25.get_scores(tokenize("ERR_4012 怎么排查"))
```

`rank_bm25` 这个库默认的 IDF 是负值修正版本，用之前建议读一眼源码，确认它对高频词的处理符合预期——不同实现的 IDF 公式有差异，换库之后排序会变。

## 融合的两条路：分数归一化与 RRF

拿到两路结果之后要合并。最直觉的做法是把 BM25 分数归一化到零到一，再与余弦相似度加权求和：

```python
def normalize(scores: list[float]) -> list[float]:
    lo, hi = min(scores), max(scores)
    return [(s - lo) / (hi - lo) if hi > lo else 0.0 for s in scores]
```

这条路的问题在于分数分布不稳定。BM25 的分数没有上界，随查询长度和语料规模漂移；余弦相似度则高度集中在零点七到零点九这个窄区间，稍微归一化就放大成噪声。同一个权重，在不同查询上的效果可能完全相反。

更稳的是倒数排名融合（reciprocal rank fusion，RRF）：

```python
def rrf(rank_lists: list[list[str]], k: int = 60) -> dict[str, float]:
    fused: dict[str, float] = {}
    for ranks in rank_lists:
        for i, doc_id in enumerate(ranks):
            fused[doc_id] = fused.get(doc_id, 0.0) + 1.0 / (k + i + 1)
    return dict(sorted(fused.items(), key=lambda x: -x[1]))
```

它只用排名不用分数，天然免疫量纲问题，`k=60` 是原论文的经验值。一个常见的默认选择就是 RRF，只有在确定要压某一路的权重时才退回归一化加权。

| 融合方式 | 依据 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 归一化加权 | 分数 | 可细调权重 | 分布漂移，需按查询类型调 |
| RRF | 排名 | 无需调参、稳定 | 丢失分数差距信息 |
| 学习排序 | 特征 | 上限最高 | 需要标注数据与训练 |

## 权重不该是一个常数

如果坚持用加权，至少把权重做成查询的函数。一种粗分类规则是：查询里含大写字母、数字、下划线连续串，或与知识库词表的重合度很低，就把 BM25 权重往上抬；查询是自然语言长句、含疑问词，就偏向向量。

还有一个更便宜的信号：看两路结果的交集。交集为空时说明查询可能落在词表外，此时提高 BM25 权重往往立刻见效；交集很大时，两路已经一致，融合方式影响不大。

要注意的是，混合检索并不能修复切分问题。如果块切得稀碎，BM25 反而更糟——短文档的长度归一化会让它虚高。混合检索的前提是块本身是完整的语义单元。

另一个实践细节是查询改写（query rewriting）。用户输入的长句里往往混着寒暄和上下文指代，直接拿去算 BM25 会引入大量无关词。常见的做法是先用规则或小模型把查询压缩成关键词串再喂给 BM25，向量路仍然用原句，让两路各取所长。这一步在客服类场景里提升明显，因为那里的提问常带着"想问一下那个……"之类的填充。但要节制：改写过度会丢掉限定词，比如"安卓端的退款"被压成"退款"，精确性反而下降。

## 实现顺序与常见问题

推荐的落地顺序是：先只上 BM25，把召回基线量出来；再加向量路，用 RRF 融合；最后才考虑交叉编码器（cross-encoder）重排。这个顺序的理由是每一步都能单独验证收益，混在一起改就分不清是谁的功劳。

有两个坑值得提。其一是在 Elasticsearch 里做 kNN 与 BM25 混合，需要注意 `num_candidates` 要显著大于 `k`，否则近似最近邻（approximate nearest neighbor，ANN）召回不足，融合的上限被卡死在候选集里。其二是过滤条件的位置：先过滤再检索和先检索再过滤，在带权限的场景下结果完全不同，后者会让本该无权访问的文档占据候选名额。

最后一句结论：BM25 之所以还活着，不是因为它比向量"更准"，而是因为它对精确字符串的敏感是结构性的，不依赖训练数据里有没有见过这个词。把两路拼起来，成本是索引要维护两份、查询要多发一次，收益是那批"向量永远答不对"的问题终于能被答对。这笔账在实践中一直是划算的。
