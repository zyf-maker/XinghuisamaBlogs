结论先放前面：日请求量在十万级以下，自己起推理服务一定比调 API 贵。我算过两次，第一次算错了，把 GPU 租赁费除以理论峰值吞吐，得出「日三万请求就能回本」的结论，上线后实际吞吐只有估算的四成，账单翻了一倍多。

## 显存怎么估，别拍脑袋

权重部分最好算：FP8 每十亿参数占 1 GB，BF16 占 2 GB。一个 671B 的 MoE 模型，FP8 权重就是 671 GB 左右，得跨八张 96 GB 卡才放得下，还得留出激活和通信缓冲。

真正吃显存的是 KV cache，公式是 `2 × 层数 × KV 头数 × head_dim × 序列长度 × 并发数 × 每元素字节`。这个 2 是 K 和 V 各一份。注意 KV 头数不等于注意力头数，GQA 模型里前者往往只有后者的几分之一，拿错参数会把估算放大四到八倍。

```python
def kv_cache_gb(layers: int, kv_heads: int, head_dim: int,
                seq_len: int, batch: int, bytes_per_elem: int = 2) -> float:
    """单卡 KV cache 占用，单位 GB。按张量并行切分时把结果除以卡数。"""
    per_token = 2 * layers * kv_heads * head_dim * bytes_per_elem
    total = per_token * seq_len * batch
    return total / (1024 ** 3)

print(round(kv_cache_gb(61, 8, 128, 8192, 1), 1))    # 单条约 1.9 GB
print(round(kv_cache_gb(61, 8, 128, 8192, 32), 1))   # 8K 上下文 32 并发约 61.0 GB，吃掉大半张 80G 卡
print(round(kv_cache_gb(61, 8, 128, 32768, 32), 1))  # 32K 上下文同样并发约 244.0 GB，只能把 batch 砍到 8
```

这就是我第一版算错的地方：只算了 8K 上下文，实际业务里有三成请求超过 32K，那部分把 cache 撑到四倍，连续批处理直接降级成串行。现在我会按 P95 上下文长度而不是平均值来定显存预算。

## 吞吐和并发不是一回事

单请求延迟由 decode 速度决定，服务总吞吐由 batch 内 token 总数决定。这两个数在一个区间内可以同时提升，超过拐点就互相挤。

我实测的那台八卡机器，单条流式输出大约 60 到 90 token/s，用户感知很好。但把并发从 8 提到 64，单条速度掉到 25 token/s，总吞吐从约 600 token/s 涨到 1600 token/s，再往上加并发，总吞吐只涨一成，单条速度继续掉。

规划容量要用总吞吐，不是单条速度乘并发。保守取 1500 输出 token/s，一条请求平均输出 600 token，就是 2.5 请求/s，日上限约 21.6 万次。这是满负载理论值，实际按 60% 利用率打折，落到 13 万次左右。所有对外承诺的容量都该按打折后的数报。

| 观察项 | 并发 8 | 并发 32 | 并发 64 | 并发 128 |
| --- | --- | --- | --- | --- |
| 单条输出速度（token/s） | 85 | 45 | 25 | 14 |
| 总输出吞吐（token/s） | 680 | 1440 | 1600 | 1790 |
| 首 token 延迟（ms） | 320 | 780 | 1900 | 4200 |
| 结论 | 单条快、浪费机器 | 甜点区 | 吞吐见顶 | 延迟不可接受 |

甜点区在 32 并发附近。低于它机器闲，高于它用户等。这条曲线跟硬件、量化精度、模型结构都有关，必须在自己机器上重测一遍，别人的数字搬过来只能当量级参考。

## 闲置成本是最容易被忽略的一笔

自托管的账单不随流量变化。凌晨三点没有请求，GPU 照样按小时计费，机房照样收电费。业务有明显波峰波谷时，这个错配会放大成本。白天按峰值备的机器，夜里空转八小时，等于每天白付三分之一。

API 在这个维度上的优势不是单价低，是它能被切成按秒计费。我的业务峰谷比大概是 3.2 比 1，按峰值备自托管机器，等于为 69% 的闲置时间付钱。

还有一笔隐性成本：模型更新。API 侧换版本是改一个字符串，自托管要重新下载权重、重跑评测、调 batch 参数、观察一周。这套流程走一遍，两个人至少三天。一年换三次版本，就是十八个人日。

## 按日请求量摊开算

假设单请求输入 1200 token、输出 600 token，输入有八成命中上下文缓存；API 那一列按 flash 的高峰单价折算，具体价格以官方文档为准。自托管按八卡 96 GB 机器、租赁价估算 25 元每小时折算，另加一名兼职运维的人力折算。所有数字都是估算，用于比量级，不能当报价。

| 日请求量 | API 月成本（估算） | 自托管月成本（估算） | 差额 | 判断 |
| --- | --- | --- | --- | --- |
| 1 千 | 约 160 元 | 约 2.1 万元 | 差 130 倍 | 自托管毫无意义 |
| 1 万 | 约 1600 元 | 约 2.1 万元 | 差 13 倍 | 自托管毫无意义 |
| 5 万 | 约 8000 元 | 约 2.1 万元 | 差 2.6 倍 | 仍有明显劣势 |
| 10 万 | 约 1.6 万元 | 约 2.1 万元 | 差 1.3 倍 | 单机刚好装下 |
| 20 万 | 约 3.2 万元 | 约 3.9 万元 | 差 1.2 倍 | 两台，仍不如 API |
| 40 万 | 约 6.4 万元 | 约 7.5 万元 | 差 1.16 倍 | 四台，已经很接近 |
| 60 万 | 约 9.6 万元 | 约 9.3 万元 | 基本持平 | 五台，临界区 |

表里的自托管阶梯是这样来的：单机租赁 25 元每小时，按 730 小时折算约 1.8 万元，摊上兼职运维再算 0.3 万元，合计 2.1 万元一台。容量上单机按 1500 输出 token/s、每条 600 token 算，理论 2.5 请求/s，即 21.6 万次/日，再按 60% 利用率打折，落到 13 万次/日。所以 10 万还在单机内，20 万要两台合计 3.9 万元，40 万要四台合计 7.5 万元，60 万要五台合计 9.3 万元。流量每跨一个台阶，账单跳 1.8 万元，而 API 那列是按用量线性爬的。

表里的 API 成本按固定单价线性外推，真实账单不会这么听话：命中率会随前缀改动下降，输出长度会随任务漂移，高峰与空闲时段的单价也不同。

盈亏平衡点在日请求量五十万到六十万之间。低于它，API 便宜且省心；高于它，自托管的边际成本才开始下降。这个数字看着比直觉高，原因是 flash 这类模型的 API 单价压得很低，自托管的固定成本没地方摊。换 pro 口径重算，同样一台机器能替掉的日请求量掉到四万左右，平衡点整个往前挪了一个数量级。上一版我按理论峰值吞吐算，把 flash 的平衡点压到了十万，实际跑出来差了三倍，这是这篇里最该记住的一次误判。

## 什么情况下这个账算不通

有三类场景会让上面的比较失效。数据不能出网就不比较成本，直接自托管，但要把人力算进预算，别只报机器钱。延迟要求高到首 token 必须 200 毫秒以内时，自托管的局域网优势比省钱更重要。请求极度稀疏、一天几百次且集中在某个时段，按需租卡用完释放，比包月合适。

我最终的方案是混合：日常流量走 API，批量离线任务（每天几百万 token 的清洗和标注）走自托管，夜里跑满，白天关机。两边的账分开算，谁也没拖累谁。
