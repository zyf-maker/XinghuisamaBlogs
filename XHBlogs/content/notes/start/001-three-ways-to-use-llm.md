第一次用大模型的人最容易犯的错，是把三条完全不同的路当成同一件事的三个难度档。网页界面、API 调用、本地部署，它们解决的不是同一个问题。界面的核心价值是「马上能用」，API 的核心价值是「可以批量、可以嵌进程序」，本地的核心价值是「数据不出机器」。选错了路，后面所有麻烦都是自找的。

## 先用三个问题定位自己

第一个问题：这些数据能不能离开你的电脑。论文草稿、实验数据、公司代码，很多时候答案是「不能」，那 API 这条路直接划掉，讨论到此为止。

第二个问题：一天要调多少次。十次以内，界面点一点比写脚本快；上百次，手点就开始烦了；上千次，必须走 API。

第三个问题：要不要可复现。同一个 prompt 今天和下周给出不同结果，是因为模型版本换了，还是因为温度不同，界面不会告诉你。需要写报告、需要对比实验的时候，这一点很致命。

## 界面：五分钟能用，但你不知道发生了什么

订阅制的网页版，主流厂商定价在每月 20 美元上下。它的好处被严重低估：文件上传、图片理解、联网检索、代码执行，这些能力在界面里是默认开着的，接到 API 里要自己一个个拼。做探索性工作时，界面的效率仍然最高。

代价是黑箱。你看不到这次对话吃了多少 token，不知道上下文什么时候被悄悄截断，也拿不到稳定的版本号。我曾经用界面整理过一份参考文献，改到第二十几轮时它开始忘记前面的约束，回头检查才发现早就超出窗口，最前面的指令被裁掉了。界面上没有任何提示。

界面适合学习、适合一次性任务、适合验证一个想法值不值得做。不适合当生产依赖。

## API：按量计费，工程化的起点

现在几乎所有厂商都提供 OpenAI 兼容接口，换厂商通常只改 `base_url` 和 `model` 两个字段。这是这几年最省事的一件事。

先跑通最小的一步。用 `curl` 确认网络和密钥没问题，再写代码：

```bash
curl -s http://127.0.0.1:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $API_KEY" \
  -d '{
    "model": "qwen2.5:7b-instruct",
    "messages": [{"role": "user", "content": "用一句话说明什么是 embedding"}],
    "temperature": 0.2,
    "max_tokens": 200
  }'
```

返回的 `usage` 字段里有 `prompt_tokens`、`completion_tokens`、`total_tokens`，这三个数字才是一切成本讨论的基础。看不到 usage 的调用方式，不要用在批量任务里。

成本量级要有直觉。假设输入 2 元每百万 token、输出 8 元每百万 token，一篇 3000 字的中文技术文档大约 4500 输入 token，单篇成本不到一分钱。真正烧钱的是三件事：反复重试、把整份文档塞进上下文、以及输出不限长度。

并发是另一个坑。多数厂商默认给每分钟几百次请求、每分钟若干万 token 的额度，超了返回 429，响应头里有 `retry-after` 告诉你等几秒。不读这个头、直接用固定 1 秒间隔重试，只会把限流窗口一直续上。正确的做法是读 `retry-after`，再加指数退避和随机抖动。

```python
import random, time
import httpx

def chat(payload, key, url="http://127.0.0.1:11434/v1/chat/completions", tries=5):
    headers = {"Authorization": f"Bearer {key}"}
    for i in range(tries):
        r = httpx.post(url, json=payload, headers=headers, timeout=60)
        if r.status_code == 200:
            return r.json()
        if r.status_code == 429 or r.status_code >= 500:
            wait = float(r.headers.get("retry-after", 2 ** i))
            time.sleep(wait + random.uniform(0, 0.5))
            continue
        r.raise_for_status()
    raise RuntimeError("重试次数用尽")
```

这段代码里最关键的不是重试次数，是「只对 429 和 5xx 重试」。400 类错误重试一万次也不会成功，只会让你在日志里找不到真正的原因。

## 本地：权重在你手里，代价也在你手里

本地的入门门槛已经被拉得很低。装好 Ollama，一条命令就能跑：

```bash
ollama pull qwen2.5:7b-instruct
ollama run qwen2.5:7b-instruct
```

难的不是跑起来，是跑得动。显存要按两块钱算：模型权重和 KV cache。

权重这部分好估。7B 参数用 Q4_K_M 量化，每个参数大约 0.55 字节，加上量化表和元数据，磁盘占用 4.4 GB 左右，加载进显存也差不多这个量级。

KV cache 经常被忽略，但它随上下文长度线性增长。粗算公式是 2（K 和 V）× 层数 × 隐藏维度 × 序列长度 × 每元素字节数。7B 模型 32 层、隐藏维度 4096，用 fp16 存 KV，上下文开到 8192 时，这部分大约 4 GB。也就是说 8 GB 显存的卡，跑 7B Q4 只够开到 4k 上下文，再多就要往内存里换，速度断崖式下降。

这个断崖我踩过。8 GB 卡上跑 7B，把上下文从 4096 调到 8192，生成速度从每秒 30 个 token 掉到每秒 2 个，`ollama ps` 里能看到模型被标成了部分加载到 CPU。不是模型变笨了，是每一层都要在显存和内存之间搬数据。

## 三条路的对照

| 维度 | 网页界面 | API | 本地部署 |
| --- | --- | --- | --- |
| 上手时间 | 5 分钟 | 30 分钟 | 1 到 3 小时 |
| 计费方式 | 月订阅 20 美元级 | 按 token，百万级起算 | 一次性硬件投入 |
| 数据去向 | 厂商服务器 | 厂商服务器 | 不出机器 |
| 可批量 | 不能 | 能 | 能，受吞吐限制 |
| 版本稳定 | 随时可能变 | 有版本号可锁定 | 完全可控 |
| 典型上限 | 单轮对话 | 每分钟请求数 | 显存与上下文长度 |

## 我的实际组合

草稿和脱敏在本地做。要处理的材料先过一遍本地 7B 模型，把姓名、单位、项目代号替换掉，再送出去。这一步用不上最强的模型，7B 足够。

正式生成走 API。需要结构化输出的时候（比如统一格式的实验记录），API 能锁 `temperature=0`，能要求 JSON schema，能记录每次的 usage，这些在界面里做不到。

界面留给探索。想验证一个新模型值不值得接进流程、想试一个没见过的任务形态，先用界面对话几轮，比写脚本快得多。

三条路不是替代关系，是分工。新手最容易卡住的地方，是拿界面的体验去想象 API 的稳定性，或者反过来，一上来就折腾本地部署，三天没跑通就放弃了。先问那三个问题，答案会自己指向一条路。
