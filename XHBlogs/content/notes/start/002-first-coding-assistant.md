装一个编程助手只要五分钟，让它改对第一处代码需要一整个下午。差别不在工具，在于你有没有把「上下文」这件事做对。下面是我带人过这一关时反复用的顺序，从安装一路到第一处能提交的改动。

## 先决定用哪一类

目前分两类，选错会浪费很多时间。

编辑器内嵌型，在 VS Code 这类编辑器里以插件形式存在，改动用内联 diff 展示，你逐块接受或拒绝。它适合已经在编辑器里工作、写的又是中小规模文件的人。

命令行代理型，在终端里跑，能自己读文件、搜代码、执行命令、跑测试。它适合不熟悉某个仓库、要从零摸清结构、或者要做跨多文件的机械改动。

我的判断标准很简单：改动涉及超过 3 个文件，用命令行代理；只改一个函数，用编辑器内嵌。这个界限不是绝对的，但能挡掉大部分「用错工具然后觉得不好用」的情况。

## 安装与第一道坎：让它能看见仓库

以命令行为例，Node 版本先确认。绝大多数工具要求 Node 20 以上，用 `node -v` 看一眼，低版本会装出一个能启动但行为古怪的东西。

```bash
node -v                 # 需要 >= 20
npm i -g @anthropic-ai/claude-code   # 具体包名以官方文档为准
cd /path/to/project
git status              # 先确认工作区干净
```

最后那步 `git status` 不是形式。助手会改文件，工作区不干净的时候，你分不清哪些改动是自己的、哪些是它写的。我习惯在开始前跑一次 `git add -A && git commit -m "wip"`，哪怕只留个本地提交，回滚成本就变成一条命令。

第一道坎通常在这里出现：助手读不到文件。原因大多是启动目录不对。它在当前目录下搜索，`cd` 错了层级，它看到的世界就是错的。启动前 `pwd` 确认一下，比事后调试半小时划算。

## 第二道坎：上下文不是越多越好

新手最容易做的动作，是把整个仓库丢进去。这会立刻撞上两个问题：token 超限，以及注意力被稀释。

一个中型前端项目，`node_modules` 加上构建产物动辄几十万行。就算工具会自动忽略 `.gitignore` 里的东西，剩下几千个源文件也远超窗口。模型在读第 200 个文件时，对你第一句话的注意力已经很弱了。

正确做法是先给它一张地图，而不是整本书。通常在仓库根目录放一个说明文件，多数工具会自动读取，名字各厂商不同，作用一样：

```markdown
项目说明

### 技术栈
Next.js 16（App Router）+ TypeScript + Tailwind

### 目录
- app/          路由与页面
- lib/db.ts     数据库访问，唯一入口，不要绕过
- components/   无业务逻辑的展示组件

### 约定
- 不要在组件里直接 fetch，统一走 lib/api.ts
- 所有对外接口必须处理 401 与 429
- 提交前跑 `npm run lint && npm run typecheck`
```

这份文件写 20 行，比丢 200 个文件有用。它省下的不只是 token，还有你反复解释「这个项目为什么要这么写」的时间。

## 第三道坎：第一处改动要小到荒谬

第一次让助手改代码，选一个「改错了也不心疼」的目标。加一个参数校验、补一条日志、修一个错别字级别的 bug，都行。

我给的标准是：预期 diff 不超过 20 行，涉及文件不超过 2 个。

先让它读，再让它改。这两步分开下指令：

```bash
## 第一步，只读
请阅读 lib/api.ts 和 app/settings/page.tsx，说明设置页保存时调用了哪个函数，
参数如何组装。不要修改任何文件。

## 第二步，限定范围的改动
在 lib/api.ts 的 saveSettings 里，给 timeout 加校验：
非数字或小于 1000 时抛出 Error，消息为 "timeout must be >= 1000"。
只改这一个函数，不要动其他代码。
```

「只改这一个函数，不要动其他代码」这句话必须写。不写的话，它会顺手把旁边的 `console.log` 删掉、把 `var` 改成 `const`、把两处无关的空行整理掉。这些改动单看都是对的，混在你的 diff 里就是噪音，review 的时候你得逐行分辨哪些是本次要的。

## 第四道坎：读懂 diff，而不是点接受

内联 diff 或终端里的 patch，接受之前至少看三件事。

看边界。改动是不是落在你指定的函数里。落在外面，说明它没读懂范围。

看删除行。新增行容易看出问题，删除行才危险。少了一个 `return`、少了一个 `await`、少了一层判空，编译能过，运行时才炸。

看它有没有偷偷加依赖。一个简单需求却引入新包，通常意味着它没找到项目里已有的工具函数。这类改动会让 `package-lock.json` 多出几百行，回滚的时候很烦。

有个具体的例子。我让人加一个「保存成功提示」，它引入了三个包做 toast，而项目里 `components/ui/toast.tsx` 早就有现成的。这不是它笨，是我没在说明文件里写「UI 组件统一从 components/ui 引入」。上下文缺失的代价，最后都变成 diff 里的噪音。

## 第五道坎：验证闭环

改完必须跑验证，而且要在同一个回合里跑完。

```bash
npm run typecheck   # tsc --noEmit
npm run lint
npm run test -- --run
```

TypeScript 项目里 `typecheck` 是第一道筛子，它抓的是签名不匹配、可选值没处理这类问题。lint 抓未使用变量和格式。测试抓行为。

三者都过，再看一眼 `git diff --stat`。行数和你预期差得远，就说明它做了额外的事，回去看具体改了什么。

## 几个参数和取舍

不同工具的叫法不一样，但核心就那么几个开关。下面这张表是我在几个工具之间来回切换后整理的对应关系，具体键名以各工具文档为准。

| 能力 | 作用 | 什么时候调 |
| --- | --- | --- |
| 自动接受编辑 | 跳过逐块确认 | 只在你已经用测试兜底时开 |
| 允许执行命令 | 让它跑测试和构建 | 需要闭环验证时开，其余关掉 |
| 模型档位 | 强模型贵且慢，弱模型快但易错 | 读代码用弱，改代码用强 |
| 上下文范围 | 全仓库检索 vs 仅当前文件 | 摸结构时全仓库，改细节时单文件 |
| 最大轮次 | 单次任务允许的自动步数 | 起步设 5 到 10，防止它自己绕圈 |

最后一条值得单说。不加限制的自动模式，遇到一个它解不了的错误时会反复尝试，每一步都在烧 token，而且越试越偏。设一个轮次上限，超了就停下来问你，比让它自己撞墙便宜。

## 什么时候该放弃让它改

有三种情况我会立刻切回手写。

一是它连续两次改错同一个地方。这说明它对这块代码的理解是错的，继续对话只会让它在这个错误理解上叠加补丁。

二是改动涉及并发、事务边界、缓存失效这类正确性推理。它能写出看起来对的代码，但边界条件经常漏。

三是报错信息本身指向环境问题。缺依赖、端口占用、版本冲突，这些不是代码问题，让它猜只会得到一堆 `try/except`。

工具的价值在于把机械劳动压缩掉，不在于替你做判断。第一处改动小到荒谬，正是为了让你在低成本的情况下，看清它的判断边界在哪里。
