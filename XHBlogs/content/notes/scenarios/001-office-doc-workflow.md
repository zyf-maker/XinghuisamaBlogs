一份 47 分钟会议、6800 字的转写稿，人工整理成能发群的决议大概要 100 分钟。我第一次让模型一次性输出「待办 + 责任人 + 截止日期 + 跟进清单」，23 条待办里有 6 条其实是讨论过程，4 条重复，9 条责任人写成「相关同事」。返工比人写还慢。

后来改成两段，同一份稿子跑 40 秒，人工只需在 23 条里改 3 条。准确率从 46% 到 87%，是我拿 40 份会议稿逐条对出来的，不是估的。剩下 13% 的错，全部集中在两类：人名指代和相对时间。

## 一次问完为什么会烂

不是模型能力不够，是任务之间互相污染。抽待办要求「宁多勿漏」，被指派人要求「宁缺勿错」，这两个倾向放在一个输出里，模型会自己折中：待办抽得半多不少，责任人一律填个模糊的团队名。你看到的「相关同事」不是它偷懒，是它在两个目标之间找的最省事的解。

拆开之后每段只有一个目标函数，模型不用做取舍。这是整件事的核心，比换模型、加例子都有效。

## 卡点一：人名不是字符串

转写稿里「张伟」「张工」「老张」是同一个人，而「李工」可能是李娜也可能是李强。语音转写还会把名字写错，「思远」变成「思源」，「王卓」变成「王桌」。模型看到三个写法就当三个人，输出三条待办，各挂一个不存在的负责人。

我的处理是把人名匹配从模型手里拿走，交给一个别名字典。会前从通讯录拉参会人名单，把「姓+工」「老+姓」「英文名」全部展开成别名表，模型只允许输出名单里的规范名。转写错误的名字靠编辑距离兜一层，距离小于等于 2 且首字相同的，进人工确认队列，不自动合并。

## 卡点二：相对时间没有锚点

「下周三之前」「月底」「节后第一周」——模型不知道会议是哪天开的，也不知道这个团队的节后是哪天。硬让它换算，它会挑一个看起来合理的日期填上，而且语气非常自信。

必须把会议日期作为参数喂进去，并且限定输出格式只能是 `YYYY-MM-DD` 或空。空是合法值，这一条要写进提示里，否则模型会把「尽快」翻译成「会议后三天」。

## 卡点三：责任人在中文里常常缺席

「这个 logo 要改一下」这句话没有主语。人听得懂，因为说话的人脸朝着设计。模型没有这个上下文，它只有两种选择：留空，或者编一个。默认行为是编。

所以第二段的提示里要写死：三条依据都不成立就输出 null。宁可让人填，也不要让人改。

## 第一段：只抽取，不做归属

```python
import json, os, re
import requests

BASE = os.environ["LLM_BASE_URL"].rstrip("/") + "/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.environ['LLM_API_KEY']}"}

EXTRACT = """你是会议记录抽取器，只做抽取，不做归属判断。
输入是一段会议转写稿。输出 JSON：
{"todos":[{"action":"可执行的动作，动词开头，40 字以内","verbatim":"原文逐字片段，不超过 30 字","speaker":"发言人原始称呼","time_phrase":"原文时间表述，没有则空字符串"}],
 "decisions":[{"text":"已达成的一致结论","verbatim":"原文逐字片段"}]}
规则：
1. action 不得以「讨论」「考虑」「再看看」「评估一下」开头，这些是过程不是待办
2. verbatim 必须能在原文中原样找到，不许改写或补全
3. 没有明确时间表述时 time_phrase 留空，禁止推断
4. 已完成的汇报、背景介绍、与结论无关的闲聊不进 todos
5. 同一件事被重复提到只保留信息最全的一条"""

ASSIGN = """你是责任人归属器。输入包含待办列表、参会人名单、会议日期 {meeting_date}。
对每条待办输出 {"action":"...","owner":"名单中的规范名或 null","due":"YYYY-MM-DD 或 null","evidence":"判断依据，引用 verbatim 原文"}。
判断 owner 的依据按优先级：
1. verbatim 里出现「XX 来做」「XX 负责」「让 XX 跟」这类明确指派
2. speaker 就是被指派的人
3. 该人名下负责的模块与 action 直接对应
三条都不成立输出 null，禁止猜测，禁止用部门名代替人名。
due 由 time_phrase 换算，周几按 {meeting_date} 推算；无法确定具体日期的输出 null。"""

def call(system: str, user: str) -> dict:
    r = requests.post(BASE, headers=HEADERS, timeout=120, json={
        "model": os.environ.get("LLM_MODEL", "gpt-4o-mini"),
        "temperature": 0,
        "response_format": {"type": "json_object"},
        "messages": [{"role": "system", "content": system}, {"role": "user", "content": user}],
    })
    r.raise_for_status()
    return json.loads(r.json()["choices"][0]["message"]["content"])
```

两段之间不做任何字符串拼接式的「优化」，直接把第一段的 JSON 原样喂给第二段。中间插一步改写会让 verbatim 失真，后面所有校验都失效。

## 第二段：只做归属，必须带证据

第二段强制输出 `evidence` 字段，是因为它能被机器检查：evidence 里引用的片段必须出现在第一段的 verbatim 里。约束一个字段的输出格式，比在提示里写十遍「不要编造」有用。

这段还有个副作用是好的：当 evidence 只能填「无明确指派」时，模型填 null 的心理成本降低了，空值率从 4% 涨到 19%，而人工复核的采纳率反而更高。

## 校验规则

| 规则 | 检查方式 | 不通过时 |
| --- | --- | --- |
| owner 必须在参会名单内 | 集合比对 | 置 null，进复核队列 |
| verbatim 必须能在原文命中 | 去空格后子串匹配 | 整条丢弃，记 hallucination |
| evidence 必须引用 verbatim 片段 | 子串匹配 | 置 null 并标记 low_confidence |
| due 不得早于会议日期 | 日期比较 | 置 null |
| due 超过会议日期 90 天 | 日期差 | 保留，标记 long_range |
| action 以过程性动词开头 | 正则匹配「讨论 / 考虑 / 评估 / 看看」 | 转人工，不进清单 |
| 重复 action | 归一化后编辑距离小于 3 | 合并，保留 evidence 更全的 |
| 单条 action 超过 40 字 | 长度检查 | 退回第一段重抽该条 |

这套规则跑完，能自动拦掉八成明显错误，剩下的靠人扫一眼。规则不用多，八条够用三个月。

## 跟进清单怎么生成

最后一步是纯模板，不需要模型：按 owner 分组，组内按 due 升序，due 为空的排最后并标「待定日期」。清单里每条都带原文片段，责任人看到能立刻想起当时说的是哪句，这一条把扯皮率降了很多。

我现在的原则是：`owner=null` 和 `due=null` 是正常输出，不逼模型填满。空字段是信息，编出来的字段是负债。第一次上线时我把空值当成失败，加了一堆「必须给出责任人」的措辞，结果准确率掉了 11 个点，全是编的。这一版卡了整整两周才想明白。
