一周 12 篇技术长文的产能，一个人做不到。纯模型也做不到：第一版全自动跑了三周，出了 36 篇，发布 9 篇，剩下 27 篇卡在事实错误和「读起来像没人写过这件事」。后来把工序拆细，在四个位置插人工卡点，产能落到一周 14 篇，但发布率到 92%，返工时间从每篇 3 小时降到 40 分钟。

关键不是让模型少干，是让它干错的成本足够低。一道工序的价值取决于两个数：它的输出错了之后，下游要花多少时间发现。选题错了，整篇白写；标点错了，没人管。所有人力应该压在发现成本高的那几道。

## 七道工序的分工

| 工序 | 谁做 | 输入 | 输出 | 卡点 | 错了的代价 |
| --- | --- | --- | --- | --- | --- |
| 选题 | 人定方向，模型扩候选 | 读者问题库、搜索词 | 20 个候选，人留 5 个 | 人工确认 | 整篇作废 |
| 提纲 | 模型 | 选题一句话 | 三级标题、每节要点 | 无 | 中，可在初稿阶段救 |
| 初稿 | 模型 | 提纲 + 指定素材 | 2500 字草稿 | 无 | 低，本来就要重写 |
| 事实核查 | 机器筛 + 人定夺 | 初稿 | 待核清单 + 判定 | 人工确认 | 最高，错一个数就失信 |
| 改写 | 模型 + 人润色 | 核过的稿 | 终稿 | 人工通读 | 中 |
| 标题与摘要 | 模型出 10 个，人选 1 个 | 终稿 | 标题、摘要 | 人工确认 | 高，影响点击 |
| 发布与回填 | 脚本 | 终稿 | 上线文件、索引 | 无 | 低，可回滚 |

九个工时里人占 5.5、模型占 3.5。模型那 3.5 个工时 12 分钟跑完，人的 5.5 个工时散在四个卡点，每次只要 10 到 15 分钟连续注意力。收益不是省人，是把注意力切成小块，能塞进任何空隙。

## 选题不能交给模型的原因

模型擅长在给定方向上扩写，不擅长判断「这个问题值不值得写」。让它出选题，会产出结构工整、覆盖全面、但没有一个人真的在搜的题目。我让它读 200 条读者提问然后出选题，前 20 个里 17 个是「XX 是什么」「XX 入门指南」，搜了也记不住。

有效的做法是人工从提问库里挑有摩擦感的问题：「为什么我的向量检索召回率一直是 0.3」「为什么同样参数在 A 卡上快三倍」。这类问题的共同点是有具体数字、有具体失败、提问的人已经试过。人挑 5 个，模型各自扩 4 个变体，人再留 5 个。20 分钟，决定后面所有工序有没有意义。

## 提纲和初稿：可以粗，但要给素材

提纲阶段最容易犯的错是让模型自由发挥。它会给一个正确的、平庸的骨架，然后初稿照着骨架填正确、平庸的内容。解法是把素材前置：写提纲时就把相关的日志片段、报错原文、实测数字作为附件给进去，让它围绕真实材料组织章节，而不是先想章节再找材料。

初稿的质量上限由输入材料决定，不由提示词决定。这一条我验证过很多次：同一份提纲，只给标题，初稿 2200 字全是通用描述；给三份实测日志和两个报错栈，初稿能写出「这一版卡在 32 并发之后延迟翻倍」这种句子。

初稿允许它有结构问题、有重复、有语气不一致。这些在后面改写阶段修，成本很低。唯一不能容忍的是它编造数字，所以初稿提示里必须写死：不确定的具体数值写成 `TODO_NUM`，不许填一个看起来合理的。

## 事实核查是唯一不能省的卡点

`TODO_NUM` 这个约定救了我很多次。初稿里凡是出现 `TODO_NUM`、`TODO_DATE`、`TODO_SOURCE` 的位置，都是模型自己知道不该硬编的地方。这三个标记的数量是质量的先行指标：一篇 2500 字的稿子如果超过 12 个标记，说明素材不够，直接退回补材料，不要往下走。

机器能做的核查只有三类：数字在素材里出现过、代码块能跑、链接域名在白名单内。剩下的判断必须人做。下面这段脚本把前两类自动化，跑在初稿上，输出待核清单。

```python
import re, subprocess, sys, tempfile, pathlib

NUM = re.compile(r"\d+(?:\.\d+)?\s*(?:%|倍|ms|s|万|次|条|篇|GB|MB)")
# 允许被模型标为待定的占位
PLACEHOLDER = re.compile(r"TODO_(?:NUM|DATE|SOURCE)")

def check_numbers(draft: str, sources: list[str]) -> list[tuple[str, bool]]:
    corpus = "\n".join(sources).replace(" ", "")
    out = []
    for m in NUM.finditer(draft):
        token = m.group(0).replace(" ", "")
        out.append((m.group(0), token in corpus))
    return out

def check_code_blocks(draft: str) -> list[tuple[str, int, str]]:
    fence = chr(96) * 3
    pattern = re.escape(fence) + r"python\n(.*?)" + re.escape(fence)
    results = []
    for block in re.findall(pattern, draft, re.S):
        with tempfile.NamedTemporaryFile("w", suffix=".py", delete=False, encoding="utf-8") as f:
            f.write(block)
            path = f.name
        proc = subprocess.run([sys.executable, "-c", f"compile(open(r'{path}',encoding='utf-8').read(),'{path}','exec')"],
                              capture_output=True, text=True, timeout=30)
        results.append((path, proc.returncode, proc.stderr.strip().splitlines()[-1] if proc.returncode else ""))
    return results

def main(draft_path: str, source_dir: str) -> int:
    draft = pathlib.Path(draft_path).read_text(encoding="utf-8")
    sources = [p.read_text(encoding="utf-8") for p in pathlib.Path(source_dir).glob("*.txt")]
    numbers = check_numbers(draft, sources)
    unverified = [(t, ok) for t, ok in numbers if not ok]
    placeholders = len(PLACEHOLDER.findall(draft))
    code = check_code_blocks(draft)

    print(f"数字总数 {len(numbers)}，素材中未命中 {len(unverified)}")
    for token, _ in unverified:
        print(f"  待核: {token}")
    print(f"占位标记 {placeholders} 个" + ("（超过 12，退回补素材）" if placeholders > 12 else ""))
    for path, rc, err in code:
        if rc:
            print(f"  代码块语法失败: {path} -> {err}")
    return 1 if unverified or placeholders > 12 or any(rc for _, rc, _ in code) else 0

if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1], sys.argv[2]))
```

`check_numbers` 只比对字符串是否在素材里出现，不等于数字被正确使用。「32 并发时延迟翻倍」和「32 并发时延迟 4 倍」都能通过。脚本的输出是待核清单，不是结论，人还得逐个看语境。

## 事实核查检查清单

这份清单固定挂在核查卡点上，每篇过一遍，八条打勾才放行。它比任何提示词都重要，因为它是错误发生之后唯一还能拦住的东西。

| 项 | 检查内容 | 判定标准 |
| --- | --- | --- |
| 1 | 所有具体数值 | 每个数字能在素材里找到出处，或标注为估算并给区间 |
| 2 | 时间与版本 | 版本号、发布日期与官方发布记录一致，不写「最近」「前不久」 |
| 3 | 引用原话 | 引号内的句子能逐字命中原文，不改写不加省略号 |
| 4 | 因果表述 | 「因为 A 所以 B」有依据支撑，仅相关就改成「同时观察到」 |
| 5 | 代码可执行 | 代码块语法通过，关键 API 签名与当前官方文档一致 |
| 6 | 结论边界 | 结论标明了适用条件，没有从单一环境推到全局 |
| 7 | 绝对化用词 | 全文无「一定」「必然」「百分之百」，除非有穷举证明 |
| 8 | 外链与图片 | 无图片，外链仅官方文档域名，且能打开 |

第 4 条最难执行，也最容易出事。「加了缓存之后 QPS 涨了 3 倍」是观测，「加缓存让 QPS 涨了 3 倍」是因果，没做对照实验就是编。改写阶段统一改成观测句式，宁可弱一点。

第 6 条常被忽略。结论如果来自 8 核 32G 的机器，硬件和版本必须写清楚，否则读者复现不出来，会认为整篇都是假的。

## 改写阶段该改什么

改写不是润色。任务是把它变成「有人写过的样子」，具体三件事：删掉每节开头的过渡句、把并列的三点合成一句带主次的表述、把抽象结论换成具体场景。

反面清单比正面要求有效。提示里明确列禁用语：「值得注意的是」「总的来说」「在当今」，以及不许把「我实测」改成「经测试」。末一条最要紧，模型的默认行为是把第一人称经验抹平成客观陈述，而那恰恰是文章唯一的值。

## 标题和摘要最后定

标题在终稿之后生成，因为这时候文章的实际内容才确定。给模型终稿全文，要 10 个候选，每个不超过 20 字，至少 3 个包含具体数字，至少 2 个是问句。人从 10 个里选 1 个再手改一版。摘要不让模型自由写，按「解决 X，方法是 Y，代价是 Z」三段填，40 字，比自由发挥稳定得多。

## 卡点的成本

四个卡点加起来，每篇 5.5 个工时里有 1 小时是切换和等待，不是干活，真正判断只有 40 分钟。瓶颈不在生成，在于人要在四个不同时刻回来做决定。所以工序按「卡点能否合并」重排过：提纲不设卡点，选题和标题合成一次选题会批量处理，一天一次，一次 5 篇。同类判断批量做，比一天切换五次快得多。

没合并掉的是事实核查。它没法批量化，每篇的核查点都不一样，而且必须在初稿完成后立刻做，隔一天就忘了数据是哪来的。
