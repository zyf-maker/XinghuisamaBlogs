同一个模型、同一批 800 条工单，一次问完「分类 + 优先级 + 回复草稿」，分类准确率 71%，优先级准确率 58%。拆成三次独立调用之后，分类 91%，优先级 84%。成本涨到 2.4 倍，但人工介入率从 43% 降到 17%。这笔账我算过：人工处理一条工单平均 4 分钟，2.4 倍的 token 钱远低于省下的工时。

先说结论：多任务一次问完是准确率杀手，不是提示词写得不好。下面讲为什么，以及拆完之后兜底怎么做。

## 单次多任务的三个失效点

输出预算被争抢。分类只需要几个 token，回复草稿要两三百 token，模型会把注意力放在生成篇幅大的那个上。它在写回复时顺手把分类填了，而写回复用的是「共情 + 安抚」的语气，这个语气倾向于把问题说得更严重、更紧急。于是标成「高优先级」的比例从实际的 18% 涨到 39%。

任务之间互相让步。分类要求判断干脆，回复要求语气柔和，两个目标冲突时模型会折中，表现为分类标签选一个「中间档」，比如分不清是「物流延迟」还是「物流丢件」就填「物流问题」。你得到了一个看起来对、实际没法路由的标签。

错误不可定位。一次输出的三个字段是一起错的。分类错了，回复也跟着错，你没法判断是分类环节还是生成环节的问题。拆开之后每个环节有自己的准确率，能定位、能单独优化、能单独回滚。

## 分类标签体系

标签设计的核心不是覆盖全，是能路由。「其他」这种标签等于没分，因为它不能触发任何动作。我的做法是每个标签必须绑定一个处理组和一个 SLA，绑不上的就不要这个标签。

| 一级标签 | 二级标签 | 处理组 | 首响 SLA | 典型触发词 |
| --- | --- | --- | --- | --- |
| 订单 | 未发货 | 仓储 | 2h | 还没发、什么时候发、一直不更新 |
| 订单 | 错发漏发 | 仓储 | 1h | 少了一件、发错了、不是我买的 |
| 物流 | 延迟 | 物流 | 4h | 卡在、停在、超时未到 |
| 物流 | 丢件破损 | 物流 | 1h | 丢了、破了、压坏、空包 |
| 售后 | 退换货 | 售后 | 4h | 想退、换一个、七天无理由 |
| 售后 | 退款未到账 | 财务 | 2h | 退了没收到、钱没退 |
| 产品 | 功能咨询 | 售前 | 8h | 支持吗、能不能、怎么用 |
| 产品 | 故障报错 | 技术 | 1h | 报错、打不开、崩了、闪退 |
| 账务 | 发票 | 财务 | 24h | 开发票、抬头、税号 |
| 账务 | 重复扣款 | 财务 | 30min | 扣了两次、多扣 |
| 账号 | 登录异常 | 技术 | 2h | 登不上、验证码收不到、被锁 |
| 投诉 | 服务态度 | 客服主管 | 30min | 态度、骂、没人管 |

12 个标签，二级标签 2 到 3 个一组。一级用于统计和路由到组，二级用于选模板。再往下分就过拟合了，我试过 34 个标签的版本，人工复核成本涨了一倍，准确率只涨 2 个点。

标签的边界要写进提示里，用「不包含」的表述比「包含」更有效。比如「物流延迟」的定义里明确写「客户已收到货但因质量问题不满的，不属于本类」，这一条就砍掉了近三成的误分。

## 分类调用

```typescript
type Ticket = { id: string; subject: string; body: string; channel: string; createdAt: string };

const LABELS = [
  "订单/未发货", "订单/错发漏发", "物流/延迟", "物流/丢件破损",
  "售后/退换货", "售后/退款未到账", "产品/功能咨询", "产品/故障报错",
  "账务/发票", "账务/重复扣款", "账号/登录异常", "投诉/服务态度",
] as const;

const CLASSIFY_SYSTEM = `你是电商客服工单分类器，只输出标签，不解释，不安抚。
可选标签（必须逐字选自下列，不得自创、不得输出多个）：
${LABELS.join("\n")}
判定顺序：
1. 工单里出现金额纠纷且客户主张被多收，走账务
2. 出现「丢/破/空包/少了」走物流/丢件破损，不走售后
3. 客户投诉的是人的态度而非商品，走投诉
4. 描述具体报错信息、页面打不开、功能失效，走产品/故障报错
5. 仅是询问是否支持某功能，走产品/功能咨询
无法判断时输出 UNKNOWN，不要猜。`;

export async function classify(t: Ticket) {
  const res = await fetch(`${process.env.LLM_BASE_URL}/chat/completions`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${process.env.LLM_API_KEY}`,
    },
    body: JSON.stringify({
      model: process.env.LLM_MODEL,
      temperature: 0,
      max_tokens: 20,
      messages: [
        { role: "system", content: CLASSIFY_SYSTEM },
        { role: "user", content: `渠道:${t.channel}\n标题:${t.subject}\n正文:${t.body}` },
      ],
    }),
  });
  const data = await res.json();
  const raw = (data.choices?.[0]?.message?.content ?? "").trim();
  return (LABELS as readonly string[]).includes(raw) ? raw : "UNKNOWN";
}
```

`max_tokens: 20` 是关键的一行。它物理上禁止模型输出解释，比在提示里写「不要解释」可靠得多。我早期版本没限长度，模型会在标签后面补一句「因为客户提到……」，解析器直接崩了。

## 优先级单独算

优先级不进分类提示。它是一个规则加模型的混合判断，输入是标签、渠道、客户等级、历史工单数。

纯模型判优先级的通病是通胀：它把「客户情绪激烈」当成「业务影响大」。骂得凶不等于损失大。我的做法是先用规则算出基线，再让模型只在基线上下调一档，禁止上调超过一档。

| 条件 | 基线 | 调整权限 |
| --- | --- | --- |
| 标签属于 账务/重复扣款、物流/丢件破损、投诉/服务态度 | P1 | 模型可下调至 P2 |
| 客户等级为 VIP 或历史工单大于等于 3 条 | 在标签基线上升一档 | 不允许再上调 |
| 渠道为电话或在线实时 | 升一档 | 不允许再上调 |
| 正文含「已经等了」「第三次」「投诉到」 | 升一档 | 累计不超过 P1 |
| 正文长度小于 20 字且无具体描述 | 降一档 | 模型可下调 |

基线由代码算，模型只输出一个 `-1 / 0 / +1` 的调整量和一句理由。输出空间被压到三个值，准确率自然上去了。这一版上线后 P1 的日均量从 210 条回落到 78 条，和实际业务量对得上。

## 兜底规则表

分流系统的价值不在于分得多准，在于分错的时候不会静默失败。下面这几条是必须有的，每条都对应一次线上事故。

| 触发条件 | 兜底动作 | 为什么 |
| --- | --- | --- |
| 分类返回 UNKNOWN | 落人工待分配池，不默认进「其他」 | 默认值会被当成正常数据统计，掩盖模型退化 |
| 连续 20 条 UNKNOWN | 熔断分类调用，全部转人工并告警 | 通常是提示词被改或模型版本变了 |
| 标签与正文关键词强冲突 | 保留模型结果但标记 `conflict`，人工优先看 | 客户常把两件事写在一张单里 |
| 优先级为 P1 但标签属产品咨询 | 降为 P2 并标记 | 促销期客户会用急迫措辞问功能 |
| 同一客户 24 小时内 3 张同标签工单 | 合并为一张并升级 | 重复工单是真实故障的信号 |
| 建议回复引用知识库外的政策 | 整段丢弃，只给人工空模板 | 编造赔付政策是最高危的错误 |
| 工单正文含法律词汇（起诉、律师、12315） | 直接 P1 到客服主管，跳过模型 | 这类单子不该由模型碰 |
| 模型响应超时 8 秒 | 重试一次，再失败转人工 | 分流是同步链路，不能挂着 |

## 建议回复最后生成

回复草稿一定放在分类和优先级都确定之后，并且把标签、SLA、可用话术模板一起作为输入。这一步的正确性主要取决于它拿到的上下文，而不是提示词措辞。

我踩过的坑是让模型直接生成完整回复。它会补上具体的退款天数、补偿金额、快递单号格式。后来改成只允许它填模板占位符，占位符的值必须从工单原文里摘，摘不到就留空给人工。模板由业务方维护，模型只做填空和语气调整。这样即便模型换了，输出结构也不会变。

拆成三步之后，每条工单的成本从 0.0031 美元涨到 0.0074 美元。有人问值不值，看的是人工介入率那一栏：43% 到 17%。剩下的 17% 里，有 11% 是 UNKNOWN 和法律词汇单，这些本来就该人看。
