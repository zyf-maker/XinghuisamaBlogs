## 为什么顺序反了会出事

直接说"把 `calculate_shipping` 改成支持满减"的结果通常是这样：代码改完，看着合理，你手动试了一个用例，对了，合并。两周后运营发现 99 元和 100 元的订单运费都算成 0，因为边界写成了 `>=` 而不是 `> 100`。

问题在于你给的需求是一个模糊的句子，模型把它翻译成一段代码，中间没有可检验的中间物。测试的作用就是造这个中间物：把"支持满减"变成五条断言，先确认这五条断言在你手上是失败的、失败原因是对的，再让它去改。

顺序反过来（先改代码再补测试）几乎必然失效。补出来的测试会照着实现的形状写，实现错了测试跟着错，覆盖率涨了，保护为零。

## 第一步：让人先写断言

测试不该由模型写，至少不该由它独立写。断言的取值来自业务，模型不知道 99 元该不该免运费。

我自己的做法是在对话前先手写测试骨架，只写数值和预期，不写断言语法：

```
满 100 免运费：
  99  -> 8.0
  100 -> 0
  250 -> 0
  非会员 99 -> 8.0
  偏远地区 250 -> 12.0
```

五行，一分钟。有了这个，剩下的翻译工作交给模型是安全的。

## 第二步：让它把骨架变成能跑的测试

```
把上面五条写成 pytest 用例，加到 tests/test_shipping.py。
只写测试，不改 src/ 下任何文件。
用现有的 ShippingCalculator 接口，不要新增参数。
```

关键的约束是"只写测试，不改 src"。不加这句，它会顺手把实现也改了，然后测试一次就绿，你失去了"失败"这个信号。

写完先跑一遍：

```bash
uv run pytest tests/test_shipping.py -q
```

期望看到五条失败（或者三条失败两条通过，取决于现状）。**这里必须检查失败原因**。如果报的是 `AttributeError: 'ShippingCalculator' object has no attribute 'region'`，说明测试用了一个不存在的接口——那是在测未来，不是在测需求。改成现有接口能表达的断言，或者先确认接口要改。

失败原因分三类，处理方式不同：

| 失败原因 | 含义 | 处理 |
| --- | --- | --- |
| 断言不成立（`assert 8.0 == 0`） | 正常红灯 | 继续 |
| 接口不存在（`AttributeError`） | 测试超前 | 改测试或先定接口 |
| 导入/语法错误 | 测试本身坏了 | 修测试，别往下走 |

只有第一类是有效的失败。第二类常见于模型自作主张加了参数，第三类通常是它编了个 fixture 名。

## 第三步：让它改实现，一次一条

```
现在改 src/shipping.py 让上面五条通过。
一次只处理一条，每改完跑一次 pytest。
不要修改测试文件的任何内容。
```

"不要修改测试"这句话不是多余的礼貌。观测到的行为是：模型遇到改不动的断言，倾向于调整断言而不是调整实现，尤其是数值类断言。加上这条约束后它会转而报告"第 4 条无法在不改接口的前提下满足"，这个报告本身就有价值。

一次一条的收益在定位。批量改完跑一次，挂了三条，你不知道哪条改动引起的。逐条跑，每条改动和每条结果一一对应，出问题时回溯成本极低。

## 第四步：绿了之后看 diff

全绿不等于对。三件事要核：

- 测试文件有没有被动过，`git diff tests/` 应该是空。
- 实现里有没有为通过测试而写的特判，比如 `if amount == 99: return 8.0`。
- 覆盖率有没有真的动，还是只覆盖了新增分支。

第二条最隐蔽。模型在压力下会写"针对性补丁"，形式上通过，实质上把逻辑硬编码了。识别方法是让它解释实现："为什么 100 这个边界用 `>` 而不是 `>=`？"答不上来或者答得含糊，就重写。

## 收益边界

这套流程在什么情况下划算，我有比较明确的判断。

**适合**：明确的输入输出映射、有现成的边界条件、逻辑集中在一两个函数、已有测试框架在跑。典型的如计价、权限判定、状态机流转、解析器。这类改动的测试写起来便宜（十分钟），而错误的代价高（线上数据错）。

**不适合**：跨多个模块的重构、性能优化、UI 布局调整、涉及外部系统的集成。这些的"正确"难以用断言表达，写出来的测试往往是"跑通就行"的形状测试，投入产出比低。

还有一个反直觉的点：**bug 修复比新功能更适合**。新功能的测试写起来要设计，bug 修复的测试是现成的——复现步骤就是断言。修 bug 时我固定这么干：

```
这是复现步骤：订单 12345，会员等级 2，优惠券叠加后金额 99.5，
运费算成 0，预期 8.0。
先写一个能复现的测试，确认它现在失败，再修。
```

"确认它现在失败"这一步不能跳。跳过的话，你无法区分"修好了"和"测试写错了但碰巧通过"。我见过一个案例，测试里 mock 的返回值跟真实接口不一致，测试一直是绿的，bug 一直在。

## 一次真实的失败

去年改一个化工项目的单位换算，我让模型先写测试。它写了十二条，全绿。我没检查失败原因，直接让它改实现，改完还是全绿，合并。

问题出在那十二条测试用的都是 `mol/L` 和 `g/mol` 这种"好算"的值，一条都没覆盖 `mol/m³` 到 `mol/L` 的千倍换算。模型选测试数据的偏好是"容易写对"，不是"容易出错"。这就是为什么第一步必须人来写数值。

后来补的规则是：测试数据里至少有一条来自真实场景，越难看越好。真实数据往往有小数、有量级差、有不整齐的边界，正是能抓到 bug 的形状。

## 落地的最小版本

如果不能全套照做，只保留两条：

1. 人先给数值表，不要让模型决定测什么。
2. 改实现前必须看到有效的红灯。

这两条几乎不增加成本，能挡掉大部分"改完看着对"的问题。剩下的流程细节可以慢慢补。
