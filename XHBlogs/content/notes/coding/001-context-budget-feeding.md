## 预算先算清楚

一个两千行的 Python 文件大约两万 token，密度高的 TypeScript 更高，注释和空行少的生成代码反而偏低。取个保守值：每行代码十个 token，加上路径和分隔符，一个三百行的模块约三千五百 token。

两百 k 的窗口听起来很宽，但有效区间窄得多。我的经验是超过六万 token 的输入，模型对中段内容的引用准确率明显下滑，长文件里靠中间的那个函数最容易被"记错参数名"。这个现象跟具体模型有关，但方向一致：塞得越满，越容易挑错重点。

所以给文件的预算定在三万到五万 token，大约八到十二个中等文件，或者三到五个大文件。这个量级能装下一个调用链，装不下整个模块。

## 先给调用链，不给相关文件

最容易犯的错是按"相关性"选文件：搜到十个提到 `invoice` 的文件就全塞进去。结果八个是测试、两个是类型定义，真正的实现被挤到预算边缘。

改成按调用链选。从你要改的入口出发，往上找谁调用它，往下找它调用谁，一条链通常三到五跳。每一跳只给签名所在的那一段，不给整个文件。

具体做法是先跑一遍结构提取，把函数和类的骨架打出来：

```bash
# Python：只列定义与签名，不列实现
rg -n '^\s*(class|def|async def)\s+\w+' src/ --type py | head -80

# TS：列导出符号
rg -n '^export (async )?(function|class|const|interface|type)' src/
```

这两条命令的输出往往不到两千 token，却能把整个模块的骨架交代清楚。先发骨架，让模型告诉你它还需要看哪几个函数的实现，再逐个补。这个方法我在一个四十万行的 Java 仓库上用过，定位一个 bug 从"翻十分钟文件"变成两轮对话。

## 目录树截到第几层

`tree` 的完整输出在小仓库上无害，在大仓库上是灾难。一个两千目录的 monorepo，全量目录树三万多行，三十万 token，直接吃满窗口，剩下的内容它全看不见。

截断规则：两层足够，第三层只给关键目录。

```bash
# 只到两层，排除产物与依赖
tree -L 2 -d --dirsfirst \
  -I 'node_modules|dist|build|.next|coverage|__pycache__|.git|venv|target' \
  | head -120

# 需要第三层时，只展开源码区
tree src -L 3 -d -I 'generated|mocks' | head -80
```

`head -120` 是硬保险。目录数超过一百二十，模型也读不完，多出来的只是噪音。真正有用的信息是"哪几个顶层目录承载业务"，这个在二十行内就看得出来。

单仓库多包的情况，先给一份人工写的结构摘要，比目录树更省：

```
apps/web        Next.js 前端，调 api 层
apps/api        FastAPI 服务
packages/core   领域模型，被 api 和 web 共用
packages/ui     组件库
infra/          terraform，不要改
```

四行，八十 token，信息量超过两百行目录树。目录树的价值只在"你完全不知道仓库长什么样"的第一次探索，之后就该用摘要。

## 摘要是最被低估的手段

把文件内容换成摘要，是压缩比最高的一步。三种摘要各有用途：

| 形式 | 压缩比 | 保留信息 | 适用场景 |
| --- | --- | --- | --- |
| 完整文件 | 1:1 | 全部 | 要改的那个文件 |
| 签名骨架 | 约 1:15 | 接口、类型、注释 | 上下游调用方 |
| 目录摘要 | 约 1:50 | 职责、边界 | 仓库全貌 |
| 单行说明 | 约 1:200 | 存在性 | 明显不相关的模块 |

规则很简单：要改的文件给全文，被调用的给签名，同层级的给一行说明，其他一概不给。

我踩过的坑是舍不得删。给了一个 `types.ts` 全文，八百行，全是 interface，占了八千 token，而模型实际只用到了其中三个。后来改成只贴那三个 interface，效果一样，预算省下七千。

## 一次给完还是分轮给

分轮。一次给完的假设是"模型能记住全部并正确取舍"，实际它会平均用力，把不重要的内容也当约束。

分轮的节奏是三段：第一轮给骨架和问题，问它要看哪些文件；第二轮按它说的给，通常只要两三个；第三轮开始讨论改法。第一轮的输出经常能纠正你的判断——你以为要改 `order.py`，它看完骨架说状态机在 `fsm.py` 里。

代价是多一轮往返，大约二十秒。在跨模块的问题上，这一轮基本都能赚回来。

## 长文件怎么切

单文件超过八百行时，整份投喂不划算。按函数边界切，不要按行数切。

```python
# 按顶层定义切分，保留 import 段
import ast, sys

src = open(sys.argv[1]).read()
tree = ast.parse(src)
lines = src.splitlines()
for node in tree.body:
    if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
        start, end = node.lineno - 1, node.end_lineno
        print(f"# {node.name}  L{start+1}-{end}  ({end-start} 行)")
```

先跑这个拿到函数清单和行号区间，再挑需要的区间读。切分点选在函数边界，模型看到的是完整逻辑单元；按固定行数切会把一个函数劈成两半，后半段没有签名，理解成本反而高。

## 判断喂够没有

一个可操作的检验：让模型复述它看到的东西。"列出你目前看到的函数，以及它们各自的调用关系。"如果它漏了关键函数，或者编造了不存在的参数，说明输入不够或者太乱，补一轮再继续。

反过来，如果它复述准确但你没得到想要的答案，那不是上下文问题，是问题本身不清楚。

另一个信号是它开始说"根据常见做法"。这句话出现时，通常意味着它没找到相关代码，在用训练数据补。这时候该做的是补文件，不是换问法。
