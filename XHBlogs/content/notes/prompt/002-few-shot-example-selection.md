少样本提示（few-shot）的效果波动很大，多数人把它归因于「模型不稳定」。实际变量只有三个：给几条、按什么顺序、和当前输入有多像。这三个都能测，都能调。

## 数量不是越多越好

固定任务、固定模型，从 0 条加到 10 条，准确率通常先上升再走平，超过某个点开始下降。上升段是模型学会了任务格式和判断标准；走平是因为边际信息趋零；下降是两个原因叠加——上下文变长带来的稀释，以及示例之间开始互相矛盾。

多数任务的最优点落在 3 到 5 条。分类类任务 3 条就够，因为决策边界简单；抽取类任务 4 到 6 条更稳，因为字段语义需要几个例子才能界定清楚。超过 8 条，除非每一条都覆盖不同的边界情况，否则只是在烧 token。

一个例外是标签体系复杂的情况。20 个类别的文本分类，示例要覆盖到多数类别，这时候数量重要，但要保证每条示例都短。

## 顺序的影响比想象的大

同样的示例集，换顺序结果会变。这个效应在 2023 年被反复测过，相邻示例的标签分布会影响模型对下一个输入的判断。全 A 类示例连着放，模型会倾向判 A。

两个实用规则。第一，打散标签，不要让同类示例连续出现。第二，把最难、最接近边界的示例放在最后，紧贴待处理输入的位置。模型对靠近输入的示例更敏感，把最难的放最后等于给它一个高权重的判断锚点。

我在一个三分类任务上验证过。随机顺序的准确率在 78% 到 86% 之间波动，按「易-中-难」排列后稳定在 89%。同一批示例，只是换了排列。

## 相似度决定收益上限

示例和当前输入越像，模型越容易迁移判断标准。这条比前两条更重要，也最常被忽略——很多人用固定的几条示例应付所有输入。

选择方式有三种。随机抽，成本低但效果差。按关键词重叠抽，简单有效，适合术语密集的领域。用 embedding 检索最近的 k 条，效果好，代价是维护一个向量库和一次检索调用。

embedding 检索的收益在长尾输入上最明显。头部常见输入随便给几条示例都能过，真正难的是那些边界样本，只有高度相似的示例才能提供有效参照。我在一个工单分类任务上把随机示例换成检索示例，整体准确率提升 6 个百分点，但边界样本上提升了 20 多个点。

代价要说清楚：检索示例会让同一类输入的提示长度不稳定，缓存命中率下降。如果走的是按 token 计费且量大，要算这笔账。

| 选择策略 | 实现成本 | 头部样本收益 | 边界样本收益 | 提示长度稳定性 |
| --- | --- | --- | --- | --- |
| 固定示例 | 极低 | 中 | 低 | 高 |
| 随机抽样 | 低 | 中 | 低 | 中 |
| 关键词重叠 | 中 | 中高 | 中 | 中 |
| embedding 检索 | 高 | 高 | 高 | 低 |
| 检索 + 去重 | 高 | 高 | 高 | 中 |

「检索 + 去重」是最后一档：检索出最近的 8 条，去掉和已选示例相似度超过阈值的，保留 4 条。长度更可控，也不会出现四条几乎一样的示例。

## 一个能跑的示例挑选器

```python
import numpy as np
from dataclasses import dataclass

@dataclass
class Example:
    text: str
    label: str
    vec: np.ndarray

def pick(query_vec: np.ndarray, pool: list[Example], k: int = 4,
         diversity: float = 0.92) -> list[Example]:
    """按相似度取候选，再做多样性过滤，避免示例同质化。"""
    sims = np.array([float(query_vec @ e.vec) for e in pool])
    order = np.argsort(-sims)
    chosen: list[Example] = []
    for idx in order:
        cand = pool[idx]
        if any(cand.label == c.label and float(cand.vec @ c.vec) > diversity
               for c in chosen):
            continue
        chosen.append(cand)
        if len(chosen) == k:
            break
    # 重排：相似度最低的在前，最难的贴住输入
    chosen.sort(key=lambda e: float(query_vec @ e.vec))
    return chosen

def render(examples: list[Example], query: str) -> str:
    blocks = [f"输入：{e.text}\n标签：{e.label}" for e in examples]
    return "\n\n".join(blocks) + f"\n\n输入：{query}\n标签："
```

`diversity` 参数控制去重强度，0.92 是个保守起点，示例池小的时候调到 0.85，否则会选不满 k 条。最后那步重排容易被忽略，但它是「难例贴底」规则的实现，去掉之后效果会退回随机顺序的水平。

注意 `vec` 必须已归一化，否则点积不是余弦相似度，排序会偏向量长。

## 几个具体的坑

示例里有格式错误，模型会照着错。清理示例集比调提示词更有效，尤其是 JSON 里的尾逗号、字段名大小写不一致这种。

示例的标签分布不均。三分类里某一类占了 8 条中的 6 条，模型会偏向这一类。要么均衡采样，要么在提示里显式说明先验。

示例太长。一条示例 500 token，4 条就是 2000，还没算输入。抽取类任务的示例可以只保留和字段相关的片段，不必给完整记录。

评估时只看总体准确率会误判。示例策略的收益集中在少数难样本上，总体指标看不出来。要按难度分层统计，否则会得出「检索没有用」的错误结论。

最后一点：示例和指令的职责别混。示例负责展示「长什么样」，指令负责说明「为什么这样判断」。把判断规则塞进示例里，模型学到的是一条条特例，换个输入就不适用。
