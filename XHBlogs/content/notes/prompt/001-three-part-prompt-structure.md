提示词写得乱，多数时候不是措辞问题，是结构问题。把所有要求揉成一段话，模型只能靠注意力去猜哪句是背景、哪句是硬约束、哪句是偏好。拆成三段之后，同一批任务的表现会稳定一大截。

## 三段各管什么

角色段定义模型站在什么位置说话。它决定知识调用方向和默认语气，是软约束。

约束段定义什么不能做、什么必须做。这是硬约束，要能被验证。写「尽量准确」等于没写，写「不得引入输入文本之外的数字」才能拿去检查。

格式段定义输出的形状。字段名、顺序、长度、空值怎么表示，全部写死。

三段顺序不能反。先给约束再给角色，模型容易把角色当成又一条规则处理，语气会变得生硬。格式放最后，因为它是离输出最近的一层，模型在生成时对末尾指令的遵循度更高。

| 段落 | 管什么 | 约束强度 | 判断标准 | 典型失效 |
| --- | --- | --- | --- | --- |
| 角色 | 知识范围与默认语气 | 软 | 能改变模型主动提及的内容 | 堆形容词，无行为差异 |
| 约束 | 可做与不可做 | 硬 | 每条能被程序或人判真假 | 写成「尽量准确」 |
| 格式 | 输出形状 | 硬 | 能被解析器直接消费 | 只描述不给反例 |

## 角色段：写能力边界，不写人设

「你是一位资深化学信息学专家」这种写法作用有限，模型不知道「资深」意味着什么。有效的是把能力范围具体化：熟悉哪类数据、惯用哪种方法、会注意哪些陷阱。

对比一下。「你是一个专业助手」几乎没有信息量。「你处理分子描述符与活性数据，习惯先检查数据泄漏，对 small sample 的交叉验证划分尤其谨慎」——这句直接改变了模型在回答里会主动提到的内容。

角色段控制在两三句。写长了会挤占约束段的注意力，而且大部分形容词不产生行为差异。

## 约束段：每条都能被判真假

约束要写成可检验的命题。我把常见的分成四类。

来源约束：只能用给定材料，不得补充外部知识。数值必须能在原文找到。

行为约束：不确定时输出「未提及」，不得推测。多个来源冲突时列出冲突，不做裁决。

范围约束：只处理与问题直接相关的段落，忽略样板文字。

禁止项：不得输出解释性前言，不得复述问题，不得使用「综上所述」类收束语。

禁止项最容易被忽略，也最有效。模型的默认行为里包含大量礼貌性铺垫，一条明确的禁止项能省下几十个 token 和一轮后处理。

## 格式段：给形状，也给反例

只描述格式不够。给一个正例，再给一个反例，模型对边界的理解会准得多。反例的价值在于它展示了「看起来对但实际错」的形态，这正是校验器会拦下的那类输出。

字段顺序也要说。JSON 的键顺序对解析没影响，但对模型生成有影响：先让它输出判断结论，再输出依据，比反过来更容易得到自洽的结果。反过来写，模型常常先编依据再硬凑结论。

## 一份完整模板

下面这份是抽取类任务的底版，改字段名就能用。三个段落用空行隔开，便于模型区分。

```
【角色】
你处理实验记录的结构化抽取，熟悉化学合成与表征数据的常见书写习惯。
你优先保证字段与原文一致，其次才是完整性。

【约束】
1. 只使用 <record> 标签内的文本，不得引入外部知识。
2. 每个字段的值必须能在原文中找到对应表述；找不到时填 null，不得推测。
3. 数值保留原文精度，不做单位换算。
4. 同一字段在原文出现多个值时，取最后一个并在此字段后加 "conflict": true。
5. 不得输出解释、前言、结语，不得复述输入。

【格式】
只输出一个 JSON 对象，键顺序固定为：solvent, temperature_k, time_h, yield_pct, notes。
类型：前四项为 string 或 number 或 null，notes 为不超过 20 字的 string。
正例：{"solvent": "乙腈", "temperature_k": 353, "time_h": 2, "yield_pct": 78, "notes": ""}
反例（不要这样）：{"solvent": "乙腈（常用极性非质子溶剂）", ...} —— 括号内为原文没有的解释。

<record>
该反应在乙腈中于 353 K 搅拌 2 小时，产率 78%。
</record>
```

反例那句是刻意的。不加这个反例，模型很爱在字段值里补充常识说明，解析没报错但数据脏了，清洗成本比重新抽一遍还高。

## 三段之外留一块

复杂任务需要一块「任务说明」，讲清这次具体做什么，和角色段分开。角色是长期设定，任务是单次指令。混在一起会导致一个后果：换任务时得重写整段提示，改动范围不可控。

我的文件组织是角色段和约束段存在模板里，任务说明和输入由代码注入。这样改任务不动模板，改约束不影响任务逻辑。

```python
TEMPLATE = """【角色】
{role}

【约束】
{constraints}

【格式】
{format_spec}

【任务】
{task}

<input>
{payload}
</input>
"""

def build(role: str, constraints: list[str], format_spec: str,
          task: str, payload: str) -> str:
    numbered = "\n".join(f"{i}. {c}" for i, c in enumerate(constraints, 1))
    return TEMPLATE.format(
        role=role.strip(),
        constraints=numbered,
        format_spec=format_spec.strip(),
        task=task.strip(),
        payload=payload.strip(),
    )
```

约束用列表传，编号由代码生成。手写编号在增删条目时最容易错位，出现过一次「第 3 条」指向旧内容的事故之后我就改成这样了。

## 结构带来的实际差别

同一批 200 条实验记录，一段式提示的字段缺失率 18%，三段式降到 6%。差异主要来自两处：约束段明确了 null 的语义，模型不再用空字符串或「未知」糊过去；格式段的反例压住了字段内的解释性文字。

还有一个隐性收益：出错时能定位。一段式提示出问题，只能整体重写；三段式可以判断是角色没覆盖、约束漏了一条、还是格式没给反例，改一处，其余不动。

模板不是越长越好。三段加起来控制在 400 字以内，超过之后每条约束的权重都在下降。约束超过 8 条就该拆分任务，而不是继续往模板里加。
