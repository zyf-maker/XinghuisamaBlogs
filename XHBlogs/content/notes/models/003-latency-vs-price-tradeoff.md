有个写作辅助功能，用户点「续写」后要盯屏幕四秒才出字。我第一反应是换更快的模型，账单从每天 90 元涨到 340 元，体感只好了半秒。后来查日志发现，慢的不是生成，是请求发出前的两件事：拼上下文花 1.2 秒，串行调了一次敏感词检测又花 0.8 秒。换模型买来的那半秒，是从 4.0 秒到 3.5 秒。

这件事让我把延迟拆成两段量，此后再没靠换模型解决过性能问题。

## 两个数不是一回事

首 token 延迟指从发出请求到收到第一个内容片段的时间，包含网络往返、排队、预填充。总时延指末位 token 落地的时间，等于首 token 延迟加上输出 token 数除以生成速度。

一段 400 字的回复，首 token 0.6 秒、生成速度 60 token 每秒，总时延约 3.3 秒。用户在这 3.3 秒里的感受完全由首 token 决定：0.6 秒内出字，他知道系统在干活；如果首 token 要 2.5 秒，前 2.5 秒是纯黑屏，他会怀疑没点上，去重复点击。

所以优化顺序是：先压首 token，再谈吞吐。压首 token 最有效的手段往往不在模型侧——砍上下文长度、把串行的前置检查改成并行、把长系统提示换成缓存命中。这些都是百毫秒到秒级的收益，比换模型大一个数量级。

## 流式改变的是等待的形状

同样 3.3 秒总时延，非流式是一次性等 3.3 秒然后整段出现，流式是 0.6 秒开始逐字出。用户对前者的评价通常是「卡」，对后者是「还行」。

但流式不是免费的。它把错误暴露得更晚：模型在第 200 个 token 处触发长度截断时，你已经把半截内容渲染给用户了，得准备替换逻辑。结构化输出与流式天然冲突，JSON 没闭合之前不能解析，只能做增量校验或退回非流式。前端也不能再拿「请求完成」当 loading 结束信号，得改听首包到达事件。

我踩过的坑是反向代理缓冲。流式在后端跑通了，前端仍然一次性收到全部内容，查了两小时发现是网关开了响应缓冲，`X-Accel-Buffering: no` 没设。这类问题在本地开发环境不会出现，只在线上暴露。

## 三档路由

不是所有请求都值得用最快的模型。我现在的分法是按「用户是否在等」和「错误代价」两个维度切三档。

| 请求类型 | 首 token 目标 | 延迟敏感 | 模型档位 | 附加处理 |
| --- | --- | --- | --- | --- |
| 输入框实时补全 | 300ms 内 | 极高 | 最小最快 | 限 30 token，禁用推理 |
| 对话首轮回复 | 1s 内 | 高 | 中档 | 流式，前置检查并行 |
| 文档摘要 | 3s 内 | 中 | 中档 | 非流式，可排队 |
| 批量打标 | 不关心 | 低 | 最便宜 | 加一次规则校验 |
| 结构化抽取 | 2s 内 | 中 | 便宜档 | 约束解码加失败重试 |
| 长文分析 | 8s 内 | 低 | 大窗口档 | 分段加进度提示 |

判据里有个反直觉的点：结构化抽取适合用便宜模型。因为这类任务的失败模式是格式而非语义，约束解码加一次重试能把成功率拉到 99% 以上，而重试的成本远低于全程用贵模型。反过来，开放式写作必须用好的，便宜模型写出来的东西格式没问题但没人愿意读，这个差距重试救不回来。

降级到便宜模型时必须配一次校验，校验什么取决于任务。抽取任务校验字段完整性和类型，打标任务校验标签是否在枚举内，摘要任务校验长度和必含要点。校验失败就升级到上一档重跑，并记一次降级失败。我这条链路的降级成功率是 87%，剩下 13% 走升级，综合成本比全用中档低 41%。

## 把两个数量出来

不用压测工具，一次 curl 就够。`time_starttransfer` 近似首 token 时间，`time_total` 是总时延，两者相减接近纯生成耗时。

```bash
measure() {
  local model="$1" prompt="$2"
  curl -sS -o /tmp/out.txt -w '%{time_starttransfer} %{time_total}\n' \
    "$API_BASE/chat/completions" \
    -H "Authorization: Bearer $API_KEY" \
    -H 'Content-Type: application/json' \
    -d "$(jq -nc --arg m "$model" --arg p "$prompt" \
      '{model:$m, stream:true, max_tokens:300,
        messages:[{role:"user",content:$p}]}')"
}

for i in 1 2 3 4 5; do
  measure "$MODEL_FAST" "用三句话说明什么是幂等" 
done | awk '{ttft+=$1; tot+=$2; n++}
           END{printf "TTFT avg=%.2fs  total avg=%.2fs  gen=%.2fs\n",
                      ttft/n, tot/n, (tot-ttft)/n}'
```

`stream:true` 是关键，非流式下 `time_starttransfer` 等于总时延，两个数会重合，看起来像首 token 很慢。跑五次取平均，单次波动能到 2 倍，尤其跨区域调用。

量完把数字写进路由配置，别写进代码。配置里存每档的首 token 目标和单价，路由时读配置算预期成本，超过日预算就自动降一档。这套东西的价值在于，厂商调价或延迟抖动时你改一行配置，不用改逻辑。

## 贵模型该留给谁

判断标准是「用户是否能感知到这一档的提升」。能感知的三种情况：等待超过 1.5 秒且没有任何进度反馈；输出是给人直接读的正文；错误会导致用户重做一遍操作。

不能感知的情况更多：后台任务、批量处理、用户已离开页面、输出只是中间产物。这些场景用最便宜的模型加校验，省下的钱足够在关键路径上多用几次贵的。

我算过一次对比：原来全站用中档模型，月账单 2600 元。改成三档路由后 1450 元，同时对话首轮的首 token 从 1.9 秒降到 0.8 秒。便宜和快不是对立的，前提是你知道哪些请求值得花钱。

## 一个反例

早期我把「实时补全」也接了中档模型，理由是质量好。结果每次按键触发请求，这部分一个月占了 60% 的成本，而用户几乎不看补全的前半句，只瞥后三个词。换成最小的模型加 30 token 上限后，采纳率没变，成本降到原来的 7%。

代价是那个小模型在中文标点处断句很怪，我加了一条后处理，把结尾不完整的片段丢掉。这条规则救了体验，也提醒我一件事：降级不是换个模型名就完，配套的后处理得一起写。
