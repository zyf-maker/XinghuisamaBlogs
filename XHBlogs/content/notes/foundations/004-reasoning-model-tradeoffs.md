把推理模型当成「更强的通用模型」是当前最常见的误用。它更贵、更慢、在简单任务上不一定更准，而且会拒绝一部分它认为需要额外思考的指令。搞清楚它的适用边界，比记哪个版本号强更重要。

## 差别在哪一层

普通模型一次前向、逐 token 输出，回答长度基本由内容决定。推理模型在给出最终答案之前先生成一段内部推理，这段内容对用户可能不可见，但计费。它在训练阶段用强化学习优化「中间推理是否正确导向最终答案」，行为和普通模型不是同一个分布。

三个直接后果。

延迟不可预测。普通模型的首 token 时间几百毫秒，推理模型可能先想 20 秒。这对同步接口是致命的，用户会以为页面卡死。

成本高一个量级。即使单价相同，推理 token 也算钱。一个需要 8000 个推理 token 的问题，流水线上跑几千次就顶不住。

指令遵循变弱。推理模型倾向自己判断任务边界，你写「直接输出 JSON」，它可能先写一段分析再给 JSON，或者认为问题太简单而直接回答、跳过你要求的步骤。格式化任务上表现经常不如普通模型。

## 什么任务值得付这个钱

判断标准只有一个：**答案能不能通过「多花时间想」变对**。

值得用的情况：多约束的排班或路径问题，需要在若干条件间找可行解；代码里定位跨文件的状态泄漏，得沿着调用链推；数学或物理的推导，中间步骤错了后面全错；数据清洗规则的边界情况，需要枚举反例。

不值得的情况：信息抽取、字段映射、文本分类、格式转换、改写润色、翻译。这些任务的难点在输入理解，不在推演，推理模型多花的 token 产生不了新信息，反而更容易在格式上自作主张。

| 任务 | 普通模型 | 推理模型 | 建议 |
| --- | --- | --- | --- |
| 从简历抽字段 | 快，格式稳 | 慢，可能加解释 | 普通模型 + schema 校验 |
| 跨文件 bug 定位 | 容易只看表面 | 能追到根因 | 推理模型 |
| 长文摘要 | 够用 | 收益极小 | 普通模型 |
| 多约束规划 | 常给出不可行解 | 明显更好 | 推理模型 |
| 单测生成 | 可用 | 边界用例更全 | 看覆盖率要求 |
| 翻译润色 | 好 | 慢，可能改结构 | 普通模型 |

一个中间方案是两条流水线：先用普通模型跑一遍，用小模型或规则做置信度判定，只在失败样本上切到推理模型。这样九成请求走快路径，成本增幅可控。

## 参数在这里基本失效

给推理模型设 temperature=0.2 想要稳定输出，通常没用。它的推理阶段用的是自己的采样策略，很多实现直接忽略或只对最终答案段生效。同样，`max_tokens` 如果设得太小，推理还没结束就被截断，返回的可能是半截推理加上错误结论，或者直接报 `finish_reason: length`。

实际配置上要改三件事。

把 `max_tokens` 放大到普通任务的 3 到 5 倍，给推理留空间。用流式输出，把推理过程和答案分开渲染，否则用户面对的是长时间空白。给请求设单独的超时预算，别沿用普通接口的 30 秒。

```python
import time
from openai import OpenAI

client = OpenAI()

def ask(prompt: str, reasoning: bool) -> dict:
    t0 = time.perf_counter()
    resp = client.chat.completions.create(
        model="REASONING_MODEL" if reasoning else "FAST_MODEL",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=8000 if reasoning else 1200,
        timeout=180 if reasoning else 30,
    )
    dt = time.perf_counter() - t0
    usage = resp.usage
    return {
        "mode": "reasoning" if reasoning else "fast",
        "elapsed_s": round(dt, 2),
        "in_tok": usage.prompt_tokens,
        "out_tok": usage.completion_tokens,
        "reasoning_tok": getattr(usage.completion_tokens_details, "reasoning_tokens", 0),
        "finish": resp.choices[0].finish_reason,
        "text": resp.choices[0].message.content,
    }
```

`reasoning_tokens` 这个字段能直接告诉你钱花在哪。如果它在总输出里占九成，说明这个任务被模型判定为「需要深思」，而你多半并不需要，换回普通模型更划算。

## 我踩过的两个坑

第一个是把推理模型放进批量离线任务，跑了两小时才发现吞吐只有原来的七分之一，队列堆了几万条。批处理的成本优势建立在吞吐上，推理模型把这个前提抹掉了。

第二个是让推理模型输出结构化结果。prompt 里写了严格的 JSON schema，它返回了一段「分析过程」加一个 markdown 代码块包着的 JSON，还多了两个我明确说了不要的字段。解析器直接抛 `JSONDecodeError`。改成「先让推理模型给结论，再用普通模型把结论转成 JSON」，两步走的稳定性高得多。

## 怎么决定用不用

先把任务拆成两类。答案能否通过更长的推理链改善，这是能力问题；单位时间的请求量能否承受，这是工程问题。两个条件同时满足才用。

可以先做一版对照：抽 30 条真实样本，两个模型各跑一遍，人工看差异。如果推理模型只在 2 到 3 条上更好，那 3 倍的延迟换不来这个收益，不如拿这笔预算去补检索质量或者加人工复核。

反过来，如果失败样本集中在「条件冲突没发现」「边界漏了」这类推演型错误，推理模型的提升会非常明显，这时候延迟就是必要代价。

一个更细的判断：看错误样本的失败模式。输错格式、漏字段、答非所问，属于表达层问题，普通模型加约束就能解决。答案看起来合理但实际不成立，属于推理层问题，才需要换模型。
