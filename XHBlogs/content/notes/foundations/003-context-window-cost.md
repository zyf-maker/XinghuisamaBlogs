上下文窗口从 8K 涨到 128K，再涨到 1M，宣传语听着像硬盘扩容：加大就完事了。实际用下来，把 200K 文档整段塞进去的效果，经常不如老老实实检索出 8K 相关段落。钱花得更多，答案还更差。

## 窗口容量和有效容量是两件事

标称的 context window 是模型架构能接受的最大 token 数，指的是不报错。有效容量指模型能稳定利用的信息量，通常低得多。

两个机制在拖后腿。第一是注意力本身：标准注意力对每个位置分配权重，位置越远、和查询越不相关，权重越低。稀释效应在长序列里是累积的，一段 100K 的上下文里，真正决定输出的往往是少数几个位置。第二是位置编码。RoPE 通过旋转把相对位置编码进 query 和 key 的内积，模型训练时见过的最大长度决定了它熟悉的位置范围。超长外推时，远距离位置的相对区分度下降，表现就是「模型好像没看见后半段」。

这解释了一个很多人都遇到过的现象：把关键信息放在文档开头或结尾，答对率明显高于放在正中间。这就是 lost in the middle，2023 年被系统测过，后面换了几代模型仍然存在，只是幅度变小。

## 位置不是等价的

同一个事实，放在 prompt 的不同位置，被用到的概率差别很大。把检索结果按相关度排序时，如果按降序塞进去，最相关的那条反而落在「高相关区」之外，被中段噪声挤掉。

我的做法是两头夹：最相关的几条放最前面，次相关的放最后面，中间堆低相关度的补充材料。这个顺序在三个模型上测过，抽取类任务的准确率比纯降序高 10 到 20 个百分点。

另一个细节是分块之间的分隔符。用 `---` 和用带编号的 `[doc 3]` 效果差不少，带编号能让模型在长上下文里定位引用，输出里也更容易追溯来源。代价是每个块多几个 token，值得。

## 成本是平方级的

注意力计算的复杂度对序列长度是平方关系。128K 上下文的算力开销是 8K 的 256 倍。多数服务商不会真按平方收费，而是分段定价或直接按 token 线性计费，但延迟和吞吐的优势依然明显：短上下文的首 token 时间和生成速度都更好。

按线性计费算笔账。输入单价 2 元每百万 token，一次请求塞 100K token，单次 0.2 元。一天 2000 次请求就是 400 元，一个月一万二。同一任务改成检索 6K 上下文，输入成本降到原来的 6%，而且准确率更高。

| 策略 | 上下文占用 | 召回质量 | 延迟 | 适用场景 |
| --- | --- | --- | --- | --- |
| 全文直塞 | 极高 | 中段易丢失 | 高 | 一次性分析单份短文档 |
| 固定滑窗 | 低 | 依赖切分粒度 | 低 | 流式日志、长对话 |
| 检索增强 | 中 | 取决于召回 | 中 | 知识库问答 |
| 分层摘要 | 低 | 细节有损 | 低 | 长篇报告通读 |
| 检索 + 原文引用 | 中 | 高 | 中 | 需要出处核对的场景 |

分层摘要适合「先摸清结构再深入」的任务：先把每章压成 200 字，汇总成大纲，再按问题回到原文取细节。缺点是两轮调用，好处是第二轮上下文很干净。

## 一个按预算分配的上下文组装器

真正要控制的是「每个部分分多少 token」，而不是「总共塞多少」。下面这个函数把预算切成固定的几块，超出就按优先级截断，避免某一段把预算吃光。

```python
from dataclasses import dataclass, field
import tiktoken

ENC = tiktoken.get_encoding("o200k_base")

@dataclass
class Part:
    name: str
    text: str
    weight: float          # 预算占比
    keep_tail: bool = False  # 截断时保留尾部（适合对话历史）

def count(text: str) -> int:
    return len(ENC.encode(text))

def assemble(parts: list[Part], budget: int, reserve_output: int = 1024) -> str:
    usable = budget - reserve_output
    total_weight = sum(p.weight for p in parts)
    out: list[str] = []
    for p in parts:
        quota = int(usable * p.weight / total_weight)
        toks = ENC.encode(p.text)
        if len(toks) > quota:
            toks = toks[-quota:] if p.keep_tail else toks[:quota]
            print(f"[truncate] {p.name}: {len(ENC.encode(p.text))} -> {quota} tok")
        out.append(f"<{p.name}>\n{ENC.decode(toks)}\n</{p.name}>")
    result = "\n\n".join(out)
    assert count(result) <= usable, "预算计算有误"
    return result

ctx = assemble(
    [
        Part("instruction", "只依据给定材料回答，找不到就说未提及。", 0.08),
        Part("evidence", "……检索到的段落……", 0.62),
        Part("history", "……最近几轮对话……", 0.20, keep_tail=True),
        Part("format", "输出：结论一句 + 依据条目，最多 3 条。", 0.10),
    ],
    budget=32_000,
    reserve_output=1_500,
)
```

`assert` 那句不是摆设。预算算错导致的截断，表现出来是模型「忽略指令」，排查起来很费时间。加一道断言，问题在组装阶段就暴露。

权重要跟着任务调。抽取任务把 evidence 提到 0.75，指令压到 0.05；多轮客服把 history 提到 0.35。别用一套比例打天下。

## 什么时候该怀疑是上下文问题

几个信号。答案里出现了上下文之外的常识补充，说明模型没从材料里取信息。答案只引用了开头的内容，后面全是废话，可能是中段丢失。同一份材料换个顺序答案就变，说明位置敏感。请求耗时随长度非线性上升，且偶发超时。

对应处理：先做一次「针在草堆」测试，把一句独特的事实放进长文本不同位置，看模型能否定位。定位失败说明有效上下文不够，别硬塞，改检索。定位成功但答错，问题在指令或格式，不在长度。

最后一句留给预算：窗口越大，越要把它当稀缺资源用。能检索就别直塞，能摘要就别全文，能分段就别一次问完。省下来的不只是钱，还有准确率。
