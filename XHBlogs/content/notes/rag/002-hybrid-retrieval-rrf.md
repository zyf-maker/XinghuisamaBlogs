纯向量检索最典型的一次失败是这样的：用户问「ERR_PG_MAX_CONN 这个错误码怎么处理」，向量模型把它编码成一个语义大致等于"数据库连接失败"的东西，返回十篇讲连接池原理的文章，一篇都没提到那个字符串。错误码、产品型号、人名、API 路径这类精确 token，向量模型天生不擅长，因为它在训练时把这些低频串当噪声压掉了。

BM25 恰好相反。它靠词频和逆文档频率，遇到精确串就给高分，遇到同义改写就完全失灵。两路合并不是锦上添花，是因为它们的失效集合几乎不重叠。

## 两路各自的位置

BM25 的打分核心是三项相乘：词的稀有度、词在文档里的出现次数、以及文档长度归一化。参数只有 k1 和 b，k1 控制词频饱和，取 1.2 到 2.0，b 控制长度惩罚，取 0.75。中文要先分词，这里最容易出事：`jieba` 默认词典会把 `ERR_PG_MAX_CONN` 拆成 `ERR`、`PG`、`MAX`、`CONN` 四个词，如果只索引了其中两个，查询时又只匹配到一个，得分直接腰斩。我的做法是入库前用正则把所有 `[A-Z_]{4,}`、`\w+\.\w+` 之类的东西先抽出来，作为独立的 token 加进索引，词表里额外挂一份。

向量那一路的瓶颈在维度选择和截断。1024 维的 bge-m3 在中文技术文档上明显好于 768 维，但一次检索 400 篇的成本也翻倍。实际部署里我先用 HNSW 索引，`M=32`、`ef_construction=200`，查询时 `ef_search=64`，召回 10 条耗时稳定在 8ms 以内。

## RRF 的公式

Reciprocal Rank Fusion 只看排名，不看原始分数。这一点很关键：BM25 的分数是无界的，可能 12.3 也可能 87.5；余弦相似度在 -1 到 1 之间。直接加权求和要先做归一化，而归一化的方式会显著改变结果，z-score 归一化还会被长尾分布带偏。RRF 绕开了这个问题。

$$\text{score}(d) = \sum_{i \in \text{retrievers}} \frac{w_i}{k + \text{rank}_i(d)}$$

`rank` 从 1 开始，`k` 通常取 60，是那篇 2009 年论文里的经验常数。它的作用是压平头部：k 越小，第一名和后几名的差距越大；k 越大，排名靠后的文档被抬得越平。k=60 时第一名贡献 1/61≈0.0164，第十名贡献 1/70≈0.0143，差距 15%。如果 k 取 1，第一名是 0.5，第十名 0.091，差五倍多，融合退化成"谁排第一听谁的"。

权重 w 一般不用，除非某一路明显更可信。我给 BM25 的权重通常设 1.0，向量 1.0。如果文档库全是中文口语转录，向量权重可以降到 0.7。

| 参数 | 常用值 | 影响 |
| --- | --- | --- |
| k | 60 | 小于 20 偏向头部，大于 100 接近平均投票 |
| 每路召回数 | 50 | 小于 20 时融合没有素材，大于 100 收益饱和 |
| BM25 k1 | 1.2 | 越大越奖励重复出现 |
| BM25 b | 0.75 | 越大越惩罚长文档 |
| 输出条数 | 10 到 20 | 取决于下游 reranker 的预算 |

## 一个能跑的融合实现

只用标准库，两路输入是已经排好序的 id 列表，权重和 k 都可调。

```python
from collections import defaultdict

def rrf_fuse(
    rankings: list[list[str]],
    weights: list[float] | None = None,
    k: int = 60,
    limit: int = 10,
) -> list[tuple[str, float]]:
    """rankings: 每路召回的 doc_id 列表，已按相关性降序。"""
    weights = weights or [1.0] * len(rankings)
    if len(weights) != len(rankings):
        raise ValueError("weights 长度必须与 rankings 一致")

    scores: dict[str, float] = defaultdict(float)
    for ranking, w in zip(rankings, weights):
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] += w / (k + rank)

    return sorted(scores.items(), key=lambda x: (-x[1], x[0]))[:limit]

# 用法
bm25_ids = ["d17", "d03", "d55", "d08"]
vec_ids  = ["d03", "d41", "d17", "d92"]
print(rrf_fuse([bm25_ids, vec_ids], weights=[1.0, 1.0], k=60, limit=5))
# d03 在两路都靠前，融合后第一；d17 次之
```

排序里加了 `x[0]` 作为第二键，是为了让同分结果稳定。线上排查时同分导致顺序漂移会让人怀疑人生，加一行就能省掉一小时的困惑。

## 去重和分块粒度

两路召回的同一个文档的不同块会互相挤占名额。一个 8 块的文档可能被 BM25 命中 6 块，融合后前十里 6 个位置全是它。这在小库上很常见，因为长文档天然有更高的词命中概率。

处理方式是融合前按文档聚合，取该文档所有命中块里的最高分作为文档分，再回填最优块。代价是丢掉了"多块命中说明这一段整体相关"的信号，某些场景下这个信号有用。我的折中是：同一文档最多保留 2 块，且两块的分差要在 30% 以内，否则只留最高的那一块。

## 融合之后再排序

融合输出 20 条，交给 reranker 压到 5 条，这一步的收益比继续调融合参数大得多。但 reranker 有个坑：它按「查询-段落」的相关性打分，不感知来源。BM25 召回的块往往是关键词密集的短块，向量召回的块是语义相近的长块，前者的分数天然偏高，因为它字面重合多。结果是 reranker 把 BM25 那一路的结果全排在前面，混合检索等于白做。

缓解方式是给 reranker 的输入加上来源标记，或者在训练/微调时按来源平衡样本。更简单粗暴的做法是融合时给两路各留固定配额，前 10 条里保证每种来源至少 3 条，剩下的按分数排。这个分配不需要理由，只需要让两种召回都有机会进入终选。

另一个实际问题是延迟。BM25 本地倒排 5ms，向量 HNSW 8ms，reranker 一次 20 条在 GPU 上 40ms、CPU 上 300ms。后者的差距决定了能不能做实时对话。CPU 上跑 cross-encoder 的时候，我的做法是把候选压到 10 条，代价是 nDCG 掉 2 个点，但端到端从 320ms 降到 120ms，体验上是明显差别。

## 什么时候不该上混合

库小于 200 篇、查询基本都是自然语言问句、术语密度低的场景，混合检索的收益在 2 到 4 个百分点，但多维护一套分词器和倒排索引，多一份同步逻辑。我见过为了提升 3% 召回引入 ES 集群，最后因为分词器和向量库更新不同步，出现"新文档只能被向量路召回"的问题，排查花了两天。

判断标准很实际：拿 50 条真实查询跑一遍纯向量，如果错的那几条里有 3 条以上是因为精确串没匹配上，混合就值得做；否则先把 reranker 加上，性价比更高。
