分块是检索系统里最不性感、也最难返工的一步。它决定了后面所有环节的上限：切坏了，换多好的 embedding 模型、加多贵的 reranker 都只是在给噪声排序。我做过一次只有 400 篇文档的库，第一版用固定长度切，召回率卡在 0.61，改成按标题切之后同一条查询集上到了 0.78，模型一个字没换。

代价不会消失，只会转移。下面这三种做法各自把成本推给了不同的环节。

## 固定长度：唯一能预估成本的做法

按 token 数硬切，参数只有两个：窗口和重叠。常见配置是 512 token 一窗、重叠 64 token，大约 12.5%。重叠不是为了让语义连贯，而是防止关键句正好落在边界上被劈成两半，代价是存储和检索冗余各涨 12% 到 15%。

窗口大小的经验值在 256 到 512 之间。低于 256，单块能承载的上下文太少，"第三季度毛利率"这种需要前后条件的表述会被切断；高于 1024，块的向量被平均掉，一个块里同时讲了三件事，任何一件都只贡献三分之一的权重，余弦相似度整体被稀释。

真正的麻烦是切在句子中间。中文没有空格，按 token 切很容易切出"该指标同比下滑 12%，主要原因是"这样的半句，下一块开头是"原材料涨价"。检索命中前一块，模型拿到一句没有结论的话；命中后一块，拿到的结论没有主语。这两种情况在 prompt 里都表现为"模型答得很虚"。

| 参数 | 建议值 | 调整信号 |
| --- | --- | --- |
| chunk_size | 512 token | 单块平均被引用次数低于 0.3 说明太大 |
| overlap | 64 token | 边界处答案缺失率高于 5% 就加大 |
| 断句对齐 | 句号、换行 | 中文按 。！？；切，英文按 . ! ? 切 |
| 最小块长 | 120 汉字 | 更短的块合并到相邻块 |

## 按标题切：用结构换稳定

文档本身有 H2 层级时，标题就是作者已经标注好的语义边界，比任何算法都准。做法是按 `##` 切，每块保留标题行（标题里的词往往是检索最强的信号），超长的节再二次切，过短的节合并。

坑在数据源。PDF 转 markdown 之后标题层级经常错乱，一份说明书里出现十几个同级 H2，其实是同一个章的十几个条目；反过来，真正的章节标题因为字号问题被转成加粗正文，`##` 一个都没有。我的处理是先统计"每篇文档的 H2 数量分布"，H2 数量为 0 或大于 30 的文档走固定长度兜底，中间的才走标题切。这个比例在技术文档里通常是 15% 左右走兜底。

另一个坑是标题信息量低。"概述""注意事项""常见问题"这种标题在向量空间里几乎重合，几十个块挤在同一个位置。解决方式是把文档标题拼进块首：`{doc_title} > {h2} > {h3}`，让"Redis 持久化 > 常见问题"和"MySQL 索引 > 常见问题"分开。

## 按语义切：相似度断点

把文档拆成句子，逐句算 embedding，相邻两句余弦相似度突然下降的地方就是话题切换点。阈值一般取全部相邻相似度差值的 95 分位，绝对值落在 0.55 到 0.65 之间。这比固定阈值稳，因为每篇文档的行文密度不同。

代价很直接：入库前要对每个句子跑一次 embedding，切完还要对每个块再跑一次，embedding 调用量翻倍。400 篇文档、平均 60 句，就是 2.4 万次单句编码，用本地 bge-m3 在单张 4090 上大约 6 分钟，用 API 按量计费则是实打实的钱。而且它对转录稿这类口语文本效果才好，正式文档上比标题切没有优势。

## 我会怎么落地

优先级是标题 > 固定长度 > 语义。语义切分只在两种场景用：没有结构的会议转录、以及 OCR 后标题全丢的扫描件。

```python
import re

MAX_CHARS = 1400        # 约 900 token，中文按 1.6 字/token 估
MIN_CHARS = 120

def split_by_heading(md: str, doc_title: str) -> list[str]:
    parts = re.split(r"(?m)^(?=## )", md)
    chunks: list[str] = []
    for part in parts:
        part = part.strip()
        if not part:
            continue
        if len(part) < MIN_CHARS and chunks:
            chunks[-1] = chunks[-1] + "\n\n" + part   # 前言、尾注并入相邻块
            continue
        heading = part.split("\n", 1)[0].lstrip("# ").strip()
        prefix = f"{doc_title} > {heading}\n"
        chunks.extend(_split_long(part, prefix))
    return chunks

def _split_long(text: str, prefix: str) -> list[str]:
    if len(text) <= MAX_CHARS:
        return [prefix + text]
    out, buf = [], ""
    for sent in re.split(r"(?<=[。！？；\n])", text):
        if len(buf) + len(sent) > MAX_CHARS and buf:
            out.append(prefix + buf)
            buf = buf[-160:] + sent        # 160 字重叠，约一个半句
        else:
            buf += sent
    if buf:
        out.append(prefix + buf)
    return out
```

重叠取 160 字而不是按比例，是因为中文一句话平均 30 到 40 字，160 字能覆盖四到五句，保证跨界的指代关系还在。

## 表格和代码块不要切

这两种内容有个共同特征：脱离上下文就没法解释，但又必须保持整体。一个 30 行的代码块被切成两段，前一段缺少 import、后一段缺少函数签名，模型看到只会瞎猜变量类型。一个 8 行的表格被拦腰切断，表头在上一块，数据在下一块，谁都不知道那列数字代表什么。

做法是先做保护区标记：扫描出所有代码围栏和连续的表格行，把它们替换成占位符 `@@BLOCK_3@@`，按正常逻辑切分，最后再把原始内容还原回去。如果一个块被切点落在占位符内部，就把整个块挪到相邻块，宁可让这一块超长到 2000 字，也不要切断。超长的代价是向量被稀释，切断的代价是信息直接丢失，后者严重得多。

表格还多一层问题。整张表编码成一个向量，语义上是"十几个字段的混合体"，检索时对任何单字段查询都只有微弱响应。表的正确用法通常是让模型看原文而不是靠检索命中，所以我在块的元数据里打一个 `has_table: true`，下游可以选择把整节原文塞进 prompt 而不是只塞这一块。

最后一条经验：块要能单独被读懂。判断标准很土，把块单独贴给一个没看过原文的人，问他"这段在说什么"，答不上来就是切错了。这个检查比任何指标都便宜，一百个块抽样看十分钟就够。
