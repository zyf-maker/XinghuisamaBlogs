「召回率 0.82」这句话在大多数项目里没有意义，因为它没说 k 是多少、没说是块级还是文档级、也没说样本量。我见过一次 A/B 对比，两组分别跑出 0.79 和 0.82，结论是 B 方案更好，实际上差异完全落在噪声范围内。改完切分策略重跑，顺序就反过来了。

## 三个指标的口径

命中率（hit rate）问的是「前 k 条里有没有至少一条相关」，取值只有 0 和 1，最后取平均，所以它其实是"至少命中一次"的比例。召回率（recall@k）问的是「所有相关块里，前 k 条覆盖了多少」，分母是标注的相关块总数。

这两个指标在标注稀疏时会打架。假设一个问题有 5 个相关块，系统召回 2 个，命中率是 1.0，召回率是 0.4。如果标注时只标了 1 个相关块（很常见，标注员找到一个就停了），同一个系统的召回率变成 1.0，虚高得离谱。所以要么把标注做全，要么老老实实只报命中率。

| 指标 | 公式 | 适用 | 陷阱 |
| --- | --- | --- | --- |
| HitRate@k | 命中查询数 / 总查询数 | 单答案问答 | 一个相关块就算满分，掩盖排序问题 |
| Recall@k | 召回的相关块 / 全部相关块 | 多跳、综述类 | 标注不全时虚高 |
| Precision@k | 前 k 中相关块 / k | 上下文预算紧 | k 大时自然偏低 |
| MRR@k | 首个相关块排名倒数的均值 | 只需一条最优 | 后续相关块被忽略 |
| nDCG@k | 折损累计增益归一化 | 有分级相关性 | 需要多级标注，成本高 |

k 的选择要跟下游对齐。如果 reranker 只取前 10 送进 prompt，那报 Recall@50 没有意义，模型看不到第 11 条。反之，如果下游有 reranker，Recall@50 才是真正决定上限的指标，排序质量交给 reranker 解决。

## 样本量：二项分布的置信区间

命中率是伯努利试验的均值，样本量 n、观测命中率 p 时，95% 置信区间的半宽约等于 $1.96\sqrt{p(1-p)/n}$。p=0.8 时，要达到 ±5 个百分点的精度，需要 n≈246；要到 ±3 个百分点，需要 n≈683。

这是最容易踩的坑：50 条查询、p=0.8，标准误 0.057，95% 区间是 [0.69, 0.91]，宽度 22 个百分点。在这个区间里任何 A/B 结论都是猜的。

p 接近 0 或 1 时正态近似失效，用 Wilson 区间。它是闭式解，不用迭代，可以直接写进 CI 脚本。

```python
import math

def wilson(k: int, n: int, z: float = 1.96) -> tuple[float, float]:
    """命中 k 次 / 试验 n 次 的 Wilson 置信区间。"""
    if n == 0:
        raise ValueError("n 必须大于 0")
    p = k / n
    denom = 1 + z * z / n
    center = (p + z * z / (2 * n)) / denom
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / denom
    return max(0.0, center - half), min(1.0, center + half)

def min_samples(p: float = 0.8, half_width: float = 0.05, z: float = 1.96) -> int:
    return math.ceil(z * z * p * (1 - p) / (half_width ** 2))

print(wilson(40, 50))        # (0.670, 0.888)  —— 50 条不够用
print(wilson(200, 250))      # (0.746, 0.845)
print(min_samples(0.8, 0.05))  # 246
```

跑一次就知道 50 条样本有多不靠谱。上面那组 [0.671, 0.883] 意味着真实命中率可能是 0.67 也可能是 0.88。

## 分层抽样比硬堆数量划算

查询不是同质的。简单问题占比 60%、中等 30%、复杂 10%，如果按自然分布抽 50 条，复杂问题只有 5 条，那 5 条里错 2 条就让整体命中率抖 4 个百分点。更糟的是你看不出问题出在哪一层。

我的做法是分层：按「单跳事实 / 多跳推理 / 精确串匹配 / 否定与排除 / 长文档摘要」五类各抽 30 条，总共 150 条。每层单独报命中率和置信区间，整体再报一个加权值。150 条在 p=0.8 时半宽是 6.4 个百分点，比 246 条差一点，但分层后能定位失效原因，信息量高得多。

代价是标注成本。150 条查询乘以平均 4 个相关块，就是 600 次判断。如果库不大，可以让模型先粗筛候选、人只做确认，速度能快三倍，但要留 20% 人工全标做校准，否则模型偏置会污染评测集。

## 常见口径错误

同一个查询的多条改写要算独立样本，不能只算一条。用 LLM 生成 5 种问法来扩充样本是常见做法，但如果这 5 条高度相似，它们的高度相关会让有效样本量远小于名义样本量，置信区间被低估。缓解办法是同一原始问题的改写只取 1 条进评测集，剩下的放到回归集里做稳定性检查。

相关块的定义要写进文档。块级标注和文档级标注算出来的召回率能差 20 个百分点，因为一个长文档被切成 12 块，命中其中 1 块在文档级算满分，在块级只有 1/12。我倾向于块级，因为它直接对应送进 prompt 的内容，但要接受数字会难看。

评测集要冻结版本。每次调参后重新标注，就等于换了考卷，之前的数据全部作废。我用 `evalset/v3.jsonl` 这样的文件名带版本号，加一条 git 提交哈希写在文件头，跑分结果里带上这个哈希，避免"上次那个 0.85 是怎么跑出来的"这类争论。

## 别只看平均值

平均值会把两端抹平。150 条查询平均命中率 0.83，听起来能用，拆开看可能是简单层 0.98、精确串层 0.71、否定层 0.62。后两层才是用户投诉的来源，而它们的样本各只有 30 条，在平均值里的权重只有五分之一。

所以报表要出分布，不只是均值。我的模板里固定三列：每层的命中率、该层的样本数、该层的置信区间。任何一层的区间宽度超过 12 个百分点，就说明这一层的样本不够，需要补标而不是继续调参。

还有一类查询要单独看：零结果查询。就是检索返回为空、或者全部相似度低于阈值的那种。它们在命中率统计里天然算失败，但原因往往是分词或索引缺字段，跟排序算法无关。把这类查询单独列出来，通常能在十分钟内发现一个明显的索引配置错误，收益比调参高得多。

## 一条最低要求

任何对外报出的检索指标，后面都要跟三件事：k 是多少、样本量多少、置信区间多宽。三样缺一样，这个数字就不该被用来做决策。这条规则写进团队的评测模板之后，讨论效率明显变高，因为大家不再争论小数点后第二位。
