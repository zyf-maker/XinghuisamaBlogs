把几家模型 API 都接一遍之后会发现，接口长得像，坑完全不同。签名都是 `messages` 加 `tools`，跑一个 hello world 全都通；一上真实业务，差异集中在三个地方：上下文怎么计费、结构化输出靠什么保证、流式里带了什么额外信息。这三点决定了你的代码能不能只写一套。

## 上下文窗口不只看最大长度

标称 128k、200k、1M 的窗口，实际可用的比标称小。系统会预留一段给输出，或者对超出某个阈值的输入按更高单价计费。

| 维度 | 常见分界 | 影响 |
| --- | --- | --- |
| 最大窗口 | 128k / 200k / 1M 三档 | 决定能否整篇文档塞进去 |
| 长上下文档位 | 超过 128k 或 200k 后单价翻倍 | 预算按最坏情况算就偏高 |
| 有效窗口 | 标称值的 85% 左右 | 留出 8k 输出余量 |
| 长文召回 | 超过 100k 后中段召回下降 | 关键信息放头尾 |

我做过一个 300 页 PDF 的问答，把全文塞进 1M 窗口后，问中间章节的具体数字，模型给出的答案明显比只喂那一章时差。这不是钱的问题，是注意力稀释。所以长上下文不能替代检索，它的正确用途是「整份材料一次性对比」，不是「从大海里捞一根针」。

定价结构必须自己核。各家都按输入、输出、缓存命中共三档计费，但倍率差别很大：输出通常是输入的 4 到 5 倍，缓存命中从输入的 10% 到 50% 不等，长上下文档位在 2 倍左右。这些数字变动频繁，硬编码进代码就是给自己埋雷。

```python
# 把单价放到配置里，按 model 精确匹配，未命中就抛错
PRICING = {
    "gpt-4o-2024-08-06":  {"in": 2.50, "cached": 1.25, "out": 10.00},  # USD / 1M tokens
    "claude-sonnet-4-5":  {"in": 3.00, "cached": 0.30, "out": 15.00},
    "gemini-2.5-flash":   {"in": 0.30, "cached": 0.075, "out": 2.50},
}

def cost(model: str, i: int, c: int, o: int) -> float:
    p = PRICING[model]          # 严格匹配，别用 startswith
    return (i * p["in"] + o * p["out"]) / 1e6 + (c * p["cached"] / 1e6)
```

上面这些单价是某次快照，写死在文档里就会过时。工程上要做的是把价格抽成配置、按精确版本号索引，并且加一个**漂移告警**：当实际扣费与该表算出的值连续三天偏差超过 10%，说明厂商调价了。用 `startswith` 匹配是常见错误，`gpt-4o` 和 `gpt-4o-mini` 会撞在一起。

## 结构化输出有四个可信度等级

「支持 JSON」这句话没有信息量。真正要分清的是下面四级，可靠性依次上升。

| 等级 | 机制 | 保证 | 失败表现 |
| --- | --- | --- | --- |
| 提示词约束 | 在 prompt 里写「只输出 JSON」 | 无 | 前后带解释文字，解析失败 |
| JSON mode | 强制输出合法 JSON | 语法合法 | 字段缺失、类型不对 |
| Schema 约束 | 传 JSON Schema，解码时按 grammar 限制 | 结构合法 | 几乎不会失败 |
| 工具调用 | 用 function calling 承接参数 | 结构合法 | 参数被截断或为空 |

第一级在实际生产里错误率 5% 到 15%，取决于模型大小和提示词长度。第二级能到 1% 以下，但仍然会给你 `{"result": "抱歉我无法回答"}` 这种结构正确、语义错误的东西。第三级靠约束解码，把非法 token 的概率直接置零，是目前最可靠的做法。

约束解码有个副作用：字段顺序会被 schema 顺序固定，而且模型「无法」在中途输出解释性文字来帮助自己推理。对复杂的分类任务，强制结构化反而会让准确率下降，因为模型失去了先写分析再给结论的余地。解决办法是让它先输出一个 `reasoning` 字段（纯文本），再输出结构化字段，顺序在 schema 里控制。

还有一种情况要防：模型输出被 `max_tokens` 截断时，JSON 一定不完整。开结构化输出时必须配 `max_tokens` 足够大，并且在解析失败时检查 `finish_reason == "length"`，这一条能把 60% 的解析错误直接归因。

## 流式响应里的差异

最基础的差异是终止信号。有的在流末尾发一个 `data: [DONE]`，有的直接关连接，有的发一个带 `finish_reason` 的普通帧。只按 `[DONE]` 判断的客户端，遇到直接断流的实现会以为网络中断，触发一次无谓重连。

第二个差异是 usage 什么时候给。有的只在最后一个 chunk 里带完整 usage，中间都是 null，必须显式传参数才返回；有的每帧都不给，只能事后查账单。要按 token 做实时预算的系统，得先确认这一项，否则流式路径上的成本统计永远是零。

第三个是工具调用的分片方式。模型可能是把参数 JSON 一个字符一个字符地流出来，客户端要自己拼 `arguments` 字符串再解析；也可能是最后一次性给全。拼装时最容易犯的错是按 chunk 解析，每收到一片就 `JSON.parse`，必然抛错。正确做法是累积到 `finish_reason` 出现再解析。

```ts
let args = ''
for await (const ev of stream) {
  const d = ev.choices?.[0]?.delta
  if (d?.tool_calls?.[0]?.function?.arguments) {
    args += d.tool_calls[0].function.arguments   // 只拼接，不解析
  }
  if (ev.choices?.[0]?.finish_reason === 'tool_calls') break
}
const parsed = JSON.parse(args)
```

## 我现在的取舍

需要严格结构化的场景，只选支持 schema 约束的那一家，多花的钱比返工便宜。做长文档对比，选窗口最大的，但输入超过 100k 时把关键段落人工复制到 prompt 末尾再做一次。做高频小任务，选最便宜的小模型，因为这类任务的失败模式是格式而非语义，加约束解码就能救。

跨厂商抽象层只做薄薄一层：统一 messages 格式、统一重试、统一日志。别去抽象采样参数，`temperature` 在不同模型上的尺度根本不一致，同样 0.7 一个偏保守一个乱飞。抽象过度会让你失去调参能力，而调参恰恰是控制质量的主要手段。
