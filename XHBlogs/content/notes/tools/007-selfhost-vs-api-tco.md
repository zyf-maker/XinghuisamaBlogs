「自部署省钱」和「自部署更贵」这两个结论都能找到数据支撑，因为大部分人只算了 GPU 单价，没算空闲率、运维工时和峰值冗余。我做过两次迁移决策，一次是从 API 迁到自建，一次是两年后迁回来。把账算细之后，结论取决于三个变量，跟技术偏好无关。

## 账要按「有效吞吐」算，不是按峰值算

GPU 按小时计费，但你只在有请求时才产生价值。这就是自部署与 API 最本质的差别：API 是你为 token 付费，自建是你为**时间**付费。同样的钱买来的是「一直开着」，而不是「用了多少」。

所以第一件事是算清楚真实负载的形状。三个数必须测出来：日请求量、单请求平均 token 数（输入加输出分开）、峰值小时占比。峰值比平均值重要，因为容量按峰值买。

一个具体的例子：日请求 8 万次，平均输入 1800 token、输出 400 token，峰值小时承载全天 12% 的请求。

| 变量 | 值 | 说明 |
| --- | --- | --- |
| 日请求 | 80,000 | 均值 |
| 输入 token/请求 | 1,800 | 含系统提示词与检索 |
| 输出 token/请求 | 400 | 绝大多数被 max_tokens 截住 |
| 峰值小时占比 | 12% | 9,600 请求/小时 |
| 日均 token 总量 | 1.76 亿 | 输入 1.44 亿 + 输出 0.32 亿 |

按 API 计价，即使全用缓存命中价算输入，一天也是几十美元量级；按输出价算，一天上百美元。这个量级下，一张 A100 的租用费（按每月 1,500 到 2,000 美元估算）看起来立刻划算。但这是错的，因为下面四项没算。

## 隐性成本的四项

第一是空闲。容量按峰值小时买：9,600 请求/小时，单卡 7B 在 8k 上下文下大约刚好每小时处理 9,600 次，也就是峰值瞬间打满。而日均只有 80,000 请求，摊到单卡日容量 230,400 上，全天平均利用率 35%。峰值那一个小时满载，剩下 23 小时都在等。

第二是运维。这不是「装一次就行」。模型版本升级、驱动与 CUDA 版本对齐、监控告警、显存泄漏排查、坏卡替换，每一项都要人。按一个熟练工程师每周投入 4 小时算，一年 200 小时；折算成钱，很可能超过省下的 API 费用。

第三是冗余。自建没有多可用区，机器挂了服务就挂。要可用性，至少双实例，容量成本直接翻倍。

第四是质量迭代成本。API 侧换模型是一行字符串；自建侧换模型要重新验证显存、重新压测并发、重新校准量化损失。这让你倾向于「一个模型用到底」，而这在快速迭代期是实质性的劣势。

## 把账写成一个函数

比拍脑袋可靠的做法是把它写成可复算的模型。下面这段是纯算术，把四个假设摊开，改参数就能看结论怎么翻。

```python
import math

def cards_needed(peak_req_per_hour: int, card_capacity: int = 9600, redundancy: int = 2) -> int:
    # card_capacity 是单卡在峰值小时能服务的请求数，7B + 8k 上下文约 9600
    return math.ceil(peak_req_per_hour / card_capacity) * redundancy

def cost_selfhost(cards: int, gpu_hour: float = 2.20,
                  ops_hours: float = 16, ops_rate: float = 90.0,
                  platform: float = 300.0) -> float:
    return cards * gpu_hour * 730 + ops_hours * ops_rate + platform

def cost_api(tok_in: float, tok_out: float, p_in: float = 2.50,
             p_out: float = 10.0, cached: float = 0.6, p_cached: float = 1.25) -> float:
    blended_in = tok_in * (cached * p_cached + (1 - cached) * p_in)
    return (blended_in + tok_out * p_out) / 1e6

cards = cards_needed(peak_req_per_hour=9600)
sh = cost_selfhost(cards)
api = cost_api(4.32e9, 0.96e9)          # 月 5.28e9 token
per_mtok = api / 5280                    # 混合单价，USD / 百万 token
print(cards, round(sh), round(api), round(sh / api, 2), round(per_mtok, 2))
print(round(sh / per_mtok), "M tokens")  # 自建与 API 打平的月用量
```

输出是 `2 4952 17160 0.29 3.25` 和 `1524 M tokens`。在这个负载下自建花 4,952 美元、API 花 17,160 美元，自建只要三分之一；盈亏平衡点落在每月 15.2 亿 token。

两个容易搞反的地方。第一，利用率不是入参。日 8 万请求对上单卡 23 万请求的日容量，利用率必然是 35%，它是结果不是旋钮。第二，卡数取整到整数，`cards_needed` 里的 `math.ceil` 决定了成本是台阶函数而非线性——这一点下面单独说。

## 盈亏平衡点在哪个位置

把上面的模型反过来解，能得到「多少 token 以上自建才划算」。同一组参数下，临界点在每月 15 亿 token（输入加输出合计），也就是每天 5,000 万 token。低于这个量，API 更便宜；高于这个量，自建的优势随规模线性放大。

要注意这个临界点是**分段**的，因为卡数是台阶函数。请求量从 9,000 涨到 9,100 每小时，不会多花一分钱；涨到 9,700，就要多买一张卡，成本直接跳一档。所以真实曲线是一串水平段加陡坡，不是一条平滑直线。

| 部署形态 | 月成本（USD） | 平衡点（月 token） |
| --- | --- | --- |
| 单卡，无冗余，轻运维（每月 8 小时） | 2,626 | 8.1 亿 |
| 双卡，跨机冗余，标准运维（每月 16 小时） | 4,952 | 15.2 亿 |
| 四卡，双副本双卡 | 8,164 | 25.1 亿 |
| 八卡，双副本四卡 | 14,588 | 44.9 亿 |

前两行的平衡点差异主要来自运维工时的假设，不是卡。第三、四行看着像「规模越大越不划算」，其实不是：卡数翻倍的同时可服务容量也翻倍，平衡点同步上移，比值不变。真正决定划算与否的是**峰值占单卡容量的比例**：峰值贴着容量跑，自建就划算；峰值只有容量的三成，钱就烧在空转上。

这也是弹性伸缩救不了的原因。LLM 冷启动要加载几十 GB 权重，从零拉起一个 vLLM 实例通常 60 到 180 秒，分钟级弹性对秒级波动无效。所以按峰值买卡几乎是必然，利用率低就是结构性成本。

| 负载形态 | 峰值占容量比 | 结论 |
| --- | --- | --- |
| 内部工具，工作日 9–18 点 | 35–45% | 中等规模即可自建 |
| 面向企业的批处理 | 60%+ | 早自建早省 |
| C 端低频应用 | 5–10% | 基本不该自建 |
| 有明显峰谷的 SaaS | 15–20% | 混合方案 |

最右一列的「混合」指的是：常态流量走 API，可预测的批量任务走自建。批量任务的特征是能排队、能等、不需要低延迟，正好填补自建机器的空闲时段。这是我认为性价比最高的形态，而不是非此即彼。

## 混合方案的实际形态

路由层按任务类型分流，不按用户分流。判断依据是延迟容忍度和调用量可预测性。

```bash
# 批量任务直接打到自建实例，串行排队即可
llm-batch --input tasks.jsonl --endpoint http://10.0.1.7:8000/v1 \
  --concurrency 16 --max-retries 2 --out results.jsonl

# 交互式请求走托管 API，带缓存前缀
llm-chat --endpoint https://api.example.com/v1 --model MODEL_ID \
  --cache-prefix prompts/system-v14.txt --timeout 20
```

这样自建机器的利用率能从 35% 拉到 60% 以上，同时交互体验不受影响。代价是两套代码路径要维护，得把抽象做薄：只统一 messages 格式和日志字段，不要试图统一采样参数。

## 一个容易忽略的收尾成本

迁移决策里最少被讨论的是退出成本。自建之后，模型权重、推理镜像、压测脚本、监控面板全都绑在特定框架上。两年后想换回 API，或者想换成更新架构的模型，迁移工作量不比当初小。

我的做法是从第一天就把「模型调用」收敛到一个内部接口，业务代码只认 `generate(messages, params)`，实现可以是 HTTP、可以是本地 vLLM、可以是 CLI。这个接口只有二十行，但它让迁移从「重写业务」变成「换一个实现」。第二次迁移时，我花了半天，而不是两周。这个抽象的成本很低，收益却要在很久之后才兑现，所以大部分项目不会做。这正是它值得做的原因。
