坚持本身不是美德。工程上更值钱的能力，是在合适的时候把项目停掉，把时间还给自己。但「感觉不行了」不是判据，它既可能来自数据，也可能来自连续三天没人下载带来的情绪。

下面三条信号都可以直接从后台和账单里读出来，不需要判断力，只需要记录。

## 信号一：留存曲线在第 2 到第 4 周没有走平

日活或周活的留存曲线只有两种形态：一路下滑到接近零，或者下滑后在上方出现一段平台。平台存在说明有一批人把这个产品纳入了固定流程；不存在说明所有人都是来试一次的。

可操作的判定方法是看第 2 周和第 4 周的留存比值。健康的形态是 W4 / W2 大于 0.75，比如 W2 是 30%、W4 是 24%。如果 W2 是 30%、W4 是 8%，这个产品没有形成习惯，再优化界面也没用，因为问题在「不需要每天用」，而不在「不好用」。

有一个例外要区分：低频但刚需的产品，比如一年用两次的报税工具、季度用的对账工具。这类产品看周活会得出完全错误的结论，应该看「同类任务发生时是否被想起」。测法是给用户发一封问询，问上次做这件事时用了什么，如果答的是你的产品，留存成立。

我做过一个周活一直掉的数据看板，从 W2 的 12% 掉到 W4 的 3%。当时以为是图表不够好看，做了三周可视化改版，曲线没变。真实原因是用户每周只看一次数据，而我的产品需要他们每周进来操作三次。产品形态和任务频率不匹配，这不是留存问题。

## 信号二：支持密度随用户增长不下降

支持密度是每千活跃用户的工单数。一个产品如果有明确的边界，这个数会随着文档完善而下降，通常在用户到 500 之后稳定在一个低位。如果它一直高位不下，甚至在涨，说明有一批用户的使用场景根本不在你设计的范围内，而你在用人力硬撑。

这条信号比留存更早出现。留存要四周才能看出来，支持密度两周就有形状。

判定阈值：连续两个月每千活跃用户月工单数高于 100，且工单里超过一半是「装不上」「跑不通」「结果不对」这类根本性问题，而不是「能不能加个功能」。前者是产品没解决问题，后者才是需求。

这时候涨价的思路是错的。工单多意味着交付成本高，涨价只会让付费用户更苛刻，工单更多。我见过一个工具把价格从 39 提到 99 想用价格筛掉麻烦用户，结果退款率从 5% 升到 14%，因为留下来的用户期待值同步提高了。

## 信号三：机会成本超过项目本身的期望收益

这条最容易被忽略，因为它在账本外面。算法很直接：这个项目最近三个月平均每月净收入，除以你每月投入的小时数，得到每小时产出。再拿它和你做别的事情的时薪比。

```python
def should_quit(mrr_net, hours_per_month,
                alt_hourly=300, months_left_investable=12,
                min_monthly_growth=-0.05):
    hourly = mrr_net / max(hours_per_month, 1)
    gap = alt_hourly - hourly
    opportunity = gap * hours_per_month * months_left_investable
    print(f"时薪 {hourly:.1f} 元，机会成本 {opportunity:.0f} 元")
    # 低于替代时薪的一半，且没有正增长，才判放弃
    return hourly < alt_hourly * 0.5 and min_monthly_growth <= 0

print(should_quit(800, 45))    # 17.8 元/小时  -> True
print(should_quit(9000, 40))   # 225 元/小时   -> False
print(should_quit(800, 45, min_monthly_growth=0.08))  # 有增长 -> False
```

第一组 17.8 元每小时，12 个月机会成本十五万以上。这个数不代表必须停，它代表「继续投入的代价是多少」，把这个数摆在桌上，决策就不再靠情绪。

第二组 225 元每小时，低于 300 的替代时薪，但只差 25%，脚本判 False。阈值故意设在替代时薪的一半，不是设成 300：低于一半说明你在用远低于市价的价格买自己的时间，那才是明确信号；差 25% 属于正常波动，靠趋势判断而不是靠单点。

第三组是同一组数据加了 8% 的月增长，判 False，因为还有改善空间。趋势怎么读：看最近三个月的月净收入斜率，连续三个月环比增长超过 5% 就给时间，连续三个月持平或下滑，再叠加支持密度不降，三条信号同时成立才是该收的时候。

## 三条信号的关系

单条信号不足以做决定，三条同时出现才有结论。它们的时间尺度不同：支持密度最快，两到四周；机会成本按月算，三个月能看出斜率；留存最慢，要六到八周。

| 组合 | 判断 | 动作 |
| --- | --- | --- |
| 仅留存差 | 形态问题 | 改任务频率或产品形态，给 6 周 |
| 仅支持密度高 | 边界问题 | 缩范围或写文档，给 4 周 |
| 仅机会成本高 | 优先级问题 | 降投入不停止，改成维护模式 |
| 留存差 + 支持密度高 | 需求不成立 | 停止新增投入，进入收尾 |
| 三条同时成立 | 明确止损 | 停止，通知用户，保留只读 |

「进入收尾」和「停止」要区分。收尾是停止开发、保留服务、把文档补齐、给用户一个迁移路径，通常再花两周。直接关停会让已有的付费用户变成负面口碑，这个成本比多跑两个月更高。

## 沉没成本的具体形态

最难的从来不是算这三条，而是承认前六个月白干了。有个特别好用的做法：在项目开始时写下「如果三个月后 X 指标低于 Y，我就停」，写在文件里，不要在脑子里。到了时间点，执行那句话，不要重新谈判条件。

因为人在投入之后会重新解释自己的判断，把「没到预期」解释成「还差一点」。写下阈值的作用就是把判断权交给三个月前的自己，那个人没有被沉没成本污染。

我关掉过一个做了七个月的项目，月净收入 400 元。关停当天把代码归档、把域名续费一年保留跳转、给 60 个付费用户发了一封说明信并提供退款。有两成的人要求退款，八成的人没回。半年后回头看，那七个月里学到的东西后来用在了另一个产品上，价值远超前者的收入。这个结论不能拿来安慰自己，但它说明一件事：停掉一个项目不等于浪费，继续一个错的项目才是。
