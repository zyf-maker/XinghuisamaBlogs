第一版做不完，几乎从来不是工期问题，而是范围问题。同样一个想法，A 用三周上线，B 用三个月还在做设置页，差别不在手速，在于 B 把「以后一定要有」的东西提前做了。

砍功能有个简单的判据：这个功能如果不存在，用户还能不能完成主流程。能，就砍；不能，再问它是不是主流程的一部分。按这个问法走一遍，二十个功能通常只剩四到六个。

## 六类必砍项

第一类是账号体系。除了必须要跨设备同步的产品，首版用一个邮箱收单、一个本地存储就够了。做注册、登录、找回密码、第三方授权，加起来是两三天，而它在验证阶段不产生任何信号。用户会不会因为要注册而流失，这个问题等有了付费用户再问。

第二类是通知与消息。站内信、邮件提醒、Webhook、微信推送，四套写下来是两周。首版用一封手工邮件通知，等你确认用户真的在意这件事再说。

第三类是权限与多角色。管理员、普通成员、只读、访客，一套 RBAC 至少三天，还要配一套界面。首版只有一个角色，所有人都是所有者。

第四类是导出格式的穷举。支持 PDF、DOCX、Markdown、HTML、CSV，每种都有排版坑。首版只做一种，而且做你访谈里出现次数最多的那种。我在一个报告生成工具里首版做了五种导出，其中三种整月零调用。

第五类是设置面板。主题、快捷键、默认值、语言，这些是产品成熟后才需要的调节旋钮。首版把默认值调到能用的程度，不提供开关。

第六类是集成。GitHub、Notion、Slack、飞书，接一个平均两天，还要处理授权过期和限流。首版用「复制粘贴 + 手动导入」，用户抱怨的时候正好是优先级信号。

## 该留下的四件事

砍到只剩骨架之后，这四件必须留：

- 主流程的一条完整路径。从输入到输出，中间不断，哪怕中间有一步是人工。
- 结果的可信度。输出错了要能看出来，至少要有一个校验或示例对照。
- 付费入口。没有付费入口的 MVP 只能验证「有人用」，验证不了「有人买」。
- 最简单的数据记录。每次调用记一行：谁、什么时候、输入多大、成功与否。这是后面所有判断的基础。

第三和第四条最常被省。省掉付费入口，你会得到一个很热闹但无法定价的产品；省掉数据记录，两周后你只能靠回忆判断哪些功能被用了。

## 用一张表排序，别用直觉

把所有候选功能列出来，按四列打分。分数不追求精确，只追求让分歧显形。

| 功能 | 主流程必需(0-3) | 验证价值(0-3) | 实现天数 | 结论 |
| --- | --- | --- | --- | --- |
| 单文件上传与解析 | 3 | 3 | 2 | 做 |
| 结果对照预览 | 3 | 2 | 1.5 | 做 |
| 批量处理 | 1 | 2 | 3 | 押后 |
| 多格式导出 | 1 | 1 | 4 | 砍 |
| 账号与历史记录 | 1 | 1 | 3 | 砍 |
| 支付与订单 | 2 | 3 | 2 | 做 |
| 团队共享 | 0 | 0 | 5 | 砍 |
| 使用量统计 | 1 | 3 | 0.5 | 做 |

排序规则是「主流程必需 + 验证价值」除以天数，低于 1 的一律不进首版，等于 1 的看有没有替代方案。批量处理那行算出来正好 1.0：让用户重复操作五次能接受，就押后。

用脚本跑一遍能省掉会议上的争论：

```python
feats = [
    ("upload",   3, 3, 2.0), ("preview",  3, 2, 1.5),
    ("batch",    1, 2, 3.0), ("export",   1, 1, 4.0),
    ("account",  1, 1, 3.0), ("billing",  2, 3, 2.0),
    ("sharing",  0, 0, 5.0), ("usage-log",1, 3, 0.5),
]
ranked = sorted(feats, key=lambda f: (f[1] + f[2]) / f[3], reverse=True)
for name, must, value, days in ranked:
    score = (must + value) / days
    tag = "keep" if score > 1.0 else ("borderline" if score == 1.0 else "cut")
    print(f"{name:10s} score={score:5.2f} {tag}")
```

输出里 usage-log 排第一、sharing 排最后，batch 落在 borderline。这跟直觉相反：使用量统计只要半天，却能回答「哪个功能真正被用了」，它的分数比上传解析还高。

## 时间盒比清单更硬

清单只能防止做多，不能防止做久。加一个时间盒：主流程的端到端版本必须在 10 个工作日内可被陌生人独立跑通。到点没通，砍的是范围，不是延期。

我现在的做法是把首版写成一句可以验收的话：「一个陌生人拿到链接，在 5 分钟内完成一次完整任务，不需要问我任何问题。」这句话同时约束了范围、引导和稳定性。做不到，说明还有隐藏的前置条件没被处理，那些条件通常就是漏掉的功能。

## 一个反例

有个把 LaTeX 公式转图片的小工具，首版我坚持做了模板库、历史记录、自定义字体、暗色主题，三周半上线。数据是：模板库使用率 2%，历史记录 0 次打开，字体设置改过的人有 3 个，主题切换有 40% 的人点过。

真正被反复用的是「粘贴即出图」这一个动作。如果首版只做这个，两天就能上线，剩下三周可以拿去推渠道。主题切换那 40% 是个陷阱：它看起来受欢迎，但不产生任何价值，用户只是无聊时点着玩。判断一个功能值不值，看它有没有改变用户完成任务的方式，而不是看点击量。

首版的目标不是少做功能，而是让唯一的那个假设尽快接触真实用户。剩下的功能，等有数据再说，那时候砍和加都有依据。
