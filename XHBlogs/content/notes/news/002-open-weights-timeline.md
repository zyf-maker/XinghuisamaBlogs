开源权重这两年更新得很快，能带走的东西不多。榜单名次每个月都在换，发布日期过半年就没有参考价值。真正稳定的只有三条结构约束：参数量换算成显存是多少、量化到几比特开始掉能力、许可协议允许你做什么。这三条不随版本变，只随架构变。

截至目前公开信息，主流开源权重的尺寸档位大致落在 7B 以下、30B 上下、70B 上下、200B 以上四段，分别对应单卡、单机双卡、单机八卡、多机。这个分布不是巧合，是硬件决定的。

## 参数量到显存不是一比一

权重占用的字节数等于参数量乘以每参比特数再除以八。fp16 是两字节一参，于是 70B 就要 140GB，单张 80GB 卡放不下。int8 减半到 70GB，勉强塞进一张卡，但留给 KV cache 的余量只有几个 G。

真正把显存吃掉的常常是 KV cache，不是权重。它的大小是 2 乘以层数、乘以 KV 头数、乘以每头维度、乘以序列长度、乘以并发数、乘以每元素字节数。前面那个 2 是 key 和 value 各一份。GQA 之所以成为标配，就是因为 KV 头数可以从 64 压到 8，KV cache 直接降到八分之一。我第一次算这块的时候漏了并发数，按单条序列估出 3GB，实际压测 16 并发时是 47GB，服务直接 OOM。

| 参数量 | fp16 权重 | int8 权重 | 4bit 权重 | 现实部署形态 |
| --- | --- | --- | --- | --- |
| 7B | 14GB | 7GB | 4GB | 单张 24GB 卡，余量充足 |
| 32B | 64GB | 32GB | 18GB | 单张 80GB 卡，或两张 48GB |
| 70B | 140GB | 70GB | 39GB | 两张 80GB 卡张量并行 |
| 200B 级 | 400GB | 200GB | 110GB | 四到八卡，需专家并行 |

4bit 那一列不是权重乘以四分之一那么干净。量化元数据、分组缩放因子、部分层保留高精度，实际文件会比理论值大百分之五到十。算显存的时候我一律按理论值加一成，剩下的留给 KV cache 和临时 buffer。

## 量化损失不均匀

困惑度涨零点几听着无害，落到具体任务上不是这么回事。我拿一份 200 条的字段抽取集测过同一个 32B 模型：fp16 准确率 91.5，Q8 是 91.0，Q5 是 90.0，Q4 掉到 87.5。整体看只掉了四个点，但拆开看，长尾实体和带单位的数值这两类掉了十一个点，常见字段几乎没动。

掉的顺序有规律。先坏的是精确复现：编号、金额、日期、代码里的符号。再坏的是长尾知识。最后才是通用语言能力。所以用困惑度或通用榜单判断量化档位，等于用最不敏感的那个指标做决定。

我的做法是固定集里专门放二十条“必须逐字正确”的样本，比如订单号、十六进制颜色值、带千分位的金额。Q4 在这些样本上的失败率是 fp16 的六倍，这个数字比任何平均分都有说服力。如果业务里没有这类要求，Q4 完全够用；如果有，就老老实实上 Q5 或 Q8，多花的显存是买准确率。

另一个容易忽略的点是量化对上下文的影响。低比特量化会放大长上下文里的位置漂移，同样的针测试，fp16 在 90% 位置能召回，Q4 就开始丢。这不是量化算法的问题，是误差在长序列上累积。

## 许可协议分成三类

这一块比技术参数更容易出事，因为它不报错，只在法务 review 的时候爆。

| 维度 | 宽松许可 | 社区许可 | 研究许可 |
| --- | --- | --- | --- |
| 商用 | 允许，无附加条件 | 允许，但有规模或命名条款 | 需单独申请 |
| 衍生物命名 | 无要求 | 常要求保留原前缀或标注改动 | 视条款而定 |
| 再分发 | 保留版权与 NOTICE 即可 | 需附带原协议全文 | 多数不允许 |
| 输出内容归属 | 归使用者 | 多数归使用者，个别有例外 | 常有争议 |
| 专利授权 | 明示授予 | 部分明示，部分沉默 | 通常无 |

读协议的顺序我固定为三步。先看定义段里“衍生物”怎么界定，微调算不算、蒸馏算不算。再看商用条款里的触发条件，是按月活还是按营收。最后看终止条款，违反之后怎么恢复。这三段决定了你能不能用，其余都是细节。

有一类坑在“输出归属”上。多数协议把模型输出归使用者，但个别协议对“用模型生成训练数据再训模型”这一路径有额外限制。做蒸馏之前必须确认，不然整个数据集都得作废。

## 权重格式绑定了工具链

safetensors 现在是事实标准，它把张量偏移写在头部，加载时能做内存映射，也不会像 pickle 那样执行任意代码。gguf 是另一条线，面向本地推理，量化档位直接编进文件名。问题是档位命名各家不统一，Q4_K_M、Q4_0、IQ4_XS 的差别在分组方式和校准数据上，光看名字判断不了质量。

所以我用文件大小反推比特数，比读文件名可靠。

```bash
# 按目录里的权重文件反推每参比特数，判断实际量化档位
# 用法: ./bits.sh ./model-dir 32000000000
dir="${1:?model dir}"
params="${2:?param count}"

bytes=$(find "$dir" -name '*.safetensors' -o -name '*.gguf' \
        | xargs -r du -cb 2>/dev/null | tail -1 | cut -f1)

awk -v b="$bytes" -v p="$params" 'BEGIN{
  bpw = b * 8 / p
  printf "files: %.2f GB\nbits/param: %.2f\n", b/1024/1024/1024, bpw
  if (bpw > 15)      print "verdict: fp16/bf16"
  else if (bpw > 8.5) print "verdict: fp8 或混合精度"
  else if (bpw > 5.0) print "verdict: ~6bit"
  else if (bpw > 4.2) print "verdict: ~5bit"
  else               print "verdict: ~4bit"
}'
```

这个脚本我放在部署脚本前面跑，防止拉了标称 fp16 实际是 Q4 的仓库。参数用错一次就会得出荒谬结论，所以参数量我从 config.json 里读，不手抄。

## 上下文长度要分训练值和推理值

标称 128K 的模型，多数是在 8K 或 16K 上训练，再用位置插值或 YaRN 外推到 128K。外推会改变短上下文的表现，尤其是位置敏感的任务。判断方法很简单：同一份 2K 的输入，原生长度和外推长度各跑一次，看输出是否一致。不一致就说明外推有问题，长上下文能力要打折扣。

另一个现实约束是 prefill 时间。128K 输入的 prefill 在单机上要几十秒，交互式场景基本不可用。这类长上下文更适合离线批处理，不适合放在对话链路里。

## 选型的顺序

先定业务要求里最硬的那条：是必须逐字准确，还是可以接受改写。这一条决定量化档位。再用显存公式倒推能上多大参数，别反过来。最后过一遍许可协议的定义段和终止段，确认商用路径。

顺序反过来做的后果我见过：先看榜单选了个大模型，算完显存发现要八卡，再降到 4bit，最后准确率不达标，整个方案推倒重来。

榜单只能告诉你它在一个通用分布上大致多强，告诉不了你在你的分布上能不能用。这中间的差距，只能靠自己的固定集去量。
