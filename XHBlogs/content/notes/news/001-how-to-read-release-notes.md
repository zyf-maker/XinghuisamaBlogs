一份发布公告里能直接采信的东西只有三样：参数量、权重文件大小、许可协议原文。其余数字都要自己复算。上个月我按公告把一套问答服务从 A 换到 B，公告口径是“综合成本下降 40%”，月底账单只降了 11%。差额出在两处：输出与输入的 token 比，我按 1:3 估，真实流量是 1:6；长 system prompt 的缓存命中率从 82% 掉到 41%，因为新模型的模板把 system 放到了变量后面，前缀对不上。

## 先确认它在跟谁比

“提升 12 个点”这种句子缺三个信息就没法用：基线是哪个版本、评测代码有没有公开、解码参数是否一致。我见过同一家两代模型之间做对比，也见过自己开了 8-shot 的结果去比对手 0-shot 的公开数字。判断方法很土，翻附录的评测配置表，如果只有模型名没有 prompt 模板和采样参数，这个数字就当不存在。

基线不明的数字还有一个麻烦：它不可复现，也就无法在半年后重新验证。我现在的做法是只记录能自己跑出来的结果，公告里的数字进文档时统一标注“厂商口径”，和自己的 200 条固定集结果分开存。

## benchmark 的三种挑选手法

第一种是挑子集。正文列九个，附录列三十个，落选的通常是掉分的那些。第二种是换裁判。用自家模型当 judge，胜率能抬五到八个点，换成人工标注或第三方裁判就回落。第三种是分档报告。同一份成绩按难度切三档，只报最容易那档的均值，中档和困难档放在小字里。

三种手法都不算造假，但没有一种能直接迁移到你的任务上。公告测的是通用能力，你的业务是固定字段抽取、固定格式改写、固定领域的判断，这三件事的排序经常和榜单相反。我的固定集是从真实流量里抽 200 条，标注一次用半年，每换一次模型重跑一遍，只看任务级准确率和格式合规率。

## 上下文长度是标称值

标称 200K 的模型，能稳定用的往往只有前面一段。原因不在窗口本身：位置编码在远端衰减，注意力被前面内容稀释，prefill 时间随长度增长得比线性快。我实测过一份 128K 的模型，把关键信息放在 90% 位置时召回是 62%，放在 10% 位置时是 97%。同一份模型，同一段文本，只改位置。

还有一层容易漏：价格按长度分档。不少价目表写着“超过 32K 的输入部分按 1.5 倍计价”，公告的“每百万 token 多少钱”用的是最短那档。真按 100K 上下文跑检索增强，单价和公告差一大截。

## 价格表要按缓存和输出重算一遍

现在的价目表基本是三段：缓存写、缓存读、输出。拿一份典型结构举例，输入 3.00、缓存写 3.75、缓存读 0.30、输出 15.00，单位都是每百万 token。2000 token 的 system prompt 每轮重发一次，十万次请求就是两亿输入 token。全部命中按 0.30 算，全部不命中按 3.75 算，差十几倍。公告不会写这一条，因为它是你的架构决定的，不是模型决定的。

输出那一段更贵。同一条回答 900 token，按 15.00 计价，十万次就是 1350 美元，占账单的大头。所以“输入降价 50%”这种消息，对你的实际成本影响可能只有几个点。

## 迁移成本只看四件事

第一是分词器。同一段中文在两家分词器上的 token 数能差 18% 到 30%，按 token 计价的预算直接失真，按 token 判定的截断位置也跟着变。

第二是对话模板。system 的位置、是否允许连续两条 user、工具结果怎么包，各家不同。把手写 prompt 原样搬过去，前五十条里必然有几条输出格式全乱，而且不报错。

第三是结构化输出。约束解码和后处理重试是两种实现，失败率差一个数量级。公告写“支持 JSON 模式”，往往只保证语法合法，不保证 schema 合规。

第四是超长处理。超过窗口时是报错、截头还是截尾，决定了你的降级逻辑要不要重写。

## 一张追问表

| 公告里的说法 | 该追问什么 | 判断依据 |
| --- | --- | --- |
| 综合能力全面领先 | 基线版本号、评测代码、采样参数 | 附录有没有配置表，没有就不采信 |
| 上下文 1M | 有效召回区间、超长段单价 | 自己放针测 10% 与 90% 位置 |
| 价格下降 50% | 降的是哪一段、缓存价是否同降 | 按自己的输入输出比例复算 |
| 支持工具调用 | 并行调用、参数校验失败后的行为 | 跑三个串联工具看错误传播 |
| 开源权重 | 许可是否允许商用、衍生物是否同名 | 读 LICENSE 原文，不看博客转述 |
| 推理速度提升 3 倍 | 对比的硬件、batch、输出长度 | 同机同 prompt 测首字延迟和吞吐 |
| 中文能力增强 | 中文 token 数、标点与数字处理 | 用自家语料数 token，别信示例 |

## 复算脚本

把真实流量结构代进去，两个价目表放一起比，差价立刻现形。

```python
# 按自己的 token 结构复算月成本，避免被公告的“单价”带偏
from dataclasses import dataclass

@dataclass(frozen=True)
class Price:
    name: str
    cache_write: float  # 美元 / 百万 token
    cache_read: float
    output: float

A = Price("A", 3.75, 0.30, 15.00)
B = Price("B", 2.50, 0.25, 12.00)

def monthly(p: Price, reqs: int, sys_tokens: int, user_tokens: int,
            out_tokens: int, hit_rate: float) -> float:
    cached = sys_tokens * hit_rate
    fresh = sys_tokens - cached + user_tokens
    cost_in = reqs * (cached * p.cache_read + fresh * p.cache_write) / 1e6
    cost_out = reqs * out_tokens * p.output / 1e6
    return cost_in + cost_out

base = dict(reqs=100_000, sys_tokens=2_000, user_tokens=600, out_tokens=900)
for hit in (0.82, 0.41):
    for p in (A, B):
        print(f"hit={hit:.0%} {p.name}: ${monthly(p, hit_rate=hit, **base):,.0f}")
```

跑出来的结果：命中 82% 时 A 是 1759 美元、B 是 1361 美元；命中掉到 41% 时 A 是 2042 美元、B 是 1546 美元。B 确实便宜两成出头，但离公告的 40% 差得远，而且缓存一失效，两家的差距还会缩小。

## 我踩过的那次

换模型第一周，p95 延迟从 1.9 秒涨到 3.4 秒。查了两天才定位：新模型回答更啰嗦，平均输出从 700 token 涨到 980，而且 JSON 校验失败重试率到了 7%，每次失败都要重发一遍完整上下文。改法很直接，加 `max_tokens` 上限、把 schema 约束前移、把 system prompt 里不变的部分放到最前面恢复缓存命中，延迟回到 2.1 秒。

那次的教训不是“新模型不好”，是公告只给了平均值，而延迟和成本都由分布尾部决定。

## 三条硬规则

只信能自己复现的数字，公告数字一律标注来源。价格按自己的 token 结构算，不看单价看账单。迁移之前先跑固定集，跑完再谈灰度。

这三条执行下来，选型会慢两天，但省掉的是上线后两周的返工。
