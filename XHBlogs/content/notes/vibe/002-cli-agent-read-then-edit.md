## 直接给指令是最贵的做法

打开终端，输入"帮我把支付回调改成幂等"，然后回车。这个动作的成本在一小时后才显现：diff 里有十七个文件，其中九个跟幂等无关，两个删掉了防御性判断，还有一处把 `except Exception` 换成了裸 `pass`。

问题不在模型能力，在流程缺了"读"这一步。代理对仓库的认知来自检索片段，它不知道 `payment/` 下的重试逻辑是三年前为了修重复扣款加的，也不知道那段丑陋的 `if retry_count > 3` 是监控告警的触发点。它只知道你让它改幂等。

先读后改，指的是把"理解"显式变成一个可检查的步骤，而不是让它在生成代码时顺带完成。

## 三段式：读、写、审

第一段只读，产出约束清单。提示写成这样：

```
只读，不改文件。找出支付回调和幂等相关的全部代码路径，
列出：入口函数、状态存储、已存在的去重手段、重试逻辑、
相关测试。给文件路径和行号，不要给建议。
```

输出通常五到十条，你扫一眼就知道它有没有读懂。读歪了就补一句"注意 `webhook/retry.py` 里的补偿任务"，再跑一轮。这一步花两分钟，省下后面半小时。

第二段写，但限定范围。约束清单之后接：

```
按上面清单，只改 webhook/handler.py 里的 process_callback，
保持函数签名不变。不改 retry.py，不改 migrations。
需要新增辅助函数就放在同文件末尾。
```

"只改哪个文件、保持什么不变、新增代码放哪"这三件事说清楚，越界概率大幅下降。相反，"顺便优化一下"这类词必须去掉，它是范围失控的入口。

第三段审 diff。不要用 `git diff` 全量看，先看统计：

```bash
git diff --stat
git diff -U0 -- '*.py' | grep -E '^[+-][^+-]' | wc -l
```

第一行看文件数，超过预期就 `git checkout -- <多余文件>` 回退。第二行看净增删行数，改一个函数通常几十行，出现三百行说明它在重构别的东西。确认范围后再逐个文件读 diff，重点看三处：异常处理有没有被简化、公开接口有没有变、日志和指标有没有丢。

## 限定范围的四把锁

| 手段 | 生效方式 | 强度 | 代价 |
| --- | --- | --- | --- |
| 提示里点名文件 | 单次对话 | 中 | 需自己先定位 |
| `--allowedTools` 白名单 | 进程级 | 强 | 编排变复杂 |
| 分支隔离 + 事后 diff | 仓库级 | 强 | 多一次合并 |
| 只读工作副本 | 文件系统级 | 最强 | 需额外目录 |

实际用法是叠加。默认在独立分支上跑，改完 `git diff develop --stat` 核对；涉及核心模块时给一个只读副本，让它把补丁写到 `/tmp/patch.diff`，我再手工 apply。文件系统权限比任何提示词都硬，副本里没有写权限，它就只能输出方案。

`--allowedTools` 值得单独说。把 `Bash` 限制成 `Bash(git diff:*)`、`Bash(pytest:*)`，代理就没法跑 `rm`、`pip install`、`npm publish`。我在一个老项目上被 `npm install` 静默升级了三个传递依赖，锁文件改了四十行，找了两小时。

## 让它自己验证

改完之后别急着看代码，先让它跑测试并把原始输出贴回来：

```
运行 pytest tests/test_webhook.py -q，把完整输出贴出来。
失败的话先只解释原因，不要改代码。
```

"先解释不要改"很关键。不加这句，它会连续改五轮把测试改绿，方式可能是放宽断言。看输出时确认三件事：测试真跑了（有收集数量）、失败是预期的、通过的数量对得上。

没有测试覆盖的模块，退一步让它写一个最小复现脚本。脚本能跑通再谈改动，比读 diff 更可靠。

## 什么时候不值得

改动跨度小于三十行、你已经知道怎么写的，自己动手更快。流程的固定开销大约十分钟，用于读和审；只有改动涉及多处调用、需要跨文件一致性时，这个开销才划算。

另一类不适合的是"我不知道要什么"的探索。先读后改假设你能写出约束清单，探索阶段写不出来。这种时候让它做只读调研，产出方案对比，人再定。

## 一个具体节奏

我现在的循环是四步，每步之间都停：

1. `git switch -c ai/order-idem` 建隔离分支。
2. 只读提示，产出清单，我改两处它漏掉的。
3. 限定文件写，`--allowedTools` 只给读和测试。
4. `git diff --stat` 核对，逐文件读，跑测试，`git commit -m "..."` 我手写。

第四步的提交信息一定自己写。让代理生成的 message 往往把"改了哪些文件"描述得很全，却说不清"为什么这么改"，半年后看历史毫无用处。
