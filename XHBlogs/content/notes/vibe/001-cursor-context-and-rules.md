## 上下文不是全库注入

编辑器类工具（Cursor、Windsurf 一类）在提问时并不会把整个仓库塞进模型。流程是：先建索引，提问时做检索，把命中的代码块拼进 prompt。这个前提决定了后面所有取舍——为什么它有时"看不见"你明摆着的代码，为什么规则文件越长越不听话。

索引的单位是 chunk，不是文件。一个八百行的 `service.py` 会被切成十几块，每块带 embedding。你问"退款状态机在哪"，系统按语义相似度召回若干块，再按预算裁剪。文件名、函数名、注释都参与相似度计算。命名糟糕的模块几乎不可能被召回，哪怕它就在眼皮底下。

我在一个 monorepo 上踩过：核心逻辑在 `pkg/legacy/helper.ts`，问了三轮都被指向一个新建的空壳 `refund-flow.ts`，因为后者语义上更"像"。解决办法不是换问法，是显式 @ 那个文件，或者把 `legacy` 目录写进规则的事实段。

索引质量先于提问技巧。做三件事：`.cursorignore` 里排除 `dist`、`node_modules`、生成的 `.d.ts`、mock 数据；给每个模块补一行文件头注释说明职责；把散落的 `utils` 拆开。这三件事做完，检索命中率的提升比调整任何 prompt 都明显。

还原一下被我用到最多的场景：报错栈指向 `pkg/legacy/helper.ts:412`，我直接把栈贴进对话，它会按行号定位到那个 chunk。行号比文件名更有用，因为行号锁定了 chunk 边界，绕开了相似度排序。

## 规则文件是每轮都要付的税

`.cursorrules`（新版本是 `.cursor/rules/*.mdc`）会随每次请求作为系统提示发出去。它不进检索，不被裁剪，不会被"忘记"。两个后果：它是唯一稳定的约束通道；它的成本按请求次数线性累加。

一份六百行的规则文件约八千到一万 token。一天两百次请求就是两百万 token 的固定开销，钱是小事，注意力稀释才是问题——规则太长时，模型对靠后条目的遵守率明显下降，前面几段退化成背景噪音。

我的经验值是四百行以内，硬约束不超过三十条。超过就拆成目录级规则，用 `.mdc` 的 `globs` 只在相关文件被编辑时注入。

## 写事实和禁令，不写形容词

无效写法：请编写优雅可维护、符合最佳实践的代码，注意性能。

有效写法：

- 数据库访问一律走 `db.session`，不直接 import 驱动。
- 新增接口必须在 `api/v1/__init__.py` 注册路由，漏了会 404。
- 测试用 pytest，命令 `pytest -x -q`。

区别在可验证性。形容词无法被检验，模型只能读成语气；具体事实和禁令能对照执行。规则里每一条都该能回答"违反了会在哪里炸"。

## 三种规则的作用范围

| 类型 | 位置 | 注入时机 | 典型成本 | 适合内容 |
| --- | --- | --- | --- | --- |
| 全局规则 | 用户设置 | 每次请求 | 每轮固定 | 语言偏好、提交信息格式 |
| 项目规则 | `.cursor/rules/*.mdc` | 按 `globs` 匹配 | 命中时固定 | 测试命令、目录约定 |
| 文件引用 | `@File` / `@Codebase` | 单次对话 | 单次 | 本次任务的输入 |

全局规则控制在二十行内。项目规则按目录拆，`src/api/**` 和 `src/ui/**` 的约束本来就不一样，混在一份里必然互相污染。

## 一份能用的骨架

```mdc
---
description: 后端服务通用规则
globs: ["src/**/*.py"]
alwaysApply: false
---
# 运行
- 装依赖：uv sync
- 测试：uv run pytest -x -q
- 单文件：uv run pytest tests/test_order.py -q

# 事实
- 配置从 app.config.settings 读，不读环境变量原文
- 写操作包在 with db.transaction(): 里
- 时间一律 UTC，用 datetime.now(timezone.utc)

# 禁令
- 不改 migrations/ 下已提交的文件，新改动写新迁移
- 不引入新依赖，除非我在对话里明确同意
- 不重排 import，isort 配置与 CI 不一致
```

`alwaysApply: false` 配 `globs` 是成本控制的关键：只有编辑匹配文件时才注入。这份骨架四十行，覆盖了八成的重复叮嘱。

## 冲突与优先级

全局规则、项目规则、目录规则同时存在时，冲突几乎必然发生。我观察到的行为是：越具体、越靠近当前文件、越靠后的条目，遵守率越高。结构上就该"全局最松、目录最紧"，把最硬的禁令放在目录级。

另一个坑是把规则写成 README 摘要。叙述性文字会被当成参考资料，而不是约束。规则里出现"本项目致力于……"这种句子，基本等于烧 token。

## 该删的时候要删

规则解决的是"每次都一样的约束"。只对这次任务成立的约束写在对话里，别落盘。规则文件是长期资产，一直在计费。

我每月清一次：已经把约束下沉到 lint 配置、类型检查、CI 脚本的条目，直接从规则里删掉。工具能强制执行的，不必再让模型记一遍。
