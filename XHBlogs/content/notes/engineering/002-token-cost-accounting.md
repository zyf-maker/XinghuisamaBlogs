线上产品里，成本问题几乎都不是「模型太贵」，而是账算错了。我见过按输出 token 定价做预算、结果被长上下文输入打穿的；也见过把缓存命中当免费额度用、被 TTL 到期后的回源账单反噬的。要控成本，先把计量口径钉死。

## token 是被接口定义的，不是被字数定义的

同一个中文段落，用不同 tokenizer 数出来能差 15% 以上。原因很直接：中文在多数 BPE 词表里是 1 个汉字 1 到 2 个 token，标点、数字、中英混排的切分规则各家不同。用 `len(text) / 1.5` 估算只适合做量级判断，做预算必须用官方 tokenizer 实际编码。

不要用「字数 × 系数」反过来推费用。正确的顺序是：先用 tokenizer 数，再乘单价。

下面这段是本地核算的基本动作，不依赖任何 SDK：

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

def count(messages: list[dict]) -> int:
    # 每条消息有固定结构开销，role 与分隔符各占几个 token
    per_msg, reply_prime = 4, 3
    total = reply_prime
    for m in messages:
        total += per_msg + len(enc.encode(m["role"])) + len(enc.encode(m["content"]))
    return total

msgs = [{"role": "system", "content": "你是助手，回答不超过三句。"},
        {"role": "user", "content": "解释一下 SSE 的心跳机制"}]
print(count(msgs))  # 40；本地口径与云端计数通常差 ±1~2
```

那 4 和 3 这类常数是历史经验值，换模型就会变。真正落地时，唯一可信的数字是响应里的 `usage` 字段。所以既要用本地 tokenizer 做**事前预算**，也要用 `usage` 做**事后对账**，两者长期偏差超过 5%，说明词表版本变了，得更新本地计数。

## 输入侧才是大头

一个典型的编码助手请求，结构大致是这样：

| 组成 | token 量级 | 是否可变 | 优化手段 |
| --- | --- | --- | --- |
| 系统提示词 | 800–2500 | 半固定 | 前缀缓存、裁剪示例 |
| 工具定义 | 1200–4000 | 固定 | 按需注入，不要全量下发 |
| 检索片段 | 2000–15000 | 波动 | 重排后截断，限制条数 |
| 对话历史 | 每轮增长 | 线性 | 滚动摘要，滑动窗口 |
| 当前问题 | 50–500 | 小 | 无需优化 |

工具定义那一栏最容易被忽略。十来个工具、每个带完整 JSON Schema 和描述，轻松吃掉 3000 token，而九成请求只会调其中一两个。改成「按意图先分类，再注入对应的 2 到 3 个工具」，单次输入能降 60%，代价是多一次分类判断，用最便宜的小模型跑就行。

对话历史不能无限滚。我的做法是保留最近 6 轮原文，更早的压成一段 200 字以内的摘要，并且摘要里只保留实体名和已确认的约束，不保留推理过程。把「我们讨论过 A 方案但否决了」这种话留在上下文里，除了烧钱还会误导后续生成。

## 前缀缓存只在字节一致时命中

缓存按前缀逐 token 匹配，任何一个字符不同，从那个位置往后全部失效。所以系统提示词里塞一个当前时间戳，等于把整块缓存作废。同理，JSON 里键的顺序不稳定、工具列表顺序每次 `Object.keys` 打乱，都会导致命中率长期贴着 0。

可缓存的前缀要满足三条：内容确定、顺序确定、放在最前面。把时间、用户 ID、随机 ID 统一挪到末尾的用户消息里。

命中之后的价格通常只有原价的 10% 到 25%，具体看厂商。计入方式要注意，有的厂商缓存写入按 1.25 倍收费，只有读取才打折。短期高频访问才划算；一个系统提示词一天只用三次，写入溢价可能亏。

下面这张是常见的账面对比，单价用相对值，重点看比值：

| 场景 | 输入单价 | 输出单价 | 备注 |
| --- | --- | --- | --- |
| 普通输入 | 1.0 | 4.0 | 基准 |
| 缓存命中 | 0.1–0.25 | 4.0 | 只对输入生效 |
| 缓存写入 | 1.25 | 4.0 | 部分厂商收 |
| 批处理接口 | 0.5 | 2.0 | 延迟放宽到 24h |

输出单价普遍是输入的 4 倍，这条比例决定了优化的优先级：先把输出压短，再谈输入。

## 输出侧的三个硬手段

`max_tokens` 必须显式设置。不设的时候，模型可能写出一段八百字的开场白，而你只需要一个 JSON。设 512 不是让回答变差，是逼模型先给结论。

停止序列比 `max_tokens` 更精细。让它输出结构化结果时，约定以 `</answer>` 结束，把这个串放进 `stop`，模型写完就停，不用等它把后面的解释也吐出来。

结构化输出本身也是省钱手段。让模型输出 200 字的自然语言，前端再正则解析，出错就重试一次，成本翻倍；让它直接输出 60 字的 JSON，解析失败率降到 1% 以下。字段名要短，`{"q":"...","a":"..."}` 比 `{"question":"...","answer":"..."}` 在每个 token 上都便宜，批量一万次就是真金白银。

## 批处理与降级

能等 24 小时的任务全部走批处理接口，价格通常是实时的一半，且不计入实时速率限制。离线打标、历史数据清洗、评测集回放，都归这一类。判断标准只有一个：用户是否在等结果。在等，就走实时。

降级要按任务难度分层，不是简单换个便宜模型。

| 触发条件 | 动作 | 风险 |
| --- | --- | --- |
| 单请求预算超 3 万 token | 截断检索片段到 8 条 | 可能丢关键上下文 |
| 连续两次 JSON 解析失败 | 换小模型重写，限 300 token | 质量下降 |
| 月度消耗达预算 80% | 关闭非核心功能的多轮追问 | 体验变差 |
| 达 100% | 只保留缓存命中请求 | 冷请求失败 |

第三、四档要有告警，并且降级开关必须能单独关掉某一个功能，而不是全局一刀切。我踩过的坑是把降级做成全局 flag，结果预算触发时连登录验证码识别都停了。

最后一条经验：给每次请求记 `input_tokens`、`cached_tokens`、`output_tokens`、`model`、`feature` 五个字段，按 feature 聚合。多数项目的成本失控来自某一个功能，而不是整体涨价，没有 feature 维度就无法定位。
