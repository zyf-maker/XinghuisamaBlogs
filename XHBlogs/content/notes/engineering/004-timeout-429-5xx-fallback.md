上游模型服务的失败不是一种故障，是三种，混在一起处理一定出错。超时说明请求可能还在跑，重试等于放大负载；429 说明你配额用完了，立刻重试是自残；5xx 说明对面出问题，跟你无关，但恢复时间不可预测。三类的正确动作完全不同，得分开写。

## 先分类，再决定要不要重试

| 故障类型 | 典型表现 | 请求是否已被处理 | 正确动作 | 禁止动作 |
| --- | --- | --- | --- | --- |
| 客户端超时 | `ReadTimeout`、`ECONNRESET` | 不确定 | 有限重试，同一 prompt 幂等 | 无限重试 |
| 429 | `rate_limit_exceeded` | 未处理 | 读 `Retry-After`，排队 | 立即重试 |
| 5xx | `500`、`502`、`503` | 不确定 | 退避重试，切备用商 | 打满并发 |
| 4xx 参数错 | `400`、`422` | 未处理 | 不重试，修参数 | 重试 |
| 内容拦截 | `finish_reason=content_filter` | 已处理 | 不重试 | 换措辞绕过 |

第一行那个「不确定」是关键。超时的时候请求可能已经在上游生成了，你重试一次就是两份账单，并且可能拿到两段内容。所以带副作用的调用（写文件、发消息）不能盲目重试，只能重试纯生成。

## 一级：连接与读取分开超时

把 `timeout=30` 这种单一值换成三段：

```python
import httpx

timeout = httpx.Timeout(
    connect=5.0,      # DNS + TLS + TCP
    read=60.0,        # 单次读等待，不是总时长
    write=10.0,       # 发送请求体
    pool=2.0,         # 从连接池取连接
)
client = httpx.Client(timeout=timeout, limits=httpx.Limits(
    max_connections=32, max_keepalive_connections=8))
```

`read` 在流式场景下是「两帧之间的最大间隔」，这正好对应心跳周期。心跳 15s，`read` 给 60s 就有四次容错。

总时长超时要单独做，用 `asyncio.timeout` 包住整个消费循环。两者不能只取其一：只有总时长，短连接的慢握手会吃掉全部预算；只有 read 超时，上游每秒吐一个字，请求能挂一小时。

## 二级：429 要读响应头，不要猜

429 的响应通常带 `Retry-After`，值是秒数或 HTTP 日期。没有这个头时，用指数退避加抖动：`min(2 ** attempt, 30) * random(0.5, 1.5)`。抖动是必需的，否则一批并发请求会在同一毫秒同时醒来，把刚恢复的配额再打空一次。

重试次数设 2 次，不要更多。三次重试意味着一个用户请求最多消耗四份配额，在配额耗尽时会把整个服务拖死。

真正的解法是排队而不是重试。本地维护一个令牌桶，容量等于你想要的突发上限，速率等于配额的 1/60。请求先取令牌，取不到就进队列，队列超过 200 或者等待超过 8s 就返回降级结果。这样 429 会从常态变成异常。

RPM 和 TPM 是两个独立限制，取更严的那个。一个 2000 token 的请求在 TPM 60k 的配额下，一分钟只能发 30 次，远小于 RPM 500 的要求。按 RPM 估算并发是常见错误。

## 三级：5xx 时切备用，但别切太早

备用商切换要满足两个条件：主路径连续失败 3 次，且熔断器处于打开状态。只按单次失败就切，会因为对方偶发的一个 502 把流量全导到备用，而备用商往往在上下文长度、结构化输出支持上有差异，切过去就是一类新 bug。

熔断器参数用这几个就够：滑动窗口 30s，最少 20 个样本，失败率超过 50% 打开，打开后 20s 半开试一个请求。半开成功一次就关闭，失败就再等 20s。

失败率阈值不能设 10%，正常波动就能触发。也不能只统计 5xx，把超时算进去才有意义，因为上游过载时最先表现的是慢而不是错。

降级后的输出必须标记。响应里加一个 `degraded: "backup_model"`，前端可以显示一个不显眼的提示，日志里能按这个字段统计降级比例。没有标记的降级是事故，因为一个月后没人知道那条质量下滑的数据是怎么来的。

## 一个能跑的退避实现

```python
import asyncio, random

class UpstreamError(Exception): ...
class RateLimited(UpstreamError): ...

async def with_retry(fn, *, attempts=2, base=1.0, cap=30.0):
    for i in range(attempts + 1):
        try:
            return await fn()
        except RateLimited as e:
            if i == attempts:
                raise
            wait = float(e.args[0]) if e.args else min(base * 2 ** i, cap)
            await asyncio.sleep(wait * random.uniform(0.5, 1.5))
        except UpstreamError:
            if i == attempts:
                raise
            await asyncio.sleep(min(base * 2 ** i, cap) * random.uniform(0.5, 1.5))
```

注意 `except RateLimited` 排在前面。429 的等待时间应当尊重服务端给的数，不要用自己的退避覆盖；5xx 没有这个信息，才用指数退避。两个 `except` 顺序写反，`Retry-After` 就被忽略了。

同步客户端里 `asyncio.sleep` 换成 `time.sleep`，逻辑一样。但别在事件循环线程里调同步客户端，一个 8s 的 sleep 会卡住整个 worker。

## 别忘了一致性

同一次重试必须带同一个幂等键。多数厂商支持在请求头里放 `Idempotency-Key`，没有的话自己在本地缓存 `(trace_id, attempt)` 到响应的映射，超时重试后拿到两份结果时，丢弃后到的那份。

流式请求的重试最麻烦。已经给前端推了 300 字，重连后重新生成，前端会看到内容跳变。处理办法是重连时携带前缀，让服务端校验前缀一致再续写；不一致就发一个 `event: reset`，前端清空重来。没有这个事件的协议，只能选「保留已收到的部分，不重试」。

## 压测这两个数才有意义

上线前至少要压出两个数字：单实例在首 token 延迟 P95 不超过 3s 时的最大并发；配额耗尽时的排队深度与平均等待。第一个决定副本数，第二个决定队列上限。

我的默认值是队列 200、等待上限 8s、并发 32。这三个数没有普适性，但作为起点够用，跑一轮压测再调。压测时不要只测成功路径，把上游 429 的比例注入到 10%，观察重试放大倍数。超过 1.3 就说明退避参数太激进。
