问「你检查一下有没有问题」，得到的一定是「我已经检查过，没有发现问题」。这不是模型在撒谎，是这个问题本身在索取结论。结论是免费的，证据才有成本。要让它真的审一遍，得把提问从「你觉得对不对」改成「把能证明它对的输出贴出来」。

## 结论型提问为什么必然失败

模型对「有没有问题」这个问题没有内部状态可查。它没有跑过代码，也没有持有一份「我刚才哪里不确定」的清单。它回答的其实是一个语言问题：一段自查报告长什么样。训练数据里的自查报告几乎都以「未发现问题」结尾。

所以真正被执行的是措辞习惯，不是检查动作。

这个问题还有一层更隐蔽的后果：一旦它宣布「没有问题」，后面你指出 bug，它就进入解释模式，开始论证那个 bug 不算 bug。立场一旦形成，纠正成本比重新生成还高。

## 把要求换成可提交的物证

有效的自审提问只包含三类要求：贴命令、贴 diff、贴失败用例。它们共同的特征是，伪造的成本比执行高。

| 索取的东西 | 具体问法 | 为什么难以糊弄 |
| --- | --- | --- |
| 命令与输出 | 跑 `npm run build`，把最后 20 行原样贴出 | 真实输出有哈希、有耗时，编不出来 |
| 改动范围 | `git diff --stat` 的结果 | 行数和你预期不符时立刻暴露越界 |
| 失败用例 | 你新加的用例，故意改坏一处，它应该红 | 用例能红才证明它真的在测 |
| 边界输入 | 空数组、单元素、超长字符串各跑一次的结果 | 三行输出无法用「已处理」概括 |

第三条是最有信息量的。一个测试写完立刻通过，通常说明它什么都没测。要求模型先把实现改坏、确认测试变红、再改回来，这个动作叫变异检查，它能把「测试存在」和「测试有效」区分开。

## 让它自己跑，而不是自己说

把审阅写成一次可执行的动作，附在提问末尾。四段分别对应构建、用例、改动范围、边界输入：

```bash
npm run build 2>&1 | tail -20
npx vitest run --reporter=verbose 2>&1 | tail -15
git diff --stat
node --input-type=module -e "
import { parse } from './lib/parse.mjs';
for (const x of ['', 'a', 'x'.repeat(5000)]) {
  try { console.log(x.length, typeof parse(x)) } catch (e) { console.log(x.length, 'THROW', e.message) }
}
"
```

四条里第二条给的是 verbose 输出，能看到每个用例名和耗时；第四条用一个极短的脚本打三种边界输入的返回类型，比任何「已处理边界情况」的描述都硬。

回报格式也要指定：先贴四条输出，再写一句结论。顺序不能反。先写结论的模型会为结论找证据，先贴输出的模型只能顺着输出说话。

## 审阅要问「哪一条最可能错」

这是我从代码评审里搬来的做法。泛泛地问哪里有问题，得到的是自我辩护；指定一个方向问，得到的是具体怀疑。

有效的问法是：「这四条里哪一条最可能在生产环境失败，为什么，需要什么输入才能触发。」它强制模型给出一个排序和一个触发条件，而不是一句「都很稳健」。

同类问法还有几个，换着用，避免它记住套路：

1. 如果输入是恶意构造的，第一个崩的地方在哪
2. 这段代码在并发下哪一行会出问题
3. 你改的这个函数，调用方有没有可能传 `undefined`
4. 这个优化在数据量降到 100 条时还是不是优化

第四类问题特别有用。很多优化只在特定规模成立，模型给出方案时默认了大数据量，你追问小规模，它会承认那里反而更慢。

## 我踩过的坑：让它审自己写的 diff

有一段时间我习惯在改完之后追加一句「review your changes」。结果它每次都能列出一堆改进点，然后开始改，改完又列出一堆，来回四轮，代码越改越复杂，最终版本比第一版长了三倍，多出的是 `try/catch` 和用不上的参数校验。

原因很直接：它在做的是「找出还能改进的地方」，这是一个永远不会返回空集的任务。任何代码都有可改进空间。

改成限定范围就正常了：「只回答一个问题：这次改动有没有破坏原有行为。判断依据是 `git diff` 里删掉的每一行，逐行说明它被谁替代。没有替代的，指出来。」

删掉的行是有限的、可枚举的，这个任务有终点。审阅一旦有终点，输出才有用。

## 分两轮，别混在一起

审阅和重构要分开。同一轮里既让它找问题又让它改，它会顺手改掉没被问到的地方，diff 变得不可审。

我的做法是：第一轮只出证据和结论，不改代码；第二轮拿着第一轮的清单，一条一条改，每条改完贴一次 diff。两轮之间由我决定哪些问题值得改、哪些是误报。

误报率通常在三分之一左右。典型误报是把「风格不一致」当成缺陷、把「没有类型注解」当成 bug、把上游库的行为当成自己的错。分两轮之后这些误报会被自然过滤，因为它们在清单里显得很轻，而真正的缺陷带着触发条件。

## 证据链要能被人复算

最终判断标准很简单：拿它贴出来的命令，自己在干净环境里跑一遍，结果应当一致。

不一致的情况我遇到过两次。一次是它贴的测试输出来自本地已存在的旧产物，重新构建后用例失败；另一次是它把 `tail` 之后的输出截断，恰好截掉了 warning 行。

所以贴证据时要求写全：命令、工作目录、退出码。三者齐全时复算才有意义。只贴一段看着像输出的文本，等于什么都没贴。

这条要求对人也一样。我给自己的规矩是，任何「已修复」的结论后面必须跟一条可复制的命令。写不出命令的修复，通常还没修。
