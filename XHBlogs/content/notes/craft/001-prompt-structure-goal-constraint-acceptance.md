同一件事，问法不同，结果差一个量级。差别不在措辞好不好听，而在信息结构：目标说清了没有，约束给了没有，什么算做完定义了没有。这三样缺任何一样，模型都会替你填，填出来的东西通常不是你想要的。

## 缺目标时模型会自己发明目标

「帮我优化一下这个函数」是最典型的坏提问。优化什么？是执行快、内存少、可读性好、还是减少依赖？这四个方向互相冲突，模型只能猜一个。猜错的代价不是它写错代码，而是它写了一堆正确的、但跟你要的不是一回事的代码，你要么重问，要么在错误方向上继续加要求。

改成一句话：「这个函数在 10 万条记录上跑 40 秒，目标是把耗时压到 8 秒以内，允许牺牲可读性，不许引入新依赖。」

这句话里包含了三件事：现状有数字、目标有数字、代价被指定。剩下的空间就只剩真正的技术选择。

目标里我最看重的是「现状有数字」。没有基线，任何改动都无法判断是否有效，模型也失去了自检依据。它会把「看起来更快」当成完成。给一个具体的 40 秒，它才知道要看循环次数、要提 N+1 查询、要加索引。

## 约束要写成可检验的否定句

约束不是「代码要优雅」，而是「不许出现 `any`」「不许新增 dependencies」「必须兼容 Node 18」。前者无法检验，后者能一条条对。

有效的约束通常落在四类：

| 类别 | 例子 | 为什么有效 |
| --- | --- | --- |
| 禁止依赖 | 不新增 npm 包，只用标准库 | 构建体积、供应链安全都可量化 |
| 禁止改动面 | 只改 `lib/parse.ts`，不动调用方 | 把回归风险关在一个文件里 |
| 兼容边界 | 必须跑在 Node 18，不能用 `Array.prototype.findLast` | 有明确的失败场景 |
| 风格硬线 | 不写 `console.log`，错误一律走 `throw` | 可以直接 grep 验证 |

约束写多了会互相打架，一般三到五条足够。超过八条时，模型开始顾此失彼，你需要重新想清楚哪几条真的是硬线。

有一点经验：把「不要做什么」写得比「要做什么」更具体。人写需求时习惯描述愿景，模型对愿景的理解偏差最大，对禁令的执行反而可靠。

## 验收标准是提问里最值钱的部分

绝大多数提问停在「做个 X」，没有说「怎么算做完了」。模型的默认验收标准是「代码能编译」，这个标准低得可怕。

验收标准要写成可以逐条打勾的形式：

1. `npm run build` 无警告通过
2. 新增的三个用例全部通过，且原有 27 个用例不回归
3. 在 10 万条样本上单次执行低于 8 秒
4. `git diff` 只涉及 `lib/parse.ts` 一个文件

这四条里没有一条需要主观判断。模型改完可以自己对一遍，你也可以对一遍，双方对「完成」的理解是一致的。

我踩过的坑是把验收写成「性能有明显提升」。模型回复「已优化，性能显著提升」，实际只把 `for` 循环换成了 `forEach`，更慢了。换成数字之后它才真的去看算法。验收标准写得越像测试，模型越像工程师。

## 一个可直接套用的模板

```text
目标：<现状数字> → <目标数字>，衡量方式是 <命令或指标>
约束：1) ... 2) ... 3) ...
验收：1) ... 2) ... 3) ...
上下文：相关文件 <路径>，已知问题 <一句话>
```

四行就够。实际用的时候我会把「上下文」写得更长，把相关的报错原文、涉及的函数签名贴进去，但前三行永远保持这个形状，因为它们决定方向。

模板的作用不是让提问变长，而是逼你在提问前想清楚。想不清楚的时候，写这四行会比反复追问模型更快地暴露你哪里没想明白。

验收标准最好能直接变成脚本，贴进提问里。下面这段是我常用的骨架，四条一一对应上面的四行：

```bash
#!/usr/bin/env bash
set -euo pipefail
npm run build 2>&1 | tee /tmp/build.log
! grep -qi "warning" /tmp/build.log
npx vitest run --reporter=dot
node scripts/bench-parse.mjs --n 100000 | awk '$1 > 8 { exit 1 }'
git diff --name-only | grep -qv '^lib/parse\.ts$' && exit 1
exit 0
```

它的价值在于：模型拿到的是可执行的判定，而不是形容词。跑完绿了才算完成，跑不绿就继续改，不需要你在中间裁决「感觉差不多了」。

## 追问时只说差在哪

第一轮回答不理想，不要重写整个提问。指出具体偏差：「第 4 条验收不满足，实测 12 秒，不是我给的 8 秒。约束 2 也被破坏了，多了一个 `lodash` 依赖。」

这样模型拿到的是可定位的差值，不是一次重来。重写提问的坏处是它会顺带丢掉上一轮里正确的部分，然后在新一轮里换一批错误。

只有当偏差超过一半、或者方向本身就错了，才值得重写提问。判断标准很简单：如果是执行没到位，补差值；如果是要做的事变了，重写目标。

## 这套结构解决不了什么

它治不了「你自己也不知道要什么」。目标写不出数字时，问题不在提问技巧，在于需求还没成形。这时候让模型先给三个方案、各自列出代价，比让它直接动手有效得多。

它也治不了模型能力边界。验收标准写得再清楚，做不到就是做不到，这时候该换模型或拆任务，而不是继续加约束。分清这两种失败，比优化措辞有用。
