大任务失败很少是因为模型不会写某个函数，而是因为中间没有任何一处能停下来判断对错。拆解的目的不是把活切小，而是切到每一步都能独立验证：跑一条命令、看一个输出、比一个数字，通过就往下走，不通过就在这一步内改。

## 判据必须是外部可观测的

「这一步完成登录模块」不是判据。「用测试账号 POST /api/login，返回 200 且 body 里有 token 字段」才是判据。区别在于后者的对错不由模型的叙述决定。

我给自己定了一条线：判据如果不能用一条命令或者一次人工点击得出结果，就还没拆完。写成「代码质量良好」「结构清晰」的，等于没有判据，模型只能自己宣布通过。

一份合格的判据包含三样：动作、输入、期望输出。三者齐全时，人和模型看到的是同一个事实。

## 一步的粒度取决于回滚成本

拆多细不是凭感觉。粒度应该跟「这一步做错了要撤多少东西」对齐。改一个纯函数，错了删掉就行，可以拆得很细；动数据库 schema，错了要写迁移回滚，就该把整批变更合成一步，一次做对。

| 变更类型 | 建议粒度 | 判据形态 | 回滚成本 |
| --- | --- | --- | --- |
| 纯函数、工具方法 | 一个函数一步 | 单元测试通过 | 删除即可 |
| 单个接口 | 一个路由一步 | curl 拿到预期状态码与字段 | 删文件 |
| 跨文件重构 | 一次一类改动一步 | 构建通过 + 用例不回归 | 需要 git 回退 |
| 数据迁移 | 整批一步 | 迁移后抽样校验行数 | 需要反向脚本 |
| 依赖升级 | 一个大版本一步 | 构建 + 全量用例 | lockfile 回退 |

这张表的作用是防止两种极端：把迁移拆成五步，每步都跑不完整，中间态无法验证；或者把重构合并成一步，出错时不知道是哪一处引起的。

## 每步要有自己的「完成信号」

一步做完，屏幕上应该出现一个具体的东西：一条绿色的测试、一段正确的 JSON、一张渲染出来的截图。没有这个信号，就不能开始下一步。

给一个具体做法，把判据写成脚本，让它跑。下面两条是「导入器能处理正常与畸形两种 CSV」这一步的完成信号：

```bash
node scripts/import.mjs fixtures/ok.csv && echo "PASS normal"
node scripts/import.mjs fixtures/broken.csv; test $? -eq 2 && echo "PASS reject"
```

第二行的分号不能用 `&&` 代替。`broken.csv` 的期望行为是退出码 2，用 `&&` 串联时它一旦正确失败，后半句 `test` 根本不执行，判据失效。这种细节只有真跑过才会注意。

判据写成 `exit code` 有额外好处：它不会因为措辞含糊而被绕过。模型说「已处理异常」，但退出码是 0，那就是没处理。

同一步里往往有好几条判据，串起来跑，任何一条失败就当场停：

```bash
step() { local name=$1; shift; echo "== $name"; "$@" || { echo "FAILED: $name"; exit 1; }; }
step "构建"  npm run build
step "单测"  npx vitest run --reporter=dot
step "词表"  node scripts/check-synonyms.mjs
```

关键在 `local name=$1; shift` 这个顺序。先把步骤名存进变量再 `shift`，后面的 `"$@"` 才是真正的命令；顺序反了，名字会被当成第一个参数吞掉，命令带着多余参数执行，报的错还与你真正的问题无关。`local` 是 bash 关键字，脚本头写 `#!/bin/sh` 在某些发行版上会直接报 `local: not found`。

## 拆解顺序按依赖排，不按难度排

常见的坏习惯是先做最难的，觉得难的部分搞定了一切都好办。结果是前三天毫无产出，第四天发现难点的前置条件没准备好。

正确的顺序是：先让最细的一条链路端到端通起来，哪怕它只处理一个硬编码的输入，然后再逐个替换掉硬编码的部分。这样每一步都在一个能跑的系统上做增量，任何一步失败都能立刻定位。

具体到「加一个站内搜索」这种任务，我会这样切：

1. 一个写死的查询返回一条写死的结果，页面上能渲染出来
2. 把写死的结果换成从索引文件里读，输入仍然写死
3. 接上输入框，把查询字符串传进检索函数
4. 排序按分数真实排，加同义词表
5. 加空结果状态和错误状态
6. 打分性能：一万条文档下，检索耗时压到 20ms 以内

第四步之后每一步都有独立价值，也都能单独上线。第三步结束时功能已经可用但排序不准，这不是半成品，是可交付的粗糙版本。

## 拆解本身要被审一遍

拆完之后别急着开工。把步骤列表贴回给模型，让它回答三个问题：哪一步的判据无法用命令验证、哪一步依赖了前面没产出的东西、哪一步失败后无法回滚。

这三个问题能筛掉大部分虚假拆解。我遇到最多的是第二类：某一步的判据要读一个「后面才生成」的配置文件。这种依赖倒置在纸质计划里看不出来，一问就露。

还有一个自检：把每步的预估改动量写下来，如果有一步超过 200 行，再拆。超过这个体量时，出错后定位成本会陡增，而且模型自己也会在长文件里丢掉前文的约束。

## 卡住时不要跳步

第 4 步的测试红了，正确的动作是停在第 4 步。跳过它先做第 5 步，会产生一个「看起来都在跑但结果全错」的系统，之后每次调试都要同时怀疑两处。

真有需要并行的情况（比如第 4 步依赖一个还没就绪的外部接口），就显式插一步 mock：把外部接口返回固定值，用它把第 5 步跑通，然后在计划里记一条「等真实接口就绪后，回补第 4 步」。插的那一步也要有判据：mock 返回的字段与真实接口的契约一致，写成一份 JSON schema 校验。

没有记录的跳过，事后一定会被忘掉。

## 一个反面样本

我见过也写过这种计划：

1. 搭好项目结构
2. 实现核心逻辑
3. 完善细节
4. 测试

四步全都不合格。第一步没有判据（什么算搭好），第二步粒度不可控（核心逻辑可能是三千行），第三步是纯粹的填充词，第四步在最后意味着前面三步的错误会累积。

改成这样就有意义：第一步的判据是 `npm run build` 通过且首页返回 200；第二步拆成检索函数、打分函数、接口三个独立步骤，各有测试；第三步本来就是前几步里已经包含的内容，删掉；第四步拆进每一步，不再单独存在。

「测试」永远不该是一个独立步骤，它应该是每步的判据。这一点是我改计划时最先动的刀。
