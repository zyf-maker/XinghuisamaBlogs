我把入门的阅读顺序搞反过一次：先啃了三篇经典论文，笔记做了二十页，然后打开 API 文档发现连 `messages` 数组怎么摆都不知道。那三篇论文讲的注意力机制，在我写出第一个能跑的请求之前，一点用都没有。后来重排了顺序，效率差别很大。这篇讲的就是这个顺序，以及每一步怎么判断自己是真的懂了而不是看懂了字。

## 为什么文档在前

文档是接口的当前事实，论文是方法的某个历史切片。你要做的东西最终落在接口上：字段叫什么、必填哪几个、返回结构长什么样、限流多少。这些东西论文一个字都不会写，写了的也早就过期。

反过来，论文解决的是「为什么这么设计」。当你遇到「为什么上下文一长效果就掉」「为什么同样的提示换个顺序结果就变」这类问题时，论文才有解释力。没有具体问题垫底，读论文只能记住几个名词。

我现在的顺序是三段：先用文档把东西跑起来，再用论文解释跑起来之后看到的怪现象，最后用源码确认边界条件。三段之间不是时间顺序，是依赖顺序，前一段没完成不进下一段。

## 第一段：官方文档，只读四类页

文档很长，绝大多数页面现在用不上。只读四类：认证与快速开始、请求与响应字段、错误码、限流与计费。其余先放着。

判断标准很硬：能不能不查文档写出一个带系统提示、带多轮历史、带结构化输出的请求。写不出来就是没读懂，跟读了多少页无关。

下面这段是我核对「官方示例到底怎么写的」时常用的动作，比在浏览器里翻页快：

```bash
# 只抓文档站的 sitemap，落到本地做全文检索
DOCS_BASE="${DOCS_BASE:?形如 scheme://host，填入文档站根地址}"
curl -sL "$DOCS_BASE/sitemap.xml" -o sitemap.xml
grep -o '<loc>[^<]*</loc>' sitemap.xml | sed 's/<[^>]*>//g' > urls.txt
wc -l urls.txt

# 找到讲结构化输出的那几页，抓下来看字段名
grep -iE 'structured|json.schema|response_format' urls.txt | head -20
```

真正的收获往往在错误码那一页。我踩过的最贵一次是 `429` 和 `402` 混着重试，把额度耗完才发现 `402` 是余额不足，重试一万次也没用。文档里写得清清楚楚，我没读。

## 第二段：论文，只读四篇的量

不是所有论文都值得读，也不是读得越多越好。按「能解决你当下问题」筛，我的清单是四类：

| 想解决的问题 | 该读的方向 | 读到什么程度算够 |
| --- | --- | --- |
| 为什么模型能按指令做事 | 指令微调与人类反馈那条线 | 知道三个阶段各在优化什么，不追公式 |
| 为什么长上下文会退化 | 长上下文评测与位置编码 | 知道「中间段最容易被忽略」这个现象及其量级 |
| 检索为什么要重排 | 检索增强与重排 | 知道召回与精排的分工，能说清为什么先粗后细 |
| 为什么要工具调用而不是纯提示 | 工具使用与规划 | 知道函数签名约束为什么比自然语言描述稳 |

四篇是上限，不是任务。我给自己定的规矩是：一篇论文只允许带走一句话结论和一个数字。带不走数字的，说明只是翻过。比如长上下文那条，我记住的是「关键信息放在开头或结尾，比放在中间，命中率高出一截」，具体倍数记不清没关系，行为改了就行。

读论文最容易掉的坑是按顺序从摘要读到附录，读到第三节就困了。有效的读法是先看图，再看结论，最后才回头找方法里支撑这个结论的那一小段。

## 第三段：源码，什么时候才进

源码不是学习材料，是排错材料。三种情况才值得进去：文档和实际行为不一致、错误信息看不懂、要判断某个参数是不是真的生效。

我进源码的第一次是因为一个「设置了最大输出长度但没生效」的问题。文档说这个参数控制生成长度，实际表现是超了也不截断。翻到服务端的请求校验那层才看到，这个参数在某个模型家族上会被静默忽略。这种结论只能从代码里得到。

读源码有个省时间的做法：不要从头读，用提交历史定位。一个行为是什么时候变的，比它现在长什么样更有信息量：

```bash
git log --oneline --follow -- path/to/handler.py | head -20
git log -S 'max_output_tokens' --oneline -- path/to/ | head -10
```

第二条命令按字符串增删找提交，比读十遍文件快。我第一次用的时候，十分钟就定位到了那个参数的引入和被弃用两次改动。

## 判断是否真读懂的方法

这是我认为最该被写下来的一张表。看懂和读懂的区别，全在能不能自己产出。

| 阶段 | 材料 | 判断方法 | 不合格的信号 |
| --- | --- | --- | --- |
| 接口 | 认证、字段、错误码 | 关掉文档写一个三消息请求并跑通 | 需要边看边抄字段名 |
| 行为 | 计费与限流页 | 预测一次请求的 token 与费用，误差 20% 内 | 不知道输出侧按什么计价 |
| 原理 | 一篇论文 | 用三句话向别人解释，不出现论文原词 | 只会复述摘要句子 |
| 边界 | 相关源码 | 说出一个文档没写的行为，并给出触发条件 | 只能总结「代码结构清晰」 |
| 迁移 | 换一家厂商 | 半天内跑通并说清差异 | 每个字段都要重新查 |

还有一条自检我一直在用：合上所有材料，写一段两百字的说明，讲清这个系统的输入、输出、失败模式。写的时候如果频繁想「这个细节回头查一下」，那就是还没读懂。这段文字写完不用给别人看，它只是让你自己知道卡在哪。

## 顺序之外的两件事

别把材料当进度条。收藏一百篇论文不会让你多懂一点，读完四篇并各写一句话会。我见过太多人的书签里有整套课程，实际动手记录是零。

也别跳过第一段直接读源码。源码能告诉你它怎么实现，不能告诉你它承诺什么。承诺在文档里，实现只是承诺的一种可能。
