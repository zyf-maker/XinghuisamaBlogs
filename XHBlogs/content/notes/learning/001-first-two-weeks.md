我带过几个同事入门，也自己从零走过一遍。结论先放这里：头两周不需要懂 Transformer，也不需要读论文，需要的是把「一次调用花多少钱、上下文什么时候会满、输出什么时候不可信」这三件事变成肌肉记忆。第一版计划我排了二十一天，做到第九天就散了，因为每天的任务太大、验收太模糊。后来砍成十四天，每段只留一个交付物，通过率立刻上来了。

## 计划表

先给全貌，后面按段展开。

| 阶段 | 天数 | 唯一交付物 | 过关标准 |
| --- | --- | --- | --- |
| 摸清计量 | 1-3 | 一个数 token 的脚本 | 估一篇 3000 字文档的 token 数，误差 15% 以内 |
| 打通调用 | 4-6 | 一个会打印用量的脚本 | 换一家厂商只改两个字段就能跑 |
| 做小工具 | 7-10 | 一个自己每天用的命令 | 连续三天在用，单次成本低于 0.05 元 |
| 加检索 | 11-14 | 一个能指回原文的问答 | 20 道自测题答对 16 道以上 |

## 第 1-3 天：把 token 和上下文摸清楚

第一天只做一件事：数。拿一段中文、一段英文、一段代码，分别用 tokenizer 数一遍，记下字符数与 token 数的比值。我手上的样本是中文约 1 字 0.7 token、英文约 1 词 1.3 token、代码约 1 字符 0.5 token，不同厂商的切分差别能到 30%。这个数字决定了你后面所有的成本估算，估错一次，一个批处理任务能从 8 块跑到 60 块。

第二天算窗口。把你常用的模型上下文长度写下来，然后算：一份 2000 字的需求文档、20 轮对话历史、一段 500 行代码，加起来多少 token，占窗口多少。我实测过，20 轮正常对话大概是 6000 到 9000 token，看着不多，但每轮都要把历史重发一遍，费用是轮数的平方级增长。

第三天做减法。写一个脚本，把超长文本按段落切块，打印每块 token 数，找出超过 800 的那几段。验收标准是你能对着任意一篇文档说出「这份塞不进去，得切三段」。

## 第 4-6 天：第一次真正调通

第四天不写代码，先用 `curl` 打一次。这一步的价值在于把变量减到最少：密钥对不对、网络通不通、模型名拼没拼错，一次就能分清。最常见的两个错误是 401 和 404，401 是密钥问题，404 多半是 `base_url` 少了 `/v1`，我在这上面浪费过一个下午。

第五天换成 Python，并且强制自己打印 `usage` 字段：

```python
import os, json, time
from openai import OpenAI

client = OpenAI(
    base_url=os.environ["BASE_URL"],
    api_key=os.environ["API_KEY"],
)

def ask(prompt: str, temperature: float = 0.0) -> dict:
    t0 = time.time()
    resp = client.chat.completions.create(
        model=os.environ["MODEL"],
        messages=[{"role": "user", "content": prompt}],
        temperature=temperature,
    )
    usage = resp.usage
    print(json.dumps({
        "prompt_tokens": usage.prompt_tokens,
        "completion_tokens": usage.completion_tokens,
        "latency_s": round(time.time() - t0, 2),
        "finish_reason": resp.choices[0].finish_reason,
    }, ensure_ascii=False))
    return {"text": resp.choices[0].message.content, "usage": usage}

if __name__ == "__main__":
    ask("把下面三条待办按紧急程度排序，只输出编号：1 修线上告警 2 写周报 3 整理书签")
```

第五天的验收是：同一个 prompt 跑三次，`prompt_tokens` 完全相同，`completion_tokens` 有波动。如果你看到 prompt 侧也在变，说明消息拼接里混进了时间戳之类的东西，后面做缓存会一直对不上账。

第六天做参数对比。固定 prompt，把温度从 0 调到 1，各跑五次，把输出贴在自己的笔记里。你会看到温度 0 也不是完全确定，这是正常的，服务端有批处理带来的微小差异。这一天的产物是一句话结论：这个任务我该用哪个温度。

## 第 7-10 天：做一个真会用的工具

选题目只有一个标准：你自己每天都烦的那件事。我选的是把一天里的会议记录和零散笔记压成一页周报草稿。别选「通用问答机器人」，那个东西没有验收标准，做完了你也不会打开第二次。

第七天定输入输出。输入是一个目录下的 `.md` 文件，输出是 `out/week.md`。要求写死在提示里：只输出三段，每段不超过 80 字，不带小标题以外的任何格式。

第八天加工程细节。三个必须有的：失败重试（指数退避，最多三次）、成本打印（每次跑完输出总 token 与估算金额）、原子写入（先写 `.tmp` 再改名）。第三条最重要，我有一次跑到一半超时，半截结果直接盖掉了旧文件，只能从备份里捞。

第九天让它能被别人用。`--dry-run` 只打印将要发送的内容不发请求，`--since` 只处理最近修改的文件。参数不加这两个，你调提示词的时候会一直烧钱。

第十天验收。连续三天在真实工作里用它，如果第三天你还在手动改它的输出，说明提示词的分段约束不够硬，回去改提示而不是改代码。

## 第 11-14 天：加检索，先别碰向量库

多数教程在这里直接上向量数据库，我认为是弯路。你的语料如果是几十份文档，SQLite 自带的全文检索就够，零依赖、能排序、出错时能一眼看出为什么命中。

第十一天建索引。分块按段落走，单块控制在 300 到 500 字，相邻块重叠 50 字，避免一句话被切断。

```bash
sqlite3 notes.db <<'SQL'
CREATE VIRTUAL TABLE IF NOT EXISTS chunks USING fts5(
  doc, seq, body, tokenize="unicode61 remove_diacritics 2"
);
SQL
```

第十二天接查询。取 top 5，把片段编号后塞进提示，要求回答里每个论断后面带 `[n]`。这一步的验收不是「答得像」，而是「答得可查」：你能顺着编号回到原文那一段。

第十三天做拒答。在提示里明确写：如果给定片段无法支撑答案，就输出「材料里没有」。我第一版没写这句，模型会把相邻领域的常识补进去，读起来很顺，全是错的。

第十四天自测。自己写 20 个问题，其中 5 个是材料里确实没有答案的。过关线是 15 个有答案的题里答对 12 个，5 个无答案的题里至少 4 个说没有。低于这个数，问题八成在分块，不在模型。

## 我卡住的两处

第六天我卡在「温度 0 为什么还不一样」，当时以为是厂商在骗人，后来读到服务端会把请求打成批、浮点累加顺序不同，才接受这件事。接受之后就明白：需要严格可复现的场景，不能只靠温度，得靠结构化输出加校验。

第十二天我卡在召回全空。查了两小时，原因是 FTS5 默认分词不认中文，整句被当成一个词。改成 `unicode61` 并按标点预切分之后才正常。这一条写在这里，能省你一个晚上。
